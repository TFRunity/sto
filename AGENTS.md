# AGENTS.md — карта знаний проекта СТО

## Старт работы

1. Прочитай этот файл и `AGENTS.local.md`, если он есть.
2. Если продолжаем по плану, открой верхний блок [stuff/TODO.md](stuff/TODO.md) и файл текущего вечера. Для точечной задачи сразу используй карту ниже.
3. Прочитай связанные исходники и нужные разделы ADR или решений. Полный план и справочники открывай, когда они нужны для задачи.
4. В рамках одного диалога используй уже прочитанные правила и контракты. Перечитывай затронутые разделы, если файл изменился или нужна точная сверка.
5. Для диагностики начинай с сообщения об ошибке и короткой проверки гипотезы. В больших файлах и сгенерированных схемах сначала найди нужный символ или маршрут, затем прочитай его с ближайшим контекстом. Расширяй чтение, если этого требует проверка.

v1 — Gateway, Users, Orders, Vehicle, Inventory, Services, общий Go-модуль `chassis`, веб клиента и директора и Android инженера. Сага оплаты входит в v1. Проектирование и реализация Chat и Reports отложены до [v2](stuff/v2/README.md).

## Запуск только с разрешения разработчика

Агент запускает следующие команды только после явного разрешения в чате:

- Любые цели `make`, любые команды `docker` / `docker compose`, скрипты проекта, включая `scripts/e2e.sh`.
- `go build`, `go test`, `go run`, `go generate`, `go mod tidy`, сборку фронтенда, генераторы, `goose` и `golangci-lint`.
- Установку пакетов и инструментов, включая команды npm, Expo, apt, pip и `go install`.

Сначала напиши точную команду, её назначение и что она изменит в файлах, кэше, контейнерах, томах или БД. Разрешение действует на один запуск указанной команды, если разработчик явно не указал иное. Чтение и правки файлов в рамках задачи и команды только для чтения разрешены. Коммиты и push по умолчанию делает разработчик. Явная просьба закоммитить разрешает локальный коммит.

## Правила, которые нужны без дополнительного поиска

- **Фронтенд.** Папка задаёт сценарий. `view.tsx` — UI, состояние и навигация. `form.ts` или `form.tsx` — описание полей и валидация. `controller.ts` — запросы и обновление кэша. Экран без формы обходится без `form`. Поиск оформляем подпапкой `search/` с теми же именами.
- **Границы модулей.** Соседние сценарии не импортируют друг друга. Переиспользуемый код поднимаем в `shared/` ближайшего общего родителя. Код одного клиента размещаем в его `common/`, а общий для веба и Android — в `frontend/common/`. Оба клиента импортируют общую схему OpenAPI оттуда.
- **Go.** Группируй по домену. Транзакции открывай в репозитории, решения оформляй чистыми доменными функциями, переходы делай условным UPDATE по ADR-031. Ошибки API используют общий конверт `{"error":{"code","message","fields"}}`. Для тестов используй ручные fake, без `testify/mock`.
- **Переиспользование в Go.** Выноси код по факту повторов. Внутри файла используй приватную функцию, между файлами модуля — его `utils`, между модулями сервиса — `chassis`. Общую HTTP-обвязку, конфиг, логи, outbox и RabbitMQ выноси в `chassis` сразу, если они нужны нескольким сервисам.
- **SQL.** PostgreSQL 18, отдельная БД для каждого сервиса. Применённые миграции исправляй новой forward-миграцией. Для таблиц с soft delete фильтруй `deleted_at IS NULL` либо помечай запрос `-- include-deleted`. Сгенерированные артефакты хранятся в репозитории.
- **ADR и UML.** Перед изменением архитектуры сверяйся с ADR. Противоречие обсуждай с разработчиком. Старый ADR сохраняй с отметкой «Заменено на ADR-0XX». При добавлении use case сразу добавляй sequence diagram, включая простые сценарии чтения. Единственное исключение в v1 — «Управлять каталогом», его покрывают две дочерние диаграммы. Контрольный счёт v1 — 22 use case и 21 sequence diagram. При изменении модели или решения обновляй [диаграмму классов](stuff/uml/class/class-diagram.drawio) и затронутые диаграммы.
- **Источники и заметки.** Открытые вопросы ведём в [TODO](stuff/TODO.md). При реализации сверяйся с документацией инструментов, в том числе Gotenberg, RabbitMQ, sqlc, goose и oapi-codegen. История решений А-NN — в [stuff/CHANGES-v1.md](stuff/CHANGES-v1.md). Личные заметки храни в локальном `AGENTS.local.md` вне коммитов.

## Режим работы B + C

- Агент делает фронтенд, документацию, инфраструктуру, SQL, OpenAPI, конфиги генерации и Go-скелеты без тел функций. Сборки и генерацию запускает по правилу разрешения.
- Go-логику, включая домен, хендлеры, репозитории, `chassis`, сборку зависимостей и тесты, пишет разработчик. Агент сразу показывает готовый код в чате в вариантах «плохо / отлично» с плюсами и минусами и правит Go-логику в файлах по прямой просьбе.
- На ревью сверяй изменения с нужными ADR, сквозными правилами и [критериями по читаемости кода](#читаемость-кода-на-ревью). `make test` и `make lint` запускай с разрешения. Отчёт содержит находки и ссылки. В режиме ревью исправления вносит разработчик.
- Сначала рабочий минимум по критерию задачи. Добавляй следующее усложнение, когда оно требуется. В рамках плана можно назвать следующий пункт, решение о внеплановых шагах остаётся за разработчиком.

### Читаемость кода на ревью

Правила действуют для фронтенда и бэкенда.

- **Разбивай большие функции-сценарии на шаги.** Оставляй в основной функции порядок действий и обработку результата. Самостоятельные шаги выноси в небольшие функции с понятными именами и одной ответственностью, даже если у шага один вызов. Проверяй, что по именам шагов можно прочитать сценарий сверху вниз. Простую операцию оставляй на месте, если выделение добавляет переход к другому участку кода без пользы для чтения.
- **Подробно комментируй сложный код.** В начале сложного сценария кратко опиши ход выполнения, если он распределён по нескольким функциям или компонентам. Рядом с неочевидными шагами и ветками объясняй, почему важны порядок, условия, гарантии и обработка ошибок или повторов. Покрой комментариями все существенные нюансы, которые нельзя восстановить по именам и коду. Простые операции читаются из самого кода.
