## ⛔ ГЛАВНОЕ ПРАВИЛО: запуск только с разрешения разработчика (31.10.2026)

Агент **не запускает** без явного разрешения разработчика в чате:
- `make` — любые цели (`generate`, `build`, `test`, `lint`, `up`, `down`, …);
- `docker`, `docker compose` — любые команды (сборка, запуск, остановка, удаление, `pull`);
- скрипты проекта (`scripts/*.sh`, в том числе `e2e.sh`);
- `go build` / `go test` / `go run` / `go generate` / `go mod tidy`, генераторы (`sqlc`,
  `oapi-codegen`), `goose`, `golangci-lint`;
- установку чего-либо (`apt`, `go install`, `npm`, `pip`, `curl | sh`).

Порядок: агент пишет **точную команду**, что она делает и что изменит (файлы, контейнеры,
тома, БД), и **ждёт**, пока разработчик прочитает и ответит «можно». Разрешение — на эту
команду один раз, не на «такие команды вообще», если разработчик явно не сказал иначе.

Без разрешения можно: читать файлы, создавать и править файлы в рамках роли агента (B),
команды только для чтения (`ls`, `cat`, `grep`, `find`, `git status` / `diff` / `log`).

## Команды (цели корневого Makefile, ADR-014 / ADR-036)
Makefile появится на этапе «Каркас». Пока его нет — команды не угадывать.
- Генерация (sqlc + oapi-codegen): `make generate`
- Тесты: `make test` (по модулю: `make test MODULE=orders`)

## Раскладка репозитория (ADR-036, Решение А-10 (принято 30.10.2026))
```
<repo>/
├── go.work · Makefile · docker-compose.yml · .env.example · .golangci.yml

└── <service>/                gateway, users, orders, vehicle, inventory, services
    ├── go.mod · Dockerfile · sqlc.yaml
    ├── cmd/<service>/main.go
    ├── internal/             по домену (ADR-004)
    ├── migrations/           goose, только forward, go:embed (ADR-024)
    └── queries/              SQL для sqlc
```

## Схема данных / БД
- Миграции: `<service>/migrations/*.sql` — первоисточник схемы, sqlc читает схему отсюда.
- Запросы: `<service>/queries/*.sql`; сгенерированный код коммитится.
- PostgreSQL 18, по контейнеру на сервис (ADR-001, ADR-038).
- Soft delete — `deleted_at`; каждый запрос фильтрует `deleted_at IS NULL` или помечен
  `-- include-deleted` (ADR-033).

## Конвенции кода
- Структура — по домену, не по слою (ADR-004).
- Ошибки API — конверт `{"error": {"code", "message", "fields"}}` из `chassis` (ADR-032).
- Транзакции — в репозитории, решения — чистые доменные функции, переходы состояний —
  условный UPDATE (ADR-031).
- Моки — ручные fake-структуры, без `testify/mock` (ADR-013).
- Линтер — `.golangci.yml`, golangci-lint v2 (ADR-014).

### Версии: v1 и v2

Проект разделён на две части (решение 19.10.2026):
- v1 — текущий рабочий объём; лежит в **корне репозитория** (31.10.2026: содержимое `v1/`

  (`adr/`, `uml/`, `design/`, `decisions/`) считаются от него.
- `v2/` — модули, отложенные на вторую версию: **Chat** (сервис, WebSocket, ADR-018) и
  **Reports** (сервис, отчёты, «Статистика по сотрудникам»). В v1 их не реализовывать и не
  проектировать; материалы лежат в `v2/` в той же раскладке.
- Сага оплаты (outbox, `saga_state`, RabbitMQ, списание в Inventory) остаётся в v1 полностью.
- Состав v1: Gateway + Users, Orders, Vehicle, Inventory, Services; общий код — `chassis`.
- Пока — только бэкенд; клиенты (веб, RN) — позже.
- Чек-лист возврата v2 в v1 — `v2/README.md`.

### Источник правды по архитектуре
Все архитектурные решения, обоснования и рассмотренные альтернативы —
в ADR (Architecture Decision Record), по темам:
```
adr/
├── architecture/    структура сервисов, сага, БД, паттерны
├── security/        модель доверия, секреты, RabbitMQ, периметр
├── testing/         объём тестирования, CI
├── stack/           выбор библиотек и инструментов
└── infrastructure/  Docker, Compose, nginx
```
Перед архитектурным решением или кодом, затрагивающим уже решённый
вопрос — свериться с соответствующим ADR. Если решение противоречит
существующему ADR — не менять его молча, явно спросить пользователя;
старый ADR в таком случае помечается «Заменено на ADR-0XX», не
удаляется.

Пометка **«Решение А-NN»** в ADR и диаграммах — конфликт, который был разрешён без
разработчика и затем разобран с ним (30.10.2026). История разбора — `CHANGES-v1.md`.

### Правило вынесения переиспользуемого кода
По нарастанию области видимости, по факту уже существующего
дублирования — не заранее, не на основании предположения о будущем
использовании:
1. Код, повторяющийся в нескольких местах одного файла — приватная
   функция в этом же файле.
2. Функция из п.1, нужная в нескольких файлах одного модуля —
   выносится в модуль `utils` внутри сервиса.
3. Функция, нужная в нескольких модулях одного сервиса — выносится
   сразу в `chassis`, минуя локальный `utils`: код, нужный нескольким
   модулям внутри сервиса, с высокой вероятностью понадобится и
   другим сервисам — переносить его в chassis позже обычно дороже.

### Sequence diagrams — 1:1 с use case diagram
Каждый use case на диаграмме (`uml/use-case/`) получает свою sequence diagram — без
исключений, включая простое чтение (`Смотреть дашборд`, `Смотреть карточку ТС` и т.п.),
даже если процесс линеен. Цель — возможность в любой момент физически сверить число
файлов в `uml/sequence/` с числом эллипсов на use case diagram и увидеть расхождение,
если что-то забыто. При добавлении нового use case — сразу заводить соответствующий
файл sequence diagram, не откладывать.

**Счёт для v1:** на use case diagram 22 эллипсов, в `uml/sequence/` 21 файлов. Разница — «Управлять каталогом» (родитель обобщения: отдельной диаграммы нет, его покрывают `sequence-catalog-items` и `sequence-catalog-services`).

### Диаграмма классов

### Режим работы — агентная разработка с обучением (B + C, решение 30.10.2026)
Пользователь учится писать Go — это по-прежнему фокус проекта. Работа разделена по типу кода:
**рутину без учебной ценности делают агенты, Go-логику пишет разработчик, а агент-ревьюер
проверяет каждый его кусок.**

**Агенты делают (B):**
- документацию: ADR, UML, `TODO.md`, файлы решений;
- инфраструктуру: `docker-compose.yml`, Dockerfile, nginx, definitions RabbitMQ, Makefile,
  CI (`.github/workflows`), `.golangci.yml`, `.env.example`;
- SQL: миграции goose, запросы для sqlc, `sqlc.yaml`;
- контракт: `api/openapi.yaml`, конфиги генерации; запуск генерации (sqlc, oapi-codegen);
- скелеты: `go.mod`, `go.work`, каталоги, пустые пакеты с объявлением `package` и
  комментариями `// TODO(dev): …` — **без тел функций**.

**Разработчик пишет сам** — любой Go-код с логикой: домен и доменные функции,
репозитории, хендлеры, сервисный слой, сагу, outbox-воркер, консьюмеры, middleware,
весь `chassis`, `main.go` (сборка зависимостей, graceful shutdown), тесты.
- Агент не пишет этот код за разработчика. Вместо готового решения — наводящие вопросы,
  объяснение концепции, примеры не из этого проекта, два варианта «плохо / отлично».
- Если разработчик прямо просит готовый код — сначала уточнить, что нужно именно решение,
  а не подсказка.

**Ревью (C)** — после каждого куска, который разработчик отдал на проверку:
- агент-ревьюер сверяет код с ADR, сквозными правилами и `decisions/*`, гоняет `make test`
  и `make lint`;
- отчёт — список находок с отсылкой к ADR/правилу; **код ревьюер не исправляет**,
  исправление — за разработчиком;
- расхождение кода с ADR — либо ошибка кода, либо повод пересмотреть ADR; второе — только
  с явного согласия разработчика.

**Git:** агенты не коммитят и не пушат; изменения отдаются файлами в рабочую папку,
коммиты делает разработчик.

**Следующий шаг** (Решение А-11 (принято 30.10.2026)): в рамках плана разработки агент может назвать
следующий пункт плана; вне плана — не предлагать «что дальше», разработчик решает сам.

Роль ассистента в объяснениях — инструмент поиска и анализа: находит информацию,
объясняет, даёт варианты. Эти правила специфичны для проекта и не отменяют общий формат
общения (уровень объяснений, уточняющие вопросы там, где выбор действительно за
разработчиком), если сам разработчик явно не попросил иное.
