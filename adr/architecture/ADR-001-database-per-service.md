# ADR-001: Database per Service

## Статус
Принято

## Контекст
Система строится как несколько независимых микросервисов (Users, Orders
и далее). Наиболее простой вариант — одна общая база данных на все
сервисы, с прямыми JOIN между таблицами разных доменов. Это даёт
удобство на старте (один SQL-запрос вместо композиции нескольких), но
создаёт скрытую связанность: сервисы перестают быть независимыми, если
физически делят одну схему БД — изменение таблицы одним сервисом может
незаметно сломать другой.

## Решение
Каждый сервис владеет собственной базой данных, к которой не имеют
прямого доступа другие сервисы. Ни JOIN, ни прямые SQL-запросы через
границу сервиса не допускаются. Обеспечивается на уровне docker-сетей:
база данных сервиса находится в сети, недоступной другим сервисам.

> Уточнено 30.10.2026 (ADR-038): в compose — отдельный контейнер
> PostgreSQL и отдельная сеть на каждую БД (пять контейнеров: у Gateway
> БД нет). Сервис физически не видит чужую базу.

## Альтернативы, которые рассматривались
- **Общая база на все сервисы** — отклонено: размывает границы
  владения данными (bounded context), делает сервисы взаимозависимыми
  через схему БД, а не через явный контракт.
- **Общая база с раздельными схемами (schema-per-service в одной БД)**
  — отклонено: технически изолирует таблицы, но не изолирует сам
  инстанс БД — один сбой/перегрузка влияет на все сервисы одновременно;
  не даёт независимого масштабирования и выбора СУБД под сервис.

## Последствия
**Плюсы:** независимое масштабирование и эволюция схемы каждого
сервиса; авария/перегрузка одной БД не задевает другие сервисы напрямую;
чёткая граница владения данными.

**Минусы:** невозможны прямые JOIN между доменами — агрегация данных из
нескольких сервисов требует либо композиции на уровне API (см. Gateway),
либо денормализации через события; согласованность данных между
сервисами становится eventual, а не strong (см. ADR-005, ADR-006).

**Требует:** сервисы обмениваются данными только через события/команды
(RabbitMQ), не через прямой доступ к чужой БД.
