# ADR-002: Оркестрация вместо хореографии для многошаговых процессов

## Статус
Принято

## Контекст
Некоторые бизнес-процессы (в v1 — единственная сага: оплата заказа) затрагивают
несколько сервисов и требуют согласованных действий с возможностью
отката при сбое на одном из шагов (Saga pattern). Существует два
общепринятых способа реализации саги: хореография (сервисы реагируют на
события друг друга без центрального координатора) и оркестрация (один
явный координатор управляет последовательностью шагов).

## Решение
Многошаговые бизнес-процессы реализуются через оркестрацию. Хореография
для таких процессов не используется, независимо от контекста конкретной
задачи.

## Альтернативы, которые рассматривались
- **Хореография** — отклонено: бизнес-процесс размывается по
  обработчикам разных сервисов, каждый из которых реагирует на события
  предыдущего шага без знания общей картины. Чтобы понять весь сценарий
  целиком (включая порядок компенсаций при сбое), нужно перепрыгивать
  между кодом разных сервисов — это увеличивает когнитивную нагрузку при
  расследовании инцидентов и изменении бизнес-логики.

## Последствия
**Плюсы:** явный, читаемый в одном месте поток управления;
централизованная обработка ошибок и компенсаций; легче добавлять
шаги/изменять порядок без правки нескольких сервисов одновременно.

**Минусы:** сервис-оркестратор становится точкой, знающей о шагах
других сервисов (некоторая связанность в обратную сторону — оркестратор
зависит от контракта команд каждого участника саги).

**Требует:** решения, где физически размещается оркестратор (см.
ADR-003).
