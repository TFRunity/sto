# ADR-003: Оркестратор саги — часть владеющего сервиса, не отдельный сервис

## Статус
Принято

## Контекст
При выборе оркестрации (см. ADR-002) возникает вопрос размещения
оркестратора: как часть кода сервиса, которому принадлежит бизнес-процесс
(например, Orders для саги оплаты заказа), либо как самостоятельный
сервис, координирующий несколько доменов извне.

## Решение
Оркестратор саги — часть кода того сервиса, который владеет
бизнес-процессом (для саги оплаты — `orders`, пакет `internal/saga`).
Отдельный сервис-оркестратор не используется.

> единственная сага — оплата заказа; создание заказа идёт без саги
> (`sequence-create-order`). Механика саги — ADR-030.

## Альтернативы, которые рассматривались
- **Отдельный saga-сервис** — отклонено. Ключевая проблема, вскрывшая
  несостоятельность варианта: неясно, где такой сервис хранит своё
  состояние (`saga_state`). Если у него появляется собственная БД — это
  фактически новый bounded context, не владеющий никакими реальными
  данными, кроме служебного состояния координации. Если он читает/пишет
  в БД Orders напрямую — прямое нарушение Database per Service
  (ADR-001). Дополнительно: лишний сетевой прыжок
  (`Gateway → Orders → Saga-сервис → Inventory`) без архитектурной пользы,
  так как логика саги — это бизнес-логика Orders, распределённая по
  шагам, а не независимая инфраструктурная функция.
- **Готовый движок оркестрации (Temporal)** — см. отдельно ADR-009;
  признан избыточным при текущем масштабе, но остаётся правильной
  альтернативой самописному оркестратору при росте числа/сложности саг.

## Последствия
**Плюсы:** нет неоднозначности владения состоянием саги; минимум
сетевых прыжков; логика бизнес-процесса физически там же, где остальная
логика домена, которому она принадлежит.

**Минусы:** сервис, владеющий сагой, приобретает дополнительную
ответственность и код (пакет `saga/`) сверх обычного CRUD — оправдано
только пока процесс один/несколько, а не десятки (см. ADR-009).
