# ADR-005: Transactional Outbox для публикации событий

## Статус
Принято. Дополнено 30.10.2026 (раздел «Дополнения»; ADR-025, ADR-030).

## Контекст
Сервисы публикуют события в RabbitMQ при изменении своих данных
(например, `UserCreated`). Наивная реализация — записать изменение в БД,
затем отдельным вызовом опубликовать событие в очередь — не атомарна:
сбой между двумя шагами приводит либо к потере события (данные
сохранены, событие не отправлено), либо к публикации события о данных,
которые не были в итоге сохранены (проблема двойной записи, dual write).

## Решение
Событие записывается в специальную таблицу `outbox` внутри той же БД и
**в той же транзакции**, что и основные данные — атомарность
обеспечивается транзакцией PostgreSQL. Отдельный фоновый воркер (общий
код в `chassis/outbox`) вычитывает неопубликованные записи и доставляет
их в RabbitMQ; при сбое воркера или недоступности брокера запись просто
остаётся неопубликованной и будет повторно обработана на следующем
цикле — источник правды остаётся в БД, ничего не теряется.

```sql
CREATE TABLE outbox (
    id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    aggregate_id  uuid NOT NULL,
    event_type    text NOT NULL,
    payload       jsonb NOT NULL,
    created_at    timestamptz NOT NULL DEFAULT now(),
    published     boolean NOT NULL DEFAULT false,
    published_at  timestamptz
);

CREATE INDEX idx_outbox_unpublished ON outbox (created_at) WHERE published = false;
```

Индекс — частичный, по необработанным записям: это самый частый запрос
воркера, а большинство строк со временем становятся `published = true`,
поэтому индексировать весь столбец нецелесообразно.

## Альтернативы, которые рассматривались
- **Прямая публикация в очередь без outbox** — отклонено: не решает
  dual write, риск потери или дублирования событий при сбое между
  записью в БД и публикацией.
- **Change Data Capture (например, Debezium поверх WAL)** — не
  рассматривалось всерьёз для текущего масштаба: добавляет отдельный
  инфраструктурный компонент (Kafka Connect и т.п.), оправданный при
  большом числе сервисов/высокой нагрузке, избыточен здесь.
- **Двухфазный коммит (2PC) между Postgres и RabbitMQ** — отклонено:
  снижает производительность и доступность, RabbitMQ не имеет
  полноценной поддержки 2PC как первоклассной функции.

## Последствия
**Плюсы:** гарантированная at-least-once доставка событий без
распределённых транзакций; события не теряются при сбое воркера или
брокера.

**Минусы:** задержка между записью данных и фактической публикацией
события (до одного цикла воркера, например ~1 секунда); at-least-once,
не exactly-once — получатели должны быть готовы к возможным дублям (см.
ADR-006 в части идемпотентности).

**Требует:** `outbox` есть у каждого сервиса, публикующего события —
общий, переиспользуемый механизм, реализованный один раз в `chassis`.

## Дополнения (30.10.2026, D-01)
- **Без блокировок строк.** Воркер: `SELECT` пачки по частичному индексу →
  публикация → `UPDATE … SET published = true, published_at = now() WHERE
  id = ANY($1)`. `FOR UPDATE SKIP LOCKED` не используется: блокировка
  держалась бы на время сетевого обмена с брокером (против ADR-031).
  Следствие: **второй экземпляр сервиса гарантированно даёт дубли** —
  допустимо только при одном экземпляре (как и в ADR-006).
- **Publisher confirm ждём на каждое сообщение отдельно.** Пометка
  `published = true` только после ack; при nack строка остаётся
  неотправленной до следующего тика.
- **AMQP `MessageId` = `outbox.id`** — для логов и трассировки.
  Идемпотентность получателей держится на бизнес-ключе (`saga_id`,
  ADR-030), а не на `MessageId`. Повтор команды допустим только
  переотправкой той же строки outbox, без новой записи.
- **В `payload` — только идентификаторы** (и технические поля вроде
  количества), без персональных данных: email, имени, телефона.
- **Журнал без чистки.** Опубликованные строки остаются навсегда (объём
  ~50–100 МБ в год при 50 заказах в день). Частичный индекс
  `WHERE published = false` обязателен — без него воркер сканировал бы
  всю историю.

> Решение А-08 (принято 30.10.2026): решение D-01 звучало «в payload только
> идентификаторы», но команда списания обязана нести количества по
> позициям. Правило уточнено: «идентификаторы и технические значения
> (количества, коды результата), без персональных данных».
