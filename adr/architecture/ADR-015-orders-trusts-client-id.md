# ADR-015: Orders не проверяет существование клиента при создании заказа

## Статус
Принято

## Контекст
При создании заказа инженер указывает клиента (`client_id`). Возник
вопрос: должен ли Orders при создании заказа обращаться к Users, чтобы
проверить, что клиент с этим id существует и не удалён (soft delete)?

## Решение
Orders не делает запрос к Users при создании заказа. `client_id`
принимается как есть, из данных, пришедших с UI, без верификации.

## Обоснование
Клиент выбирается инженером **на экране UI**, где список клиентов уже
получен из Users — то есть `client_id` физически не может быть введён
вручную или произвольным значением, он всегда результат выбора из уже
существующих записей на момент отображения списка.

Дополнительно: в системе действует soft delete (общий паттерн
`deleted_at` в доменных таблицах, ADR-033) — физическое удаление пользователя не
предусмотрено. Операция создания заказа должна проходить даже в
краевом случае, когда клиент был удалён между моментом отображения
списка на UI и моментом отправки запроса — отсутствие жёсткой
проверки здесь намеренно, не недосмотр.

Это то же рассуждение, что применено к perimeter trust (ADR-010):
проверка, дублирующая уже данную на другом уровне гарантию
(здесь — сам факт выбора из актуального списка на UI), добавляет
связанность и точку отказа (что если Users временно недоступен в
момент создания заказа?) без реальной защиты от вероятного сценария.

## Альтернативы, которые рассматривались
- **Синхронный HTTP-запрос Orders → Users на существование** —
  отклонено: создаёт временную связанность (temporal coupling),
  которую мы исключили как принцип для взаимодействия между доменными
  сервисами (ADR-002), ради проверки условия, которое почти никогда не
  будет ложным.
- **Локальный кэш активных `client_id` в Orders через подписку на
  события Users (`UserCreated`/`UserDeleted`)** — рассмотрено,
  отклонено как избыточное: решает ту же редкую гонку ценой
  добавления состояния и синхронизации, которую нужно поддерживать.

## Пересмотреть, если
Появится реальный, наблюдаемый сценарий частых заказов с
несуществующими клиентами (не гипотетический) — тогда стоит вернуться
к варианту с подпиской на события, а не к синхронной проверке.
