# ADR-031: Транзакции — в методе репозитория; бизнес-правила — чистые функции; переходы — условный UPDATE

## Статус
Принято

## Контекст
По ADR-013 тестируются только unit-уровни, БД не поднимается. Нужно
решить, кто открывает транзакцию, где живут решения между SQL-запросами
и как защищаться от гонок на переходах состояния.

## Решение
1. **Транзакция открывается внутри метода репозитория**, один метод на
   сценарий; допускается разбиение на приватные подметоды. `defer
   Rollback` сразу после `Begin`; без вложенных транзакций.
2. **Сетевые вызовы — только вне репозитория**, в сервисном слое между
   методами репозитория. Пример справки: метод «взять задачу» → вызов
   Gotenberg → метод «условно перевести в `completed`/`failed`».
3. **Решения внутри транзакции делегируются чистым доменным функциям**
   (без БД и сети), их покрывают табличные unit-тесты. Стартовый перечень
   (дополняется при разработке):
   - Orders: перевод этапа в «выдан» (`paid` + сага `completed`, иначе
     409); допустимость отмены (`requested`/`active`); допустимость
     начала оплаты (`active`); расчёт суммы (по сохранённым ценам,
     `decimal`); шаг саги «состояние + ответ → завершить / откатить /
     проигнорировать»; справка — нужна ли попытка и когда следующая;
   - Inventory: «состояние попытки + команда → действие» (полная таблица
     «состояние × команда» в тестах);
   - Vehicle: нормализация госномера (регистр, пробелы, латиница/
     кириллица) перед проверкой уникальности.
4. **Сквозное правило переходов состояния:** во всех таблицах с
   конечным автоматом (`saga_state`, статус справки, статус заказа при
   отмене и оплате, попытки Inventory) переход — условный `UPDATE …
   WHERE <состояние> = <ожидаемое>` с проверкой числа затронутых строк.
   0 строк — не ошибка, а «другой участник успел раньше».
   **Исключение:** claim (ADR-017) остаётся без защиты от гонки.

> Разбор А-09 (30.10.2026): **принято разработчиком**. Отмена заказа (`sequence-cancel-order`) раньше
> была безусловным `UPDATE … SET status='cancelled'`. По сквозному
> правилу и D-07 она стала условной: `WHERE status IN
> ('requested','active')`, 0 строк → 409. Иначе можно было отменить уже
> оплаченный заказ — и тогда компенсация саги (`WHERE status='paid'`)
> не смогла бы откатить его.

## Альтернативы, которые рассматривались
- **Транзакция в сервисном слое через замыкание** — граница видна там,
  где принимается решение, но лишний интерфейс. Отклонено ради
  очевидности.
- **Транзакция в `context.Context`** — неявная, компилятор не скажет, что
  вызов ушёл мимо транзакции. Отклонено.
- **`SELECT … FOR UPDATE`** для переходов — держит блокировку дольше,
  логика «прочитал → решил → записал» размазана. Отклонено.

## Последствия
**Плюсы:** сервисный слой не знает о транзакциях, мок репозитория
тривиален; бизнес-правила покрыты тестами; гонки на переходах закрыты
средствами БД.

**Минусы:** SQL-оркестрация внутри репозитория тестами не покрывается
(ADR-013 — осознанно); новые сценарии — новые «толстые» методы.
