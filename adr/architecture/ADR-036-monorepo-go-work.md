# ADR-036: Монорепо, отдельный `go.mod` у каждого модуля, связка через `go.work`

## Статус
Принято

## Контекст
Шесть сервисов и общий модуль `chassis`, задуманный как личный
переиспользуемый модуль. Варианты: один `go.mod` на всё; монорепо с
модулями и `go.work`; `chassis` в отдельном репозитории с версиями по
тегам.

## Решение
Монорепо; отдельный `go.mod` у каждого из шести сервисов и у `chassis`;
`go.work` в корне связывает их для локальной разработки.

Раскладка (решение А-10, принято 30.10.2026: конкретные имена каталогов выбраны
здесь, принципы — из ADR-004 и решений P/I):
```
<repo>/
├── go.work
├── Makefile                 # generate / lint / test / build / up / down
├── docker-compose.yml
├── .env.example
├── .golangci.yml
├── api/openapi.yaml         # одна публичная спецификация (ADR-028)
├── deploy/nginx/            # конфиг nginx
├── chassis/                 # go.mod; outbox/, certificate/, rabbit/, httpx/ …
└── <service>/               # gateway, users, orders, vehicle, inventory, services
    ├── go.mod
    ├── Dockerfile           # свой у каждого сервиса (ADR-038)
    ├── cmd/<service>/main.go
    ├── internal/            # по домену (ADR-004)
    ├── migrations/          # goose, go:embed (ADR-024)
    ├── queries/             # SQL для sqlc
    └── sqlc.yaml
```

## Альтернативы, которые рассматривались
- **Один `go.mod` на всё** — `chassis` перестаёт быть модулем; у всех
  сервисов общий список зависимостей. Отклонено.
- **`chassis` в отдельном репозитории сейчас** — каждая правка: коммит,
  тег, обновление версии в шести сервисах, пока `chassis` активно
  меняется. Отклонено; переход позже — почти механический.

## Последствия
**Плюсы:** правки `chassis` сразу видны во всех сервисах; у каждого
сервиса свои зависимости; `chassis` готов к выносу.

**Минусы:** Docker-образы и CI собираются из корня репозитория (иначе
`chassis` не попадёт в контекст сборки); нужно понимать, где действует
`go.work` (локально, в CI, в Docker).
