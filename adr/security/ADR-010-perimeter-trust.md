# ADR-010: Perimeter trust вместо Zero Trust между сервисами

## Статус
Принято. Дополнено ADR-019 (проверка роли в Gateway) и ADR-037
(allowlist заголовков на проксировании).

## Контекст
API Gateway проверяет JWT-токен клиента на входе. Открыт вопрос: должны
ли Users-service и Orders-service повторно проверять подлинность запроса
внутри docker-сети, или полагаться на то, что любой запрос, дошедший до
них, уже прошёл проверку на Gateway.

## Решение
Выбрана модель perimeter trust: проверка токена происходит только на
уровне API Gateway. Users-service и Orders-service не проверяют
повторно подлинность запроса.

**Обязательное условие, при котором решение остаётся безопасным:**
`users-service` и `orders-service` не публикуют порты наружу в
`docker-compose.yml` (секция `ports:` есть только у nginx и Gateway).
Perimeter trust валиден исключительно пока сеть физически герметична —
это явно проверяемый инвариант конфигурации, а не невидимое допущение.

## Альтернативы, которые рассматривались
- **Zero Trust между сервисами** (каждый сервис самостоятельно проверяет
  токен/подпись запроса) — отклонено для текущего масштаба. В индустрии
  Zero Trust между сервисами реализуется практически всегда не вручную в
  коде каждого сервиса, а через отдельный инфраструктурный слой (service
  mesh — Istio, Linkerd, Kuma), берущий на себя mTLS и авторизацию
  прозрачно для кода приложения; "ручной" Zero Trust без mesh — редкая
  практика сама по себе. Даже среди крупных организаций зрелость таких
  программ низкая (по прогнозам, лишь малая часть крупных предприятий
  достигнет зрелой, измеримой программы Zero Trust к 2026 году). Для
  проекта такого масштаба внедрение вручную означало бы операционную
  сложность энтерпрайз-уровня без соответствующей инфраструктуры (mesh),
  которая обычно её компенсирует. Дополнительный фактор — накопительная
  задержка от проверки на каждом сетевом хопе в цепочке вызовов.

## Последствия
**Плюсы:** простота — токен валидируется в одном месте; отсутствие
дублирования кода проверки в каждом сервисе; отсутствие накопительной
задержки на межсервисные вызовы.

**Минусы:** вся защита HTTP-уровня зависит от одного допущения
(герметичность сети); при его нарушении (случайная публикация порта)
защиты не остаётся ни на одном уровне; модель не защищает
messaging-путь (RabbitMQ-обмен между Orders и Users) — это отдельный
вопрос (см. ADR-012).

**Пересмотреть при:** переходе на Kubernetes/реальный production-контур
с внешними пользователями, и/или росте числа сервисов и команд —
тогда стоит рассмотреть service mesh, а не ручную реализацию Zero Trust
в коде каждого сервиса.
