# ADR-011: Secrets management через .env, без Vault/Docker Secrets

## Статус
Принято

## Контекст
Пароли БД, credentials RabbitMQ и другие секреты нельзя хранить прямо в
`docker-compose.yml`: этот файл коммитится в git, и любое значение,
однажды туда попавшее, остаётся в истории репозитория даже после
удаления. Нужен способ хранения, отдельный от файла, коммитящегося в
систему контроля версий — как локально, так и в CI/CD.

## Решение
**Локальная разработка:** секреты выносятся в `.env`-файл, добавленный в
`.gitignore`; `docker-compose.yml` ссылается на переменные (`${POSTGRES_
PASSWORD}`), не хранит значения. В git коммитится `.env.example` —
пустой шаблон для других разработчиков.

**CI/CD:** секреты хранятся в защищённом хранилище самой платформы
(например, GitHub Actions → Settings → Secrets), подставляются в
пайплайн только во время выполнения — например, генерацией `.env` на
лету на CI-раннере перед `docker compose up`, без сохранения в
репозитории. `.env` для локальной разработки и Secrets CI/CD-платформы —
два раздельных места хранения одних и тех же по смыслу значений, не
связанных друг с другом напрямую.

## Альтернативы, которые рассматривались
- **Секреты прямо в `docker-compose.yml`** — отклонено: попадают в
  историю git безвозвратно.
- **Docker Secrets** — рассмотрено, отложено: даёт дополнительную защиту
  (секреты монтируются как файлы в защищённую временную ФС контейнера, а
  не видны как переменные окружения процесса через `docker inspect`/
  `/proc/<pid>/environ`), но эта угроза (доступ к самому хосту/
  контейнеру) не входит в модель угроз данного масштаба.
- **HashiCorp Vault / внешнее хранилище секретов** — отклонено:
  динамическая выдача секретов, ротация, аудит доступа — оправдано на
  энтерпрайз-масштабе, для pet-project на Docker Compose избыточно. То
  же рассуждение, что применено к выбору perimeter trust (ADR-010).

## Последствия
**Плюсы:** секреты не попадают в git ни при каких обстоятельствах при
соблюдении дисциплины `.gitignore`; разделение между локальной средой и
CI/CD не создаёт единой точки отказа/утечки.

**Минусы:** `.env` физически лежит на диске разработчика в открытом виде
— защищает от утечки через git, но не от компрометации самой машины
разработчика; нет встроенной ротации или аудита доступа к секретам.

**Требует:** обязательного `.gitignore` для `.env` с самого первого
коммита проекта — не постфактум.
