# ADR-023: Аутентификация — JWT HS256 на 7 дней, пароли — bcrypt

## Статус
Принято

## Контекст
Users выпускает токен (`POST /login`, `/register`), Gateway проверяет его
(ADR-010) и роль (ADR-019). Нужно выбрать алгоритм подписи, срок жизни,
наличие refresh и способ хранения паролей.

## Решение
**Токен:** `golang-jwt/jwt/v5`, HS256, один долгоживущий токен на 7 дней,
без refresh.
- Секрет — 32+ случайных байт в `.env` у Users и Gateway (ADR-011).
- При разборе — `WithValidMethods` (только HS256) и обязательный `exp`.
- `sub` = `user_id`, роль — отдельный claim.
- Срок жизни — переменная окружения Users.

**Пароль:** bcrypt (`golang.org/x/crypto/bcrypt`), cost 12.
- Длина пароля ≤ 72 байт проверяется при регистрации (лимит bcrypt).
- Если пользователь не найден — сравнение с фиктивным хешем: одинаковое
  время ответа, защита от перебора логинов.

## Альтернативы, которые рассматривались
- **RS256 / EdDSA** — Gateway хранил бы только публичный ключ. Отклонено:
  при perimeter trust Gateway и так точка доверия, асимметричная подпись
  почти ничего не даёт, а ключи в `.env` сложнее.
- **Короткий access + refresh-токен** — отклонено ради простоты.
- **argon2id** — стойче к GPU, но bcrypt проще и достаточен для масштаба.

## Последствия
**Плюсы:** минимум механики; одно место проверки токена.

**Минусы:**
- Смена роли и удаление пользователя действуют только после перелогина
  или истечения токена (до 7 дней) — следствие ADR-019.
- Logout только клиентский: на сервере токен валиден до `exp`.
- На RN токен хранится в защищённом хранилище (Keychain/Keystore), не в
  `AsyncStorage`.
