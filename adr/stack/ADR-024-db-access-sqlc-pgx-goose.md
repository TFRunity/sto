# ADR-024: Доступ к БД — sqlc + pgx/pgxpool; миграции — goose, только вперёд

## Статус
Принято

## Контекст
Проект насыщен SQL-спецификой PostgreSQL: частичные индексы, `ON
CONFLICT`, условные `UPDATE … WHERE`, `jsonb`, `numeric`. SQL —
первоисточник, ORM/DSL не нужен. Outbox должен писаться в одной
транзакции с доменными данными (ADR-005). Каждому сервису — свой набор
миграций (ADR-001).

## Решение
**Доступ к данным:** sqlc (генерация под `pgx/v5`) + `pgxpool`.
- Схема для sqlc читается из миграций goose.
- Интерфейс `DBTX` + `WithTx`: репозиторий и `chassis/outbox` работают и
  с пулом, и с транзакцией — outbox в той же транзакции, что и данные.
- Overrides типов в `sqlc.yaml`: `uuid` → `google/uuid`, `numeric` →
  `decimal.Decimal` / `decimal.NullDecimal` (ADR-026).
- Динамические фильтры — через `sqlc.narg` или отдельные запросы.
- Сгенерированные модели остаются внутри репозитория и маппятся в
  доменные типы.
- Сгенерированный код коммитится; CI проверяет отсутствие диффа после
  `sqlc generate` (ADR-014).

**Миграции:** goose, встроены через `go:embed`, применяются при старте
сервиса; **только forward** — down-миграции не пишутся.
- Ошибка схемы исправляется новой up-миграцией.
- Упавшая миграция откатывается транзакцией goose (нет состояния dirty).
- Настоящий откат — из бэкапа (`pg_dump` перед применением миграций).

## Альтернативы, которые рассматривались
- **pgx + SQL руками** — ручной сканинг строк, нет проверки запросов до
  запуска. Отклонено в пользу генерации.
- **sqlx** — меньше сканинга, но без проверки SQL. Отклонено.
- **GORM** — скрывает SQL, плохо вяжется с SQL-ориентированным стилем.
- **golang-migrate, atlas** — goose выбран за транзакцию на миграцию и
  встраивание через `go:embed`.

## Последствия
**Плюсы:** ошибки в SQL ловятся до запуска; минимум шаблонного кода;
SQL остаётся читаемым первоисточником.

**Минусы:** три слоя типов (OpenAPI DTO, sqlc-модели, домен) с маппингом
между ними; запуск миграций при старте допустим только при одном
экземпляре сервиса (ADR-006).
