# ADR-025: RabbitMQ — `amqp091-go`, топология в definitions, confirms, ручной ack

## Статус
Принято

## Контекст
RabbitMQ используется только между Go-сервисами: команды саги оплаты
Orders → Inventory и ответы Inventory → Orders (ADR-002, ADR-030).
Официальный клиент `github.com/rabbitmq/amqp091-go` низкоуровневый:
реконнект, топологию и обёртки нужно писать самим (место — `chassis`).
Outbox (ADR-005) имеет смысл только с подтверждениями публикации.

## Решение
| Часть | Решение |
| --- | --- |
| Соединения и каналы | Отдельные соединения для публикации и потребления; канал на роль/горутину (канал не потокобезопасен для публикации) |
| Топология | Direct exchange для команд и ответов; quorum-очереди. Вся топология (exchange, очереди, binding, лимит доставок, пользователь) — в definitions, загружаемых брокером при старте. Сервисы делают только **пассивную** проверку своих очередей и падают при их отсутствии (compose перезапустит, ADR-038) |
| Публикация | Publisher confirms; outbox помечает `published = true` только по ack, confirm ждём на каждое сообщение (ADR-005). At-least-once — получатели переживают дубли |
| Потребление | Ручной ack строго после коммита транзакции; prefetch 1 для обоих консьюмеров |
| Ошибки обработки | Временная ошибка: nack с requeue после паузы 0,2 с. После 5 доставок сервис логирует сообщение (error) и делает ack — выбрасывает. Счётчик — заголовок `x-delivery-count` quorum-очереди; на брокере страховочный `x-delivery-limit` выше (10) |
| Реконнект | Цикл-супервизор в `chassis`: подключение → канал → Qos → Consume → обработка до обрыва → пауза с нарастанием (0,5 с … 30 с) → заново; выход по `ctx.Done()`. `NotifyClose` с буферизованным каналом |
| Креды | Пользователь описан в definitions; definitions — встроенным текстом в compose с подстановкой из `.env` (`RABBITMQ_DEFAULT_USER` при импорте definitions игнорируется — ADR-012) |
| Образ | `rabbitmq:4.3-management`, минорная версия зафиксирована; Management UI (`15672`) наружу не публикуется (ADR-012) |

**Имена (Решение А-07 (принято 30.10.2026)):**
- exchange `saga_commands` → очередь `inventory.saga_commands`;
  сообщения `DeductStock {saga_id, order_id, items[{item_id, qty}]}`,
  `CancelStock {saga_id, order_id}`;
- exchange `saga_replies` → очередь `orders.saga_replies`;
  сообщения `StockDeducted {saga_id, order_id}`,
  `StockRejected {saga_id, order_id}`.

Решения D-02/P-06 называли только `saga_commands` и `orders.saga_replies`;
имена сообщений и очереди Inventory выбраны здесь, их можно переименовать
без последствий для архитектуры.

## Альтернативы, которые рассматривались
- **Сервисы сами объявляют топологию** — отклонено: топология размазана
  по коду, расхождения между сервисами ловятся только в рантайме.
- **Dead-letter exchange вместо «выбросить после 5 доставок»** —
  отклонено ради простоты; потеря ответа саги покрывается дедлайном
  (ADR-030).
- **Шаблон definitions + генерация файла перед запуском** — отклонено:
  лишний шаг, забытая генерация = старый пароль (ADR-038).

## Последствия
**Плюсы:** порядок шагов саги сохраняется (prefetch 1); падение сервиса
не теряет сообщения; вся топология видна в одном месте.

**Минусы:** ack старых доставок через новый канал невозможен — после
реконнекта сообщение придёт повторно (норма при at-least-once); JSON
definitions живёт внутри compose-файла.
