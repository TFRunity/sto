# ADR-029: Загрузка и хранение фото — подготовка на клиенте, том Docker, отдача через сервис

## Статус
Принято

## Контекст
Фото ТС: обложка (`cover_photo_url`, клиент в вебе) и фотофиксация
(инженер в RN). Снимки с телефона большие, с EXIF-поворотом и GPS.
Нужно решить, где уменьшать фото, где хранить файлы и как ограничить
загрузку.

## Решение
**Подготовка (P-14):** на клиенте — уменьшение, применение EXIF-поворота
к пикселям, JPEG, итог **≤ 3 МБ**. В вебе — через canvas, в RN —
проверить, что пикер применяет поворот к пикселям.

**Проверка на сервере (S-11, S-12):**
- `http.MaxBytesReader` ~3,5 МБ на весь запрос; `413` через
  `errors.As(*http.MaxBytesError)` — в формате ошибок ADR-032.
- `ParseMultipartForm` с небольшим `maxMemory`.
- `DetectContentType`; белый список JPEG/PNG; `DecodeConfig` с лимитом
  размеров до `Decode` (защита от «пиксельной бомбы»); HEIC не
  принимается.
- Перекодирование в JPEG **без ресайза** — стирает метаданные, включая
  GPS.
- Имя файла — свой UUID, клиентский `filename` не используется.

**Хранение:** том Docker, монтируется только в Vehicle; в БД — только
ключ файла. Порядок записи: файл → строка → при ошибке удалить файл.
Отдача — через сам сервис (`http.ServeFile`), путь nginx → Gateway →
Vehicle; права проверяет общий middleware. Бэкап тома — отдельно от
`pg_dump`.

**Лимиты по цепочке (I-06):** клиент ≤ 3 МБ → сервис ~3,5 МБ → nginx
`client_max_body_size 4m` (страховка: обычный `413` отдаёт сервис в
нашем формате, а не nginx в своём HTML).

## Альтернативы, которые рассматривались
- **Ресайз на сервере** (`x/image/draw`, `imaging`) — больше трафика и
  работы на сервере. Отклонено.
- **Объектное хранилище (MinIO)** — отдельный компонент. Отклонено.
- **Раздача фото напрямую nginx** — обходит проверку прав. Отклонено.

## Последствия
**Плюсы:** малый трафик; метаданные стёрты; права на фото проверяются.

**Минусы:** логика подготовки дублируется в вебе и RN; том нужно
бэкапить отдельно.
