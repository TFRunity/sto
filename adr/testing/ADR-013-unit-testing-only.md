# ADR-013: Только unit-тестирование на данном этапе

## Статус
Принято. Уточнено 30.10.2026 (P-09): моки — ручные, без `testify/mock`.

## Контекст
Возможные уровни тестирования для этой архитектуры: unit-тесты (чистые
функции, сервисный слой с моками), интеграционные тесты repository
против реальной БД, контрактные тесты между Orders и Users, полные
E2E-сценарии саги. Нужно решить, с какого уровня начинать и в каком
объёме.

## Решение
На данном этапе в проекте реализуется только unit-тестирование.
Интеграционные, контрактные и E2E-тесты не реализуются.

**Библиотеки:** встроенный пакет `testing` как основа; `testify`
(`github.com/stretchr/testify`) — только ассерты (`assert`/`require`).

**Моки — ручные** (уточнено 30.10.2026, P-09): fake-структуры с
полями-функциями в `*_test.go`. `testify/mock` и генераторы моков
(`mockery`, `moq`) не используются: поведение задаётся в каждом тесте
своё, проверку делает компилятор, а не строковые имена методов;
интерфейсы держатся маленькими (на стороне потребителя).

**Стиль:** table-driven tests — тестовые случаи, включая граничные,
перечисляются как данные в срезе структур, не как отдельные функции на
каждый случай (идиоматичный для Go подход).

**Что покрывается:** чистые функции с бизнес-правилами (без внешних
зависимостей); сервисный слой, зависящий от репозитория через интерфейс
(зависимость подменяется моком, реальная БД не поднимается).
Решения внутри транзакций выносятся в чистые доменные функции, чтобы
они попадали под unit-тесты (ADR-031).

## Альтернативы, которые рассматривались
- **Интеграционные тесты repository с реальной тестовой БД** (например,
  через `testcontainers-go` — поднимает настоящий Postgres в Docker во
  время выполнения тестов, без постоянной "тестовой БД", за которой
  нужно следить руками) — жизнеспособный подход, отложен как следующая
  ступень, не первый шаг.
- **Контрактные тесты между Orders и Users** (проверка, что оба сервиса
  одинаково понимают формат событий/команд) — отложено, актуально
  тем сильнее, чем больше сервисов и команд участвует в проекте.
- **E2E-тесты полного сценария саги** — отложено как наиболее тяжёлая и
  медленная ступень тестирования.

## Последствия
**Плюсы:** быстрая, дешёвая база тестов без внешней инфраструктуры;
покрывает бизнес-логику и её граничные случаи.

**Минусы:** unit-тесты с моками не проверяют, что реальные SQL-запросы
корректно работают против реальной БД, и не проверяют совместимость
форматов сообщений между сервисами — эти классы ошибок остаются
непокрытыми на данном этапе.

**Пересмотреть при:** появлении необходимости в более глубокой
уверенности, чем даёт unit-уровень — в первую очередь при росте
сложности SQL-запросов или числа сервисов, обменивающихся событиями.
