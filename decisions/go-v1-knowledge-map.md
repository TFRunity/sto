## 1. Контекст v1 (минимум для старта в чужом контексте)

**Состав v1:** шесть Go-приложений — `gateway`, `users`, `orders` (+ оркестратор саги оплаты), `vehicle`, `inventory`, `services`; общий модуль `chassis` (`chassis/outbox`, `chassis/certificate`). Клиенты: веб (клиент, директор) и React Native (инженер) — не Go.
**Ушло в v2 (не реализовывать, не проектировать):** Chat (WebSocket), Reports, «Статистика по сотрудникам».

**Инфраструктура:** Docker Compose; nginx → Gateway; PostgreSQL по базе на сервис (ADR-001); RabbitMQ только между Go-сервисами.

**Ключевые архитектурные факты, определяющие объём Go-знаний:**

| Факт | Источник | Следствие для кода |
|---|---|---|
| Database per Service, JOIN между сервисами нет, ссылки — `uuid` без FK | ADR-001, ADR-007 | Агрегация только в Gateway (API composition) или событиями |
| Сага оплаты — единственная, самописный оркестратор в Orders, `saga_state` | ADR-002/003/006, `sequence-pay-order` | State machine, tx, консьюмер ответов |
| Transactional outbox, воркер в `chassis/outbox`, at-least-once | ADR-005 | Фоновый воркер, транзакции, publisher confirms |
| Perimeter trust: JWT проверяет только Gateway; роль — тоже в Gateway | ADR-010, ADR-019 | Auth/role middleware, reverse proxy, герметичная docker-сеть |
| Секреты через `.env`, RabbitMQ — смена дефолтных кредов, без TLS/ACL | ADR-011, ADR-012 | Конфиг из env, никаких секретов в коде |
| Код по домену, плоский `internal/` для одного домена | ADR-004 | Раскладка пакетов, без `handler/service/repository` |
| Только unit-тесты: `testing` + `testify`, table-driven, репозиторий за интерфейсом | ADR-013 | Интерфейсы на стороне потребителя, моки |
| CI (план): `go test`, `golangci-lint`, `go build` | ADR-014 | Линтер-конфиг, чистый `go vet` |
| Orders не проверяет `client_id`; claim без защиты от гонки; без retry оплаты | ADR-015/016/017 | Намеренно простой код — не «улучшать» |
| Claim = `UPDATE orders` + `INSERT order_engineers ON CONFLICT DO NOTHING` в одной tx | ADR-020 | Транзакции в репозитории |
| Статус заказа и этап работ — две независимые оси, «выдан» только при `paid` (409) | ADR-021 | Доменные правила, маппинг ошибок в HTTP |
| Справка: PDF из снапшота, `active → completed/failed`, retry-воркер ≤3 | `sequence-certificate` | Генерация PDF, фоновый воркер |

**Правило вынесения кода (AGENTS.md):** дубль в файле → приватная функция; между файлами модуля → `utils` сервиса; между модулями сервиса → сразу `chassis`.

## 2. Что зафиксировано, а что остаётся выбором

**Зафиксировано ADR:** Go; PostgreSQL; RabbitMQ; Docker Compose; nginx; `testing` + `testify`; table-driven; `golangci-lint` в CI; `.env`; без Temporal, CQRS, Vault, testcontainers, service mesh.

**Не зафиксировано (ВЫБОР):** HTTP-роутер; драйвер/слой доступа к БД; инструмент миграций; алгоритм и срок жизни JWT; хеш пароля; RabbitMQ-клиент (практически безальтернативно — официальный); PDF-библиотека; тип денег; хранилище фото; формат ошибок API; конфиг-библиотека; монорепо vs отдельный репозиторий `chassis`. Сводный список — раздел 10.

## 3. Блок L — язык (от синтаксиса)

### L-01 🔴 Модули, пакеты, видимость
`go mod init/tidy`, структура модуля, `internal/` как барьер импорта, экспорт по регистру первой буквы, циклические импорты запрещены. Для `chassis` — отдельный модуль: версионирование, `replace` / `go.work` на время локальной разработки.
**Задачи:** (1) разложить `users` как плоский `internal/` (ADR-004) и объяснить, почему `gateway` не может импортировать `internal/` из `orders`. (2) Подключить локальный `chassis` к сервису двумя способами (`replace` и `go.work`) и сравнить поведение при `go build` в CI.

### L-02 🔴 Типы, структуры, методы
Структуры, композитные литералы, zero value как рабочее состояние, методы, value vs pointer receiver (когда какой, смешивание receiver'ов в одном типе — запах), встраивание (embedding) как композиция, не наследование. Определённые типы (`type Status string`) против алиасов.
**Задачи:** (1) смоделировать `Роль`, `СтатусЗаказа`, `ЭтапРабот`, `СтатусСправки` как определённые типы с константами; решить, где живёт валидация значения. (2) Объяснить, почему `Order` с `sync.Mutex` внутри нельзя копировать.

### L-03 🔴 Константы и перечисления
`const`, `iota`, типизированные константы; в проекте enum'ы строковые (хранятся `text`), поэтому `iota` почти не нужен — но понимать его необходимо.
**Задача:** сравнить `string`-enum и `int`-enum с `iota` по критериям: сериализация в JSON, запись в Postgres, читаемость в БД, защита от невалидного значения.

### L-04 🔴 Массивы, срезы, мапы
Backing array, `len/cap`, `append` и алиасинг, `copy`, nil-срез vs пустой (в JSON: `null` против `[]` — частый баг контракта), мапа не потокобезопасна, запись в nil-мапу — panic, порядок обхода мапы случаен.
**Задачи:** (1) воспроизвести ситуацию, когда два среза делят массив и `append` портит чужие данные. (2) Сделать так, чтобы пустой список заявок всегда сериализовался как `[]`.

### L-05 🔴 Интерфейсы
Неявная реализация; интерфейс объявляется **на стороне потребителя** и маленький (ключ к ADR-013: сервисный слой зависит от `Repository`-интерфейса, мок подставляется в тесте); «принимай интерфейсы, возвращай структуры»; ловушка nil-интерфейса (интерфейс с nil-указателем ≠ nil); `any`, type assertion, type switch.
**Задачи:** (1) определить интерфейс репозитория для Orders ровно под методы, нужные сервисному слою оплаты. (2) Воспроизвести ловушку «функция вернула nil-указатель в `error`, `err != nil` истинно».

### L-06 🔴 Ошибки
`error` как значение, `fmt.Errorf("…: %w", err)`, `errors.Is/As`, sentinel-ошибки, собственные типы ошибок. В проекте критично: доменная ошибка → HTTP-код (ADR-021: «выдан без paid» → 409; номер ТС занят → 409; не найдено → 404).
**Задачи:** (1) придумать схему доменных ошибок Orders и единое место маппинга в HTTP. (2) Объяснить, когда wrapping раскрывает детали реализации наружу и как этого избежать на границе API.

### L-07 🔴 defer, panic, recover
Порядок `defer` (LIFO), аргументы вычисляются в момент `defer`, `defer` в цикле, `defer tx.Rollback()` после `Begin`, `defer rows.Close()`. `panic` — не механизм ошибок; `recover` — только в middleware/воркере верхнего уровня.
**Задачи:** (1) объяснить, почему `defer tx.Rollback()` безопасен после успешного `Commit`. (2) Написать (самостоятельно) middleware, превращающий panic в 500 и не роняющий процесс.

### L-08 🔴 Конкурентность
Горутины, каналы (буферизованные/нет, закрытие, `range`), `select`, `sync.WaitGroup/Mutex/Once`, `context.Context` (отмена, дедлайн, передача первым аргументом, не хранить в структуре), `errgroup` (`golang.org/x/sync`), утечки горутин, гонки данных, `go test -race`. Нужно для: параллельных запросов в дашборде Gateway, воркеров outbox/retry справки, консьюмера RabbitMQ, graceful shutdown.
**Задачи:** (1) описать, как `GET /dashboard` делает два параллельных запроса и что отдаёт, если один из сервисов упал или завис. (2) Найти и устранить утечку горутины в воркере с `time.After` внутри цикла.

### L-09 🔴 Время
`time.Time`, `Duration`, `Ticker` vs `Timer`, `time.After` в цикле (утечка до срабатывания), часовые пояса и `timestamptz`, сериализация в RFC3339; «желаемая дата» заявки — `date`, а не `timestamp`.
**Задача:** выбрать представление «желаемой даты» на трёх уровнях (Postgres, Go, JSON) без потери смысла при смене часового пояса.

### L-10 🔴 JSON
`encoding/json`: теги, `omitempty` (и его ловушка с нулевыми значениями), `json.RawMessage` (поле `payload jsonb` в outbox и `снапшот` справки), кастомные `MarshalJSON`, строгость к неизвестным полям (`DisallowUnknownFields`), ограничение размера тела.
**Задачи:** (1) хранить `payload` outbox как `RawMessage` и объяснить, зачем не `map[string]any`. (2) Решить, как валидировать вход, не доверяя клиенту поля `owner_id` (по `sequence-add-vehicle` оно берётся из токена).

### L-11 🔴 Тестирование
`testing`, `go test ./...`, table-driven tests, `t.Run`, `t.Helper`, `t.Cleanup`, `testify` (`assert`/`require`/`mock`), покрытие `-cover`, `-race`. Что тестируется по ADR-013: чистые бизнес-правила и сервисный слой на моках; БД и RabbitMQ не поднимаются.
**Задачи:** (1) табличный тест правила «`выдан` только при `paid`» с граничными случаями. (2) Тест шага саги: дублирующийся или устаревший ответ отбрасывается по сравнению `current_step`.

### L-12 🔴 Инструменты языка
`go fmt/vet/build/test/mod`, `golangci-lint` (конфиг `.golangci.yml`), `gopls`; `go vet` как минимальный барьер.
**Задача:** собрать минимальный набор линтеров под проект и обосновать каждый (что ловит и чем мешает).

### L-13 🔴 Ресурсы и выход: graceful shutdown
`os/signal.NotifyContext`, `http.Server.Shutdown(ctx)`, остановка воркеров и закрытие канала/соединения RabbitMQ, закрытие пула БД; порядок остановки.
**Задача:** описать порядок остановки Orders (HTTP-сервер, консьюмер ответов саги, outbox-воркер, пул БД) и что произойдёт при SIGKILL посреди публикации.

### L-14 🟡 Дженерики
Параметры типа, ограничения. В v1 понадобятся редко (утилиты в `chassis`); избегать, пока нет реального дублирования (правило вынесения кода).

### L-15 🟡 `go:embed`
Встраивание файлов в бинарь: шрифт для PDF (кириллица), шаблоны, SQL-миграции.

### L-16 🟡 Версии Go и новые возможности
Актуально на 21.10.2026: поддерживаются Go 1.27 и 1.26 (1.27.3 — последний патч на 19.10.2026). Важное, доступное с 1.21–1.23: `log/slog`, `min/max/clear`, расширенные шаблоны `http.ServeMux` (метод и `{id}` в паттерне), per-iteration loop variable, `range` по int. Для старта брать актуальную стабильную.

### L-17 ⚪ Не нужно
`reflect` (кроме понимания тегов), `unsafe`, `cgo`, plugin'ы, assembly, build tags.

## 5. Блок P — библиотеки и фреймворки

Формат: назначение · статус · варианты · плюсы/минусы выбранного по умолчанию.

### P-01 🔴 HTTP-роутер / фреймворк — `ВЫБОР`
Варианты: **stdlib `net/http` + `ServeMux` (Go 1.22+)**, `chi`, `Gin`, `Echo`.
- stdlib: плюсы — нет зависимостей, идиоматика, максимум понимания языка (цель проекта — обучение), `ReverseProxy` и так оттуда; минусы — нет группировки маршрутов с middleware «из коробки», биндинг/валидацию писать вручную.
- chi: плюсы — тонкая обёртка над `net/http` (совместимые `http.Handler`), группы маршрутов и middleware; минусы — внешняя зависимость.
- Gin: плюсы — биндинг/валидация/группы из коробки, много материалов; минусы — свой `gin.Context` вместо `http.Handler`, тяжелее переносить middleware, меньше учит стандартной модели.
По умолчанию: один выбор на весь проект. Для Gateway критична совместимость с `http.Handler` (ReverseProxy, middleware) — это аргумент в пользу stdlib/chi.

### P-02 🔴 JWT — `golang-jwt/jwt/v5`
Users выпускает токен (`POST /login`, `/register`), Gateway проверяет. Claims минимум: `user_id`, `role` (ADR-019), `exp`.
`ВЫБОР`: HS256 (общий секрет в `.env` у Users и Gateway; проще, но секрет подписи есть у проверяющего) против RS256/EdDSA (Gateway хранит только публичный ключ; сложнее ключи в `.env`). **Обязательно:** жёстко указывать допустимый алгоритм при разборе токена; проверять `exp`. Следствие ADR-019: смена роли действует только после перевыпуска токена — срок жизни токена определяет, как долго «старая роль» работает.
**Задача:** выбрать срок жизни и обосновать относительно ADR-019 (ручной `UPDATE` роли) и отсутствия refresh-механизма в документах.

### P-03 🔴 Хеш пароля — `golang.org/x/crypto/bcrypt` (альтернатива `argon2id`)
Плюсы bcrypt: простое API, достаточно для масштаба; минус: лимит 72 байта входа, меньше стойкости к GPU, чем argon2id. Нужны: хеширование при регистрации, сравнение при входе, одинаковая реакция на «нет пользователя» и «неверный пароль».

### P-04 🔴 PostgreSQL — драйвер и доступ к данным — `ВЫБОР`
По умолчанию: **`jackc/pgx/v5` + `pgxpool`, SQL руками**. Основание: проект насыщен SQL-спецификой (частичный индекс `WHERE published=false`, `ON CONFLICT DO NOTHING`, атомарный `UPDATE … WHERE quantity …`, `jsonb`, `gen_random_uuid()`, `FOR UPDATE SKIP LOCKED` для воркера outbox), а SQL — единственное, что допустимо получать готовым.
- Плюсы: полный контроль над SQL, нативная поддержка `jsonb`/`uuid`/`timestamptz`/`numeric`, пул, батчи.
- Минусы: ручной сканинг строк и много шаблонного кода; нет проверки SQL при компиляции.
- Альтернативы: `database/sql` + `pgx/stdlib` (переносимо, но беднее), `sqlx` (меньше сканинга), `sqlc` (генерация кода из SQL: безопасно и компактно, но прячет механику, что хуже для обучения), `GORM` ⚪ (скрывает SQL, плохо вяжется со стилем ADR).
**Ключевая проектная деталь:** outbox-вставка должна идти **в той же транзакции**, что и доменные данные → репозиторий и `chassis/outbox` принимают общий интерфейс «исполнитель запросов» (и `Pool`, и `Tx` его реализуют), а не конкретный тип.
**Задачи:** (1) спроектировать этот интерфейс минимальным. (2) Решить, где в `claim` открывается и закрывается транзакция (в репозитории или в сервисном слое) и как это тестировать на моках (ADR-013).

### P-05 🔴 Миграции — `ВЫБОР`
Варианты: `golang-migrate/migrate`, `pressly/goose`, `atlas`. Требование: по набору миграций **на каждый сервис** (ADR-001); запуск при старте или отдельным one-shot-контейнером в compose; встраивание через `go:embed`. Плюсы goose/migrate: SQL-файлы up/down, зрелые; минус: down-миграции часто фикция.

### P-06 🔴 RabbitMQ — `github.com/rabbitmq/amqp091-go` (официальный клиент)
Что необходимо знать про брокер и клиент: connection vs channel (**канал не потокобезопасен** — отдельный на горутину/роль), exchange/queue/binding, durable queues и persistent messages, **publisher confirms** (без них outbox теряет смысл: пометка `published=true` только после подтверждения), consumer с ручным `ack/nack` и `prefetch (QoS)`, **клиент не переподключается сам** (обработка `NotifyClose`, реконнект), at-least-once → дубли возможны. Очереди из документов: `saga_commands`, `orders.saga_replies`.
- Плюсы: официальная поддержка, тонкий слой над протоколом; минусы: низкоуровневый — реконнект, топологию, обёртки писать самому (место для них — `chassis`).
- ⚠ Замечание из ADR-006: идемпотентность обработки команды «списать» в Inventory отложена, но при at-least-once дубль команды дважды спишет остаток. ADR-006 сам помечает это шагом «с дорогим побочным эффектом» для точечного пересмотра — решение надо принять до реализации консьюмера Inventory.
**Задачи:** (1) описать, какие сбои возможны между «outbox записан» и «ack получен», и что произойдёт в каждом. (2) Описать реконнект консьюмера, не теряя и не дублируя обработку сверх допустимого.

### P-07 🔴 UUID — `github.com/google/uuid`
Либо генерировать в БД (`gen_random_uuid()` по ADR-005), либо в Go; определить единообразно. Интеграция с `pgx` (тип `uuid`).

### P-08 🔴 Деньги — `ВЫБОР`
`Заказ.рассчитатьСумму(): decimal`, цены в `Товар`/`Услуга` — `decimal`. Варианты: `shopspring/decimal` (+ адаптер к `numeric` в pgx) против целых минорных единиц (`int64` копейки). Целые: проще и быстрее, но конвертация на границах; `decimal`: ближе к модели, но зависимость и адаптер. **Никогда `float64`.**
**Задача:** выбрать тип и показать сквозной путь значения: Postgres `numeric` → Go → JSON → клиент.

### P-09 🔴 Тестирование — `github.com/stretchr/testify` (ADR-013)
`assert`, `require`, `mock`. Плюсы: де-факто стандарт, меньше шаблона; минусы: `testify/mock` строится на строковых именах методов и `interface{}` — ошибки видны в рантайме. Альтернатива для генерации моков: `mockery`, `moq` 🟡. Проверка сложных структур: `go-cmp` 🟡.

### P-10 🔴 Линтер — `golangci-lint` (ADR-014)
Конфиг в репозитории. Замечание: ADR-014 приводит `golangci-lint-action@v6`; при переходе на golangci-lint v2 версия action должна быть новее — проверить совместимость при реализации CI.

### P-11 🔴 PDF для справки (`chassis/certificate`) — `ВЫБОР`
Контракт: `собрать(шаблон, данные) → PDF`, без состояния; маппинг данных — в Orders (диаграмма классов, `sequence-certificate`). Сигнатура намеренно отложена (TODO §5).
Варианты: форки `fpdf` (прямое рисование), `maroto` (табличная вёрстка поверх), HTML → PDF через headless Chrome (`chromedp`) — богатая вёрстка, но тяжёлый образ и зависимость от браузера; коммерческие библиотеки с лицензионными ограничениями — избегать. **Перед выбором проверить актуальность и поддержку** конкретной библиотеки.
**Обязательный нюанс:** кириллица требует регистрации TTF-шрифта с поддержкой Unicode (встроить через `go:embed`); стандартные шрифты PDF её не поддерживают.
**Задачи:** (1) сформулировать интерфейс генератора, не завязанный на конкретную библиотеку. (2) Сравнить прямое рисование и HTML→PDF по размеру образа, времени сборки, сложности шаблона и воспроизводимости в unit-тестах.

### P-12 🔴 Конфигурация из окружения — `ВЫБОР`
`os.Getenv` + собственная структура и проверка при старте (быстрое падение при отсутствии обязательных переменных) либо `caarlos0/env`. `godotenv` не нужен: compose сам подставляет `.env` (ADR-011). `viper` — избыточен.

### P-13 🟡 Валидация входа — `go-playground/validator/v10` либо ручные проверки

### P-14 🟡 Масштабирование изображений — `golang.org/x/image/draw` или `disintegration/imaging`

## 6. Блок D — паттерны, специфичные для проекта

### D-01 🔴 Transactional outbox (ADR-005, `chassis/outbox`)
Запись события в `outbox` — в той же tx, что и данные. Воркер: цикл по `Ticker` (~1 с), выборка пачки неопубликованных (`ORDER BY created_at`, частичный индекс), публикация с подтверждением, пометка `published=true, published_at`. При нескольких экземплярах — блокировка строк (`FOR UPDATE SKIP LOCKED`).
- Плохо: опубликовать в брокер, затем писать в БД (dual write); либо ставить `published=true` до подтверждения брокера; либо читать outbox без ограничения пачки.
- Отлично: запись события в tx с данными; пометка только после confirm; ограничение пачки; воркер завершается по `ctx.Done()`.
**Задача:** описать, какие дубли возможны и почему получатель обязан их переживать (связь с P-06).

### D-02 🔴 Оркестратор саги оплаты (ADR-002/003/006)
`status → paid` + `saga_state='verifying_stock'` + outbox-команда списания — **одна транзакция**. Ответ приходит с `order_id`, не с `saga_id` (индекс по `order_id`). Идемпотентность — сравнением `current_step` перед шагом. Failed → компенсация `paid → active`, без retry (ADR-016). Один экземпляр Orders (иначе нужен атомарный `UPDATE … WHERE current_step=…`, ADR-006).
**Задачи:** (1) нарисовать конечный автомат шагов и допустимых переходов. (2) Определить, что делает консьюмер ответов при ответе на сагу, которой нет, или на шаге, который уже пройден.

### D-03 🔴 Транзакции и границы
Одна `Tx` на сценарий, `defer Rollback`, коммит в конце; без вложенных tx; не делать сетевые вызовы внутри транзакции. Сценарии с tx: claim (ADR-020), create-order (+ `order_engineers`), оплата (D-02), запись справки.

### D-04 🔴 API Composition в Gateway (`sequence-director-dashboard`)
Два параллельных запроса (Orders stats, Users engineers-load) → склейка; таймауты; поведение при частичном отказе (ошибка всего дашборда или частичный ответ — решить). Инструмент — `errgroup` + `context`.

### D-05 🔴 Периметр и роли в Gateway (ADR-010, ADR-019)
Таблица «группа эндпоинтов → допустимая роль» (RN-API — `engineer`, директорские — `director`, клиентские — `client`). Идентичность передаётся вниз заголовками, выставленными Gateway после проверки токена (стирать присланные клиентом). Инвариант безопасности: сервисы и RabbitMQ Management (`15672`) **не публикуют порты наружу** (`ports:` только у nginx и Gateway).

### D-06 🔴 Retry-воркер справки (`sequence-certificate`)
`failed` + `retry_count ≤ 3` → повтор сборки; после — «обратитесь в поддержку» (в v1 статический экран). Справка создаётся после `paid`, снапшот фиксируется на успехе и неизменен.
⚠ Неоднозначность: `retry_count += 1` после каждой неудачи и повтор при `retry_count <= 3` дают до 4 сборок суммарно (первая + 3 повтора), тогда как ADR-016 говорит «до 3 попыток». Уточнить, сколько всего попыток подразумевается.

### D-07 🔴 Доменные правила в чистых функциях
Правило «`выдан` ⇐ `paid`», расчёт суммы, допустимость отмены (`requested`/`active`) — функции без зависимостей: именно их покрывают unit-тесты по ADR-013.

### D-08 🟡 Soft delete
Флаг `deleted`; все выборки обязаны фильтровать; часть уникальных индексов должна учитывать флаг.

### D-09 🟡 Известные расхождения документов, влияющие на код (из `TODO.md §7`)
- Списание: условие `quantity > 0` не защищает от ухода в минус при списании >1 шт. (нужно `quantity >= N` и/или `CHECK`).
- Между `paid` и ответом Inventory заказ уже `paid`: справка и этап «выдан» технически доступны в этом окне.
- В `order_items`/`order_services` нет цены: изменение прайса меняет суммы старых оплаченных заказов.
- ADR-003/009 приводят сагу «создание заказа» как пример; единственная сага — оплата.
- В плане CI (ADR-014) три сервиса, в v1 — шесть.
