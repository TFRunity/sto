# ADR-004: Структура кода — по домену, не по техническому слою

## Статус
Принято

## Контекст
Распространённый в языках вроде C# подход — организовывать код по
техническому типу: `handler/`, `service/`, `repository/`, `domain/` на
верхнем уровне пакета. В Go-сообществе этот подход спорен: часть
источников считает его переносом чуждой парадигмы (Clean
Architecture/C#-style layering), которая плохо ложится на идиомы языка
и создаёт разделение по типу файла, а не по зоне ответственности.

## Решение
Пакет `internal/` каждого сервиса организуется по домену/смысловой зоне
ответственности, а не по техническому слою. Для сервиса с одним доменом
— плоская структура без подпапок (`internal/user.go`,
`internal/repository.go`, `internal/service.go` и т.д. в одном пакете).
Для сервиса с несколькими зонами ответственности — подпапки по смыслу
(например, `internal/order/` и `internal/saga/`), а не по типу файла.

## Альтернативы, которые рассматривались
- **Layered/Clean Architecture** (`internal/handler/`,
  `internal/service/`, `internal/repository/` на верхнем уровне) —
  отклонено как основной подход. Признаётся легитимной практикой для
  крупных приложений (Hexagonal Architecture в части источников
  описывается именно так), но для сервисов с одним доменом создаёт
  лишнюю навигационную сложность без выгоды: домен один, дробление по
  слою не решает никакой реальной задачи разделения ответственности.

## Последствия
**Плюсы:** вся логика одного домена физически рядом — не нужно прыгать
между `handler/`, `service/`, `repository/`, чтобы понять один сценарий
целиком; соответствует идиоматичной Go-практике организации по фиче/
домену; не создаёт лишней вложенности там, где домен один.

**Минусы:** при существенном росте сложности одного домена внутри
сервиса структура может потребовать пересмотра в сторону явного
разделения — это осознанный компромисс на пользу простоты сейчас, а не
единственно верный подход навсегда.
