# ADR-006: Отслеживание прогресса саги через saga_state

## Статус
Принято. **Частично заменено ADR-030 (30.10.2026).**

> **Что устарело в этом ADR** (текст ниже не переписан, чтобы сохранить
> историю решения):
> 1. «Ответы приходят с `order_id`, не с `saga_id`» — теперь команды и
>    ответы несут `saga_id` (+ `order_id` для логов); поиск саги по PK.
> 2. «Атомарный `UPDATE … WHERE current_step = …` отклонён» — **принят**:
>    за сагу конкурируют два участника даже в одном процессе (консьюмер
>    ответов и воркер дедлайнов).
> 3. «Explicit-идемпотентность отложена» — для списания реализована в
>    Inventory по `saga_id` (таблица попыток).
> 4. Схема `saga_state`: добавлен `deadline`; колонка `status` удалена
>    (см. ADR-030, Решение А-05 (принято 30.10.2026)).

## Контекст
Оркестратор саги (см. ADR-002, ADR-003) выполняет процесс из нескольких
шагов, ожидая ответов от других сервисов между ними. Если процесс
хранится только в памяти сервиса, перезапуск (деплой, падение) приводит
к полной потере прогресса: сервис не знает, что где-то есть незавершённый
процесс, ожидающий ответа, и не может корректно обработать запоздавший
ответ.

## Решение
Прогресс каждой саги хранится в таблице `saga_state`, обновляемой на
каждом шаге. Обновление состояния и публикация следующей команды
происходят **в одной транзакции** (используя тот же механизм, что и
outbox, см. ADR-005) — иначе связка теряет надёжность: состояние может
утверждать, что шаг выполняется, хотя команда для него не была
отправлена из-за сбоя между двумя раздельными операциями.

```sql
CREATE TABLE saga_state (
    saga_id       uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    order_id      uuid NOT NULL REFERENCES orders(id),
    current_step  text NOT NULL,
    status        text NOT NULL,
    created_at    timestamptz NOT NULL DEFAULT now(),
    updated_at    timestamptz NOT NULL DEFAULT now()
);

CREATE INDEX idx_saga_state_order_id ON saga_state (order_id);
```

Индекс по `order_id` обязателен: ответы от сервисов-исполнителей
приходят с `order_id`, не с `saga_id` (исполнитель не знает о внутреннем
идентификаторе саги) — это самый частый запрос к таблице.

Идемпотентность на дублирующиеся/устаревшие ответы обеспечивается через
сравнение `current_step` перед выполнением шага — естественная защита,
не требующая отдельного механизма дедупликации в базовом случае (см.
"Альтернативы" ниже).

## Альтернативы, которые рассматривались
- **Без сохранения состояния (только в памяти)** — отклонено: не
  переживает рестарт сервиса, сага "теряется" при любом деплое или
  сбое.
- **Explicit-идемпотентность через отдельную таблицу
  `processed_messages`** (уникальный `message_id`, `INSERT ... ON
  CONFLICT DO NOTHING`) — рассмотрено и отложено как избыточное для
  текущего набора шагов саги, где все операции либо являются чтением,
  либо естественно идемпотентны (`SET status = 'confirmed'` безопасно
  выполнить повторно). Пересмотреть точечно для конкретных шагов с
  реальным побочным эффектом высокой цены (списание средств, изменение
  остатков склада), если такие появятся.
- **Атомарный переход состояния через `UPDATE ... WHERE current_step =
  '...'`** вместо простой проверки `if state.CurrentStep != "..."` в
  коде — рассмотрено как защита от гонки при параллельной обработке
  двумя экземплярами оркестратора. Отклонено: несколько параллельных
  экземпляров `orders-service` не планируются, простая проверка
  достаточна и не требует изменения. Пересмотреть при переходе к
  горизонтальному масштабированию Orders.

## Последствия
**Плюсы:** оркестратор переживает рестарт без потери прогресса;
устаревшие/дублирующиеся ответы естественно отбрасываются без
дополнительного кода.

**Минусы:** архитектурно зависит от корректной работы outbox (ADR-005)
— рассинхронизация между `saga_state` и фактически отправленными
командами возможна только при нарушении этой связки, не сама по себе.

**Требует пересмотра при:** росте числа параллельных экземпляров
Orders (нужен атомарный `UPDATE ... WHERE`) или появлении шагов с
дорогим побочным эффектом (нужна explicit-идемпотентность).
