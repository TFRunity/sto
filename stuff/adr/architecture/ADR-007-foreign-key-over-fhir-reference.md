# ADR-007: Типизированные внешние ключи вместо generic JSON-ссылок (FHIR-style)

## Статус
Принято

## Контекст
При Database per Service (ADR-001) ссылки между сущностями разных
сервисов не могут быть физическими `FOREIGN KEY` (базы разные).
Рассматривался вариант единого generic-формата ссылок по аналогии с
FHIR `Reference` (`{ resourceType: "User", id: "123" }`), хранимого в
JSONB-поле, вместо обычной типизированной колонки (`user_id uuid`).

## Решение
Ссылки между сервисами реализуются как обычные типизированные колонки
по соглашению (`<entity>_id`, тип `uuid`), не обеспеченные физическим
`FOREIGN KEY`, но проверяемые на уровне доменной логики. Единый
generic-формат ссылок (FHIR-style) не используется.

## Альтернативы, которые рассматривались
- **FHIR-style generic reference** (`references: jsonb` с единым
  форматом `{service, id}` для любых связей) — отклонено для текущего
  масштаба. Такой формат даёт гибкость, оправданную там, где число типов
  сущностей и связей велико и растёт непредсказуемо (как в реальном
  FHIR-стандарте, рассчитанном на десятки типов ресурсов и множество
  организаций-потребителей). При стабильном, заранее известном наборе
  сервисов и связей эта гибкость не используется на практике, а стоимость
  реальна: потеря контроля типов на уровне БД, менее эффективные и
  менее очевидные индексы (JSONB path вместо колонки), более сложный для
  чтения запрос (`WHERE references->'user'->>'id' = $1` вместо `WHERE
  user_id = $1`).

  Отдельно отмечено: подход обоснован и используется автором в реальной
  практике (на другом проекте, с иным масштабом связей) — там, где связи
  между сервисами закладываются как часть контракта на старте и является
  устоявшейся конвенцией команды, единый формат ссылок оправдан. Для
  данного проекта это условие не выполняется (расширение состава
  сервисов не планируется), поэтому решение принято по контексту этого
  конкретного проекта, а не как отрицание практики в целом.

## Последствия
**Плюсы:** контроль типов на уровне БД; простые и быстрые обычные
индексы; запрос читается без знания дополнительной конвенции.

**Минусы:** добавление нового типа связи требует миграции схемы
(добавление колонки), а не просто нового ключа в JSON — приемлемо при
низкой частоте изменения набора связей.

**Пересмотреть, если:** состав сервисов и связей между ними станет расти
часто и непредсказуемо — тогда стоимость миграций может превысить
стоимость потери типизации.
