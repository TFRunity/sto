# ADR-035: Справка — только после завершённой саги; 3 попытки с нарастающей паузой; всё собирает воркер

## Статус
Принято

В v3 справка по-прежнему создаётся при успешном списании товара. Заказ получает подтверждённую отметку оплаты раньше. [ADR-043](ADR-043-manual-payment-stock-gate.md)

## Контекст
По `sequence-certificate` справка создавалась после `paid` в статусе
`active`, retry-воркер повторял `failed`, пока `retry_count ≤ 3`. Три
проблемы:
- `retry_count += 1` и повтор при `≤ 3` дают 4 сборки, а ADR-016 говорит
  «до 3 попыток»;
- после ADR-030 `paid` ещё не окончателен: в течение 10 с оплата может
  откатиться, и у неоплаченного заказа осталась бы справка;
- при падении Gotenberg воркер с тиком 1 с сжёг бы все попытки за пару
  секунд.

## Решение
- **Всего 3 попытки** сборки, включая первую. Поле `attempts` (сколько
  сборок сделано) вместо `retry_count`; повтор при `attempts < 3`.
- **Создание — автоматически:** в той же транзакции, где сага переходит в
  `completed` (консьюмер ответа `StockDeducted`, ADR-030), —
  `INSERT certificates (status='pending')`. Справка существует только у
  заказа с подтверждённой оплатой. Инженер справку не запускает: момент
  оплаты — точка, когда со стороны СТО всё уже оформлено (исполнители,
  позиции). Одна справка на заказ (`UNIQUE (order_id)`): успешно
  завершиться может только одна сага заказа.
- **Все сборки делает воркер**, включая первую: справка рождается в
  `pending`, воркер берёт `pending` или `failed` с `attempts < 3` и
  `next_attempt_at <= now()`. Сетевые вызовы (Users/Inventory/Services
  за именами, Gotenberg) — вне транзакции (ADR-031).
- **Пауза нарастает:** после 1-й неудачи — 10 с, после 2-й — 1 мин. После
  3-й — `failed` окончательно: `attempts = 3`, `next_attempt_at = NULL`;
  пользователь видит «обратитесь в поддержку».
- Переходы статуса — условный UPDATE (ADR-031).
- Статусы: **`pending | completed | failed`**.

В v3 API показывает `processing` при формировании и запланированном повторе,
`ready` после сохранения PDF и `failed` после трёх неудач без следующей
попытки. Клиент видит список и PDF своих заказов. Директор читает статус
и PDF любого заказа. Инженер видит статус в карточке заказа, где он
ответственный или исполнитель. Доступ из истории ТС не расширяет права на справку.

> Разбор А-01 (30.10.2026): рассматривался вариант «справку создаёт
> инженер кнопкой с проверкой саги» — ради сохранения use case
> «Сформировать справку». Отклонён разработчиком: в момент оплаты всё уже
> должно быть готово. Use case остался как `«include»` от «Оплатить
> заказ» без связи с актёром «Инженер»; RN-кнопка убирается (TODO §7).
>
> Решение А-02 (принято 30.10.2026): статус `active` переименован в `pending` (так его
> называло решение D-06); отдельного «в процессе» нет — если воркер
> упадёт посреди сборки, справка останется `pending` и будет подобрана
> снова, попытка не засчитается.

```sql
CREATE TABLE certificates (
    id              uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    order_id        uuid NOT NULL UNIQUE REFERENCES orders(id),
    status          text NOT NULL CHECK (status IN ('pending','completed','failed')),
    attempts        int  NOT NULL DEFAULT 0 CHECK (attempts BETWEEN 0 AND 3),
    next_attempt_at timestamptz,
    snapshot        jsonb,
    pdf             bytea,
    created_at      timestamptz NOT NULL DEFAULT now(),
    updated_at      timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX idx_certificates_due ON certificates (next_attempt_at)
    WHERE status IN ('pending','failed') AND next_attempt_at IS NOT NULL;
```

## Альтернативы, которые рассматривались
- **4 сборки (1 + 3 повтора)** — расходится с ADR-016. Отклонено.
- **Фиксированная пауза** — либо долго ждать при единичном сбое, либо
  мало при длинном. Отклонено.
- **Справку создаёт инженер кнопкой** (с проверкой `paid` + сага
  `completed`) — лишний ручной шаг и 409 в окне 10 с после оплаты.
  Отклонено при разборе А-01.
- **Первая сборка синхронно в запросе** — две логики (первая попытка и
  повторы) и сетевой вызов на пути HTTP-запроса. Отклонено.

## Последствия
**Плюсы:** справка только у подтверждённой оплаты; кратковременный сбой
Gotenberg не сжигает попытки; одна логика воркера.

**Минусы:** справка появляется не мгновенно (до тика воркера); снапшот
фиксирует исполнителей на момент оплаты — добавленный позже исполнитель
в справку не попадёт.
