# ADR-039: Список заказов директора — поиск и имена через API composition в Gateway

## Статус
Принято

## Контекст
Таблица «Все заказы» директора (`director-web-design_1.md`) показывает
ТС/номер, клиента и инженера и ищет по номеру и клиенту. В базе Orders
есть только `client_id`, `vehicle_id`, `engineer_id` — имена и госномера
принадлежат Users и Vehicle (ADR-001). Показ имён можно добрать после
получения страницы, но поиск — нельзя: фильтр должен сработать **до**
пагинации, а Orders не знает, какой `client_id` у «Иванова».

## Решение
Эндпоинт Gateway `GET /director/orders?status=&q=&page=` — собственный,
как дашборд (ADR-028, ADR-032). Gateway остаётся оркестратором: только
склеивает данные, бизнес-правил не принимает.

1. **`q` задана** → параллельно `GET /users/search?q=` (имя / телефон) и
   `GET /vehicles/search?q=` (номер, нормализованный той же функцией,
   что при записи — ADR-031) → списки `client_ids`, `vehicle_ids`.
   Оба пусты → сразу пустая страница, Orders не вызывается.
2. `GET /orders?status=&client_ids=&vehicle_ids=&page=` — Orders
   фильтрует `client_id = ANY($1) OR vehicle_id = ANY($2)` (необязательные
   параметры — `sqlc.narg`), сортирует и пагинирует сам.
3. Для страницы — параллельно пакетные `GET /users?ids=` (клиенты и
   инженеры) и `GET /vehicles?ids=` (номера) → склейка.
4. Отказ любого вызова или общий дедлайн 3 с → `502` / `504`, частичного
   ответа нет (ADR-032).

> Разбор А-12 (30.10.2026): **принято пока** (пересматриваемо —
> разработчик может вернуться к параметрам):
> - `q` — от 2 символов, `ILIKE` по подстроке;
> - Users и Vehicle возвращают не больше 200 id; больше —
>   `422 search_too_broad` («уточните запрос»);
> - поиск и пакетная выдача по id **включают удалённых**
>   (`-- include-deleted`, ADR-033): у удалённого клиента остаются старые
>   заказы, и их нужно находить и подписывать.

## Альтернативы, которые рассматривались
- **Снапшот имени и номера в заказе** (как цена, ADR-034) — один запрос с
  `ILIKE`, но синхронные вызовы Users/Vehicle при создании заказа и
  персональные данные в БД Orders. Отклонено.
- **Локальная реплика через события** — консьюмеры, eventual
  consistency; ADR-015 уже отверг такой кэш как избыточный. Отклонено.
- **Поиск только по номеру заказа** — урезает функцию. Отклонено.

## Последствия
**Плюсы:** ни один сервис не хранит чужие данные; паттерн тот же, что у
дашборда; пагинация остаётся в Orders.

**Минусы:** 3–5 внутренних запросов на страницу (при масштабе СТО —
незаметно); в Users и Vehicle — по два новых эндпоинта (поиск → id,
пакет по id); широкий запрос режется лимитом.

Тот же приём (пакетная выдача по id) годится для любых списков, где
нужны имена из чужих сервисов.
