# ADR-019: Роли client / engineer / director и проверка роли в Gateway

## Статус
Принято. Дополняет ADR-010 (не заменяет). Реализация таблицы ролей и
передачи идентичности — ADR-022, ADR-037.

## Контекст
По исходному `web-design.md` пользователь при регистрации получал
базовую роль, «совпадающую с ролью инженера на уровне данных». Отличить
клиента от инженера в данных было невозможно. Gateway (ADR-010)
проверяет только подлинность токена, поэтому клиент, зарегистрированный
через веб, мог войти в RN-приложение инженера, увидеть общий пул заявок
и нажать «Взять в работу».

## Решение
Роль — enum `client | engineer | director` в таблице пользователей
Users-service.
- `POST /register` (только веб) всегда создаёт `client`.
- `engineer` и `director` заводятся вручную, напрямую в БД — как и
  раньше, без админ-интерфейса.
- Роль кладётся в токен при входе. Gateway, помимо подлинности токена,
  проверяет роль по группе эндпоинтов: RN-API — только `engineer`,
  директорские эндпоинты — только `director`, клиентские — `client`.

Сервисы за Gateway по-прежнему не перепроверяют ни токен, ни роль —
модель perimeter trust из ADR-010 сохраняется, расширяется только набор
проверок на периметре.

## Альтернативы, которые рассматривались
- **Одна базовая роль, как было** — отклонено: дыра «клиент в
  приложении инженера» реальна и не требует злого умысла.
- **`users` + таблицы профилей (`client_profile`, `employee_profile`)**
  — отклонено как избыточное для 5–7 сотрудников: лишние JOIN без
  практической выгоды. Пересмотреть, если у сотрудников появится много
  полей, которых нет у клиентов.

## Последствия
**Плюсы:** perimeter trust начинает разграничивать доступ, а не только
аутентифицировать; правка минимальная — одна колонка и таблица правил
в Gateway.

**Минусы:** перевод клиента в инженеры — ручной `UPDATE` в БД;
изменение роли вступает в силу только после перевыпуска токена.
