# ADR-037: Gateway — allowlist заголовков на проксировании, идентичность выставляет только Gateway

## Статус
Принято. Дополняет ADR-010 и ADR-019.

## Контекст
Gateway после проверки JWT передаёт вниз `X-User-Id` и `X-User-Role`, и
сервисы верят им без проверки (ADR-010). `ReverseProxy` по умолчанию
копирует входящие заголовки: если клиент сам пришлёт
`X-User-Role: director`, а Gateway его не уберёт, периметр пробит.

## Решение
- **Allowlist:** исходящий запрос собирается заново; из входящего
  переносятся только явно разрешённые заголовки. Стартовый набор:
  `Content-Type`, `Accept`, `Accept-Language`.
- `X-User-Id`, `X-User-Role` выставляет Gateway после проверки токена.
- `X-Request-Id` генерирует Gateway; от клиента не принимается.
- `Authorization` (JWT) вниз не уходит — сервисам он не нужен.
- Middleware в `chassis` читает заголовки идентичности в контекст. Нет
  заголовка на защищённом маршруте → `401` (формат ADR-032) + warn-лог,
  отличающий ошибку конфигурации от обычного «не залогинен».
- Инвариант: `ports:` в compose только у nginx (и Gateway в разработке) —
  ADR-010, ADR-038.

## Альтернативы, которые рассматривались
- **Удалять конкретный список заголовков** — новый заголовок
  идентичности легко забыть добавить.
- **Удалять по префиксу (`X-User-*`)** — защищает новые заголовки, но
  остаётся denylist-подходом.

Оба варианта **ломаются открыто**: забытый заголовок = дыра, которую
тесты не покажут. Allowlist **ломается закрыто**: забытый заголовок =
неработающая фича, видно на первой же проверке. Та же логика
deny-by-default, что в таблице ролей (ADR-022).

## Последствия
**Плюсы:** подмена идентичности клиентом невозможна по построению.

**Минусы:** список пропускаемых заголовков нужно вести (например,
проверить multipart `Content-Type` с boundary при загрузке фото).
