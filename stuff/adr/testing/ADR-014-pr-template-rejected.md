# ADR-014: PR-шаблон с ручным чеклистом не используется; CI-пайплайн — план к реализации

## Статус
Частично отклонено, частично принято как план. План CI уточнён 30.10.2026.

## Контекст
Рассматривались два механизма контроля качества перед мержем изменений:
автоматический CI-пайплайн (тесты, линтер, сборка) и PR-шаблон с ручным
чеклистом (текстовая форма с пунктами для самопроверки автора PR).

## Решение

**CI-пайплайн — принято как план, не реализовано технически.**
Планируется пайплайн, блокирующий мердж при провале любого из шагов.
Реализация — отдельная предстоящая задача (этап «Каркас» плана разработки).

> Уточнено 30.10.2026 (P-10, I-07, I-08, D-08). Исходный план покрывал три
> сервиса и `golangci-lint-action@v6`, который не поддерживает
> golangci-lint v2. Актуальный план:

- **Шесть приложений + `chassis`** — семь Go-модулей монорепо (ADR-036):
  `gateway`, `users`, `orders`, `vehicle`, `inventory`, `services`, `chassis`.
- **Matrix-джоб по модулю**: для каждого модуля параллельно `go build ./...`,
  `go test ./...`, `golangci-lint run`. В интерфейсе GitHub сразу видно,
  какой модуль упал.
- **Линтер:** golangci-lint v2.x (минорная версия зафиксирована),
  `golangci/golangci-lint-action@v9`, `version: "2"` в `.golangci.yml`.
  Линтеры: standard (`errcheck`, `govet`, `ineffassign`, `staticcheck`,
  `unused`) + `errorlint`, `bodyclose`, `noctx`, `exhaustive`, `nilerr`.
  `gosec` не включён (шум); сгенерированный код исключается по заголовку
  `Code generated … DO NOT EDIT`.
- **Общий джоб проверок:**
  - нет диффа после `sqlc generate` (ADR-024);
  - нет диффа после `oapi-codegen` (ADR-028);
  - soft delete: каждый SQL-запрос к таблице с `deleted_at` содержит
    `deleted_at IS NULL` либо пометку `-- include-deleted` (ADR-033).
- **CI вызывает цели корневого Makefile** (`generate`, `lint`, `test`) —
  локальная проверка и CI не расходятся. Makefile один, в корне монорепо,
  заводится сразу (а не «по факту накопления команд» в `chassis`).

```yaml
# .github/workflows/ci.yml — целевой план (набросок, не рабочий файл)
jobs:
  module:
    strategy:
      matrix:
        module: [chassis, gateway, users, orders, vehicle, inventory, services]
    steps:
      - run: make build MODULE=${{ matrix.module }}
      - run: make test  MODULE=${{ matrix.module }}
      - uses: golangci/golangci-lint-action@v9
        with:
          working-directory: ${{ matrix.module }}
  checks:
    steps:
      - run: make generate && git diff --exit-code   # sqlc + oapi-codegen
      - run: make check-soft-delete
```

**PR-шаблон с ручным чеклистом — отклонено, не отложено.**

## Обоснование отклонения PR-шаблона
То, что проверяется автоматически (тесты, линтер, успешность сборки),
берёт на себя CI — дублирование этого в шаблоне как галочки для ручной
отметки избыточно и создаёт ложное чувство проверки без реальной
гарантии (человек может отметить пункт, не выполнив его). То, что не
проверяется автоматически (например, своевременное обновление
документации при смене архитектурного решения) — остаётся на
дисциплине разработчика, а не оформляется как процессная обвязка.

## Последствия
**Плюсы:** нет процесса, дающего ложное чувство контроля там, где
реальный контроль не гарантирован; CI, когда будет реализован, даёт
gate, который физически невозможно обойти в отличие от чеклиста.

**Минусы:** до реализации CI-пайплайна проект не имеет автоматической
защиты от мерджа сломанного кода — контроль полностью на дисциплине
разработчика в переходный период.

**Пересмотреть:** если в проект начнут вовлекаться другие разработчики —
тогда полагаться исключительно на личную дисциплину каждого станет
недостаточно, и вопрос PR-шаблона (или иной формы обязательного
описания изменений) может быть поднят заново в новом контексте.
