# Решения по инфраструктуре v1 (блок I)

Дата: 30.10.2026

## Как пользоваться

Сводка решений по блоку I карты знаний `go-v1-knowledge-map.md`. Продолжает `stack-decisions-v1.md` (S, P) и `pattern-decisions-v1.md` (D). Каждое решение — заготовка ADR: решение, причина, следствия.

---

## I-01 — Docker-образы сервисов

- **Решение:** multi-stage сборка (`CGO_ENABLED=0`); runtime-образ — `alpine` (тег зафиксирован); healthcheck через `wget` на `/healthz`; отдельный Dockerfile у каждого из шести сервисов.
- **Причина:** шелл и `wget` в образе — удобно отлаживать и проверять здоровье без доработок бинаря; отдельные файлы проще настраивать под конкретный сервис.
- **Следствия:**
  - в образе создаётся непривилегированный пользователь, процесс не запускается от root;
  - контекст сборки — корень репозитория (I-10);
  - общие изменения сборки (версия Go, флаги) вносятся в шесть файлов;
  - отвергнуто: `distroless/static:nonroot` + подкоманда healthcheck в бинаре; один Dockerfile с `ARG SERVICE`.

## I-02 — Docker Compose

- **Решение:**
  - пять контейнеров Postgres — по одному на сервис с БД (у Gateway БД нет);
  - сети: `edge` (nginx ↔ Gateway), `backend` (Gateway ↔ сервисы ↔ RabbitMQ ↔ Gotenberg), по отдельной сети на каждую БД (сервис ↔ его Postgres);
  - при подключении Next.js к Compose задать явные имена сетей Docker: `sto-edge` для `edge` и `sto-backend` для `backend`. Next.js и nginx подключаются только к `edge`, Gateway подключается к обеим сетям. Внутренние Go-сервисы остаются в `backend` и в нужных им инфраструктурных сетях;
  - браузер обращается к API через опубликованный nginx и Gateway. Серверный код Next.js может обратиться к Gateway по `edge`. У Next.js нет общей Docker-сети с внутренними Go-сервисами. Для локального `make web` Next.js запускается на хосте;
  - `depends_on` с `condition: service_healthy` на свой Postgres и RabbitMQ;
  - `restart: unless-stopped` у всех сервисов;
  - `ports:` только у nginx (и Gateway, если нужно в разработке) — ADR-010/012.
- **Причина:** ADR-001 обеспечивается сетью, а не только правами — сервис физически не видит чужую БД; сервис падает при отсутствии очередей (P-06) и должен перезапускаться.
- **Следствия:** пять томов и пять бэкапов (`pg_dump` по каждой БД); больше потребление памяти; отвергнуто: один Postgres с пятью базами.

## I-03 — PostgreSQL (закрывает долг «версия Postgres в compose»)

- **Решение:** образ `postgres:18` (тег мажорной версии, патчи подтягиваются); том монтируется в `/var/lib/postgresql`.
- **Причина:** 18 — последняя стабильная мажорная версия (поддержка до 14.11.2030, последний патч 18.6 от 11.08.2026); Postgres 19 на 30.10.2026 в стадии RC, GA запланирован на 19.11.2026.
- **Следствия:**
  - в образе 18+ каталог данных — `/var/lib/postgresql/18/docker`, VOLUME — `/var/lib/postgresql`; монтирование в старый путь `/var/lib/postgresql/data` ломает запуск контейнера;
  - переход на 19 после выхода и обкатки; пока идёт разработка — пересозданием тома;
  - типы, индексы, `ON CONFLICT`, `CHECK` — решены в P и D.

## I-04 — `.env`

- **Решение:** `.env` в `.gitignore` с первого коммита; в git — `.env.example` со всеми переменными и фиктивными значениями; обязательные переменные проверяются при старте сервиса (P-12).
- **Причина:** ADR-011.

## I-05 — RabbitMQ в compose (закрывает долг «пользователь при `load_definitions`»)

- **Проверено:** при импорте definitions при старте брокер игнорирует `RABBITMQ_DEFAULT_USER`/`PASS` (и `default_user` в `rabbitmq.conf`) — пользователь должен быть описан в самих definitions. Поведение задумано, подтверждено мейнтейнерами.
- **Решение:**
  - definitions описываются в compose через `configs:` → `content:` (встроенный текст); пароль подставляется из `.env` (`${…}`), отдельного файла с секретом нет;
  - образ `rabbitmq:4.3-management` (минорная версия зафиксирована; на 06.10.2026 последняя ветка 4.3, патч 4.3.6 — по сторонним трекерам, сверить с официальной страницей релизов при сборке);
  - Management UI (`15672`) не публикуется наружу (ADR-012).
- **Причина:** ADR-011 (секреты только в `.env`) сохраняется без шага генерации файлов; дополняет P-06 (топология в definitions), меняется только место хранения.
- **Следствия:** JSON топологии живёт внутри compose-файла; отвергнуто: шаблон + генерация `definitions.json`; отказ от definitions.

## I-06 — nginx

- **Решение:**
  - пока только локальный запуск по HTTP; веб — по имени `sto.localhost` (браузеры резолвят `*.localhost` в 127.0.0.1 без правки `hosts`); nginx слушает не только 127.0.0.1;
  - RN на реальном телефоне — по IP машины в локальной сети, Android-эмулятор — `10.0.2.2`; адрес API в RN задаётся конфигом;
  - лимиты загрузки фото: клиент сжимает до ≤ 3 МБ (P-14); сервис — `MaxBytesReader` ~3,5 МБ на весь запрос (S-11); nginx — `client_max_body_size 4m` (страховка, `413` в нашем формате отдаёт сервис).
- **Причина:** публичного развёртывания пока нет; лимиты согласованы, чтобы ошибку видел клиент в формате долга №9, а не HTML nginx.
- **Следствия:**
  - в RN-приложении для разработки явно разрешается открытый HTTP (Android cleartext, iOS ATS) — иначе запросы падают с `Network request failed`;
  - фото лежат в томе Docker, размер влияет на том и его бэкап, не на Postgres;
  - **долг:** HTTPS (TLS на nginx) — обязателен при публичном развёртывании, иначе JWT уходит открытым текстом.

## I-07 — CI (GitHub Actions)

- **Решение:** matrix-джоб по модулю (шесть сервисов + `chassis`): `go build`, `go test`, `golangci-lint`; отдельный общий джоб — проверки диффа генерации (sqlc, oapi-codegen) и soft delete (D-08). Полный перечень — раздел «Проверки в CI» в `pattern-decisions-v1.md`.
- **Причина:** после I-10 линтер и сборка работают по модулю; matrix даёт параллельность и показывает, какой модуль упал.
- **Следствия:** CI вызывает цели Makefile (I-08). **При реализации — разобрать с разработчиком, что такое matrix-джоб и как он устроен.**

## I-08 — Makefile

- **Решение:** один Makefile в корне с самого начала; цели `generate` (sqlc + oapi-codegen), `lint`, `test`, `up`/`down`.
- **Причина:** локальная проверка и CI вызывают одни и те же цели и не расходятся.

## I-09 — `/healthz`

- **Решение:** `/healthz` проверяет только, что процесс жив (всегда 200); вызывается `wget` из healthcheck compose (I-01).
- **Причина:** простота; compose не перезапускает unhealthy-контейнер, healthcheck нужен для порядка запуска и наглядности.
- **Следствия:** «healthy» у сервиса не означает доступность его БД; реальную готовность БД гарантирует `depends_on` на healthcheck самого Postgres (`pg_isready`); RabbitMQ — реконнект в сервисе (P-06).

## I-10 — организация репозитория (закрывает долг из `stack-decisions-v1.md`)

- **Решение:** монорепо; отдельный `go.mod` у каждого из шести сервисов и у `chassis`; связка через `go.work` в корне.
- **Причина:** правки `chassis` сразу видны во всех сервисах; `chassis` остаётся настоящим модулем и позже выносится в отдельный репозиторий с версиями по тегам почти механически.
- **Следствия:**
  - Docker-образы и CI собираются из корня репозитория (иначе `chassis` не попадёт в контекст сборки);
  - у каждого сервиса свой набор зависимостей;
  - отвергнуто: один `go.mod` на всё (`chassis` не модуль); отдельный репозиторий `chassis` сейчас (тег и обновление версии в шести сервисах на каждую правку).
