## Сквозные правила (действуют во всех сервисах)

| Правило | Откуда |
| --- | --- |
| В `payload` сообщений (outbox) — только идентификаторы, без персональных данных (email, имя, телефон) | D-01 |
| Переход состояния в таблицах с конечным автоматом — условный `UPDATE … WHERE <состояние> = <ожидаемое>` с проверкой числа затронутых строк; 0 строк — не ошибка, а «другой участник успел раньше». Исключение: claim (ADR-017) остаётся без защиты от гонки | D-02 |
| Транзакция открывается в методе репозитория (метод на сценарий); ветвления внутри — через чистые доменные функции (D-07); сетевые вызовы — только вне репозитория | D-03 |
| Ошибки API — свой конверт `{"error": {"code", "message", "fields"}}` из `chassis`; `code` — стабильная машиночитаемая строка; внутренние детали (цепочка `%w`, текст ошибок Postgres) только в логах | Долг №9 |

## D-01 — transactional outbox

- **Решение:**
  - без блокировок строк (`FOR UPDATE SKIP LOCKED` не используется): `SELECT` пачки → публикация → `UPDATE … WHERE id = ANY($1)`;
  - publisher confirm ожидается на каждое сообщение отдельно;
  - AMQP `MessageId` = `outbox.id`;
  - журнал без чистки; частичный индекс `WHERE published = false` обязателен.
- **Причина:** один экземпляр сервиса (ADR-006); нагрузка невелика; блокировка удерживалась бы на время сетевого обмена (против D-03). Объём журнала мал: ~0,5–1 КБ на строку, ~50–100 МБ в год при 50 заказах в день.
- **Следствия:**
  - второй экземпляр сервиса гарантированно даст дубли — записать явно в ADR outbox (ADR-005);
  - при nack строка остаётся неотправленной до следующего тика;
  - скорость воркера не зависит от размера таблицы только при наличии частичного индекса;
  - `MessageId` — для логов и трассировки; идемпотентность получателей держится на бизнес-ключе (D-02), а не на `MessageId`;
  - дедупликация по `MessageId` ловит только повторную доставку того же сообщения: повтор команды допустим только переотправкой той же строки outbox, без новой записи.

## D-02 — оркестратор саги оплаты (закрывает долг P-06, часть 5)

### Решение

- **Старт:** в одной транзакции — заказ `paid`, сага `verifying_stock`, `deadline = now() + 10s`, outbox-команда «спиши» (`saga_id`, `order_id`).
- **Ключ идемпотентности — `saga_id`**, не `order_id` (**пересматриваемо**): каждая попытка оплаты независима, tombstone одной попытки не блокирует следующую. Команды и ответы несут `saga_id` (+ `order_id` для логов).
- **Inventory:**
  - таблица попыток по `saga_id` с состояниями `deducted | rejected | cancelled` и таблица позиций (что и сколько списано) — Inventory сам источник истины для возврата;
  - `rejected` записывается при нехватке товара, чтобы поздний дубль команды не списал;
  - повторное «спиши» → повторяется тот же ответ (не молчаливый ack — иначе потерянный первый ответ приведёт к ложному откату по дедлайну);
  - «отмени» по несуществующей попытке → tombstone `cancelled`; последующее «спиши» по этой попытке отклоняется (не зависит от порядка доставки).
- **Orders:**
  - переходы саги — условный `UPDATE … WHERE current_step = …` (консьюмер ответов и воркер дедлайнов конкурируют за одну сагу);
  - воркер дедлайнов (тик ~1 с), в одной транзакции: условный переход в `failed`, `paid → active`, outbox-команда «отмени» (`saga_id`);
  - ответ на неизвестную сагу или пройденный шаг → ack + warn-лог.
- **Потерянная команда «отмени»** (выброшена после 5 доставок) → error-лог с `saga_id`, ручной разбор через SQL. Риск принят: двойной сбой при масштабе СТО.

### Причина

At-least-once доставка и выбрасывание ядовитых сообщений (P-06) могли оставить сагу в `verifying_stock` навсегда. Дедлайн гарантирует завершение саги; идемпотентный Inventory делает компенсацию безопасной.

### Следствия

- Часовая задача для застрявших саг **не нужна** — убрана из плана.
- Посылка ADR-006 «один участник — атомарный UPDATE не нужен» больше не выполняется: участников два даже внутри одного процесса.
- Ложный откат возможен при задержке > 10 с; ответ «успех» после дедлайна отбрасывается проверкой `current_step`, списание отменяется командой «отмени».
- Отвергнуто: mutex в Go (защита в памяти для состояния в БД, ломается при втором экземпляре); ручной разбор просроченных саг; ключ `order_id` (ломается на повторной оплате и позднем дубле после `rejected`).

## D-03 — транзакции

- **Решение:** транзакция открывается внутри метода репозитория, один метод на сценарий; допускается разбиение на приватные подметоды.
- **Причина:** интуитивно очевидно; сервисный слой не знает о транзакциях; мок репозитория тривиален.
- **Следствия:**
  - решения между запросами (например, «UPDATE затронул 0 строк → доменная ошибка») делегируются чистым доменным функциям — иначе они не покрываются unit-тестами (ADR-013);
  - сетевые вызовы — в сервисном слое между методами репозитория. Пример справки: метод «создать» → вызов Gotenberg → метод «условно перевести в `completed`/`failed`»;
  - сценарии с транзакцией: claim, create-order, старт саги, ответ саги, воркер дедлайнов, справка;
  - отвергнуто: транзакция в сервисе через замыкание; транзакция в `context.Context` (неявная, компилятор не проверяет).

## D-04 — API composition (дашборд) и долг №9

### Дашборд

- **Решение:** всё или ничего — `errgroup.WithContext`, первая ошибка отменяет соседний запрос.
- **Причина:** частичный отказ крайне редок; простой контракт.
- **Следствия:**
  - общий дедлайн на дашборд через контекст (ориентир 3 с) + таймаут `http.Client` как страховка;
  - сервис ответил ошибкой или недоступен → `502`; не уложились в дедлайн → `504`;
  - при недоступности одного сервиса директор не видит дашборд целиком.

### Формат ошибок API (долг №9 — закрыт)

- **Решение:** свой конверт `{"error": {"code": "...", "message": "...", "fields": {...}}}` в `chassis` вместе с хелпером записи ответа и маппингом доменной ошибки в HTTP.
- **Причина:** минимально и ровно под нужды трёх клиентов.
- **Следствия:**
  - `code` — стабильная строка (`order_not_paid`, `plate_taken`); клиенты ветвятся только по ней, тексты для пользователя формируют сами;
  - `message` — для разработчика, не для показа;
  - `fields` — ошибки валидации в формате P-13;
  - Gateway пропускает ошибки сервисов как есть, свои (`401`, `403`, `502`, `504`) отдаёт в том же формате;
  - формат описывается в OpenAPI самостоятельно (отвергнут RFC 9457).

## D-05 — периметр и роли

- **Решение:**
  - заголовки при проксировании — **allowlist**: исходящий запрос собирается заново, из входящего переносятся только разрешённые (стартовый набор: `Content-Type`, `Accept`, `Accept-Language`); `X-User-Id`, `X-User-Role` выставляет Gateway после проверки JWT;
  - `X-Request-Id` генерирует Gateway, от клиента не принимается;
  - middleware в `chassis` читает заголовки идентичности в контекст; нет заголовка на защищённом маршруте → `401` + warn-лог.
- **Причина:** allowlist ломается закрыто (забытый заголовок = неработающая фича, видно сразу), denylist — открыто (забытый заголовок = дыра, тесты не покажут). Та же логика deny-by-default, что в таблице ролей P-01.
- **Следствия:**
  - `Authorization` (JWT) вниз не уходит;
  - список пропускаемых заголовков нужно вести (например, при загрузке фото проверить multipart `Content-Type` с boundary);
  - warn-лог отличает ошибку конфигурации от обычного «не залогинен»;
  - инвариант: `ports:` в compose только у nginx и Gateway (ADR-010/012).

## D-06 — retry справки

- **Решение:**
  - всего **3 попытки** сборки (включая первую), поле `attempts` вместо `retry_count`, повтор при `attempts < 3`;
  - справка создаётся в той же транзакции, где сага переходит в `completed` (не при `paid`);
  - справка рождается в `pending`; все сборки, включая первую, делает воркер: берёт `pending` или `failed` с `next_attempt_at <= now()`;
  - пауза между попытками нарастает: 10 с → 1 мин (поле `next_attempt_at`).
- **Причина:** снимает расхождение 3/4 попытки (ADR-016); после D-02 `paid` может откатиться в течение 10 с; сетевой вызов внутри транзакции саги запрещён (D-03); кратковременный сбой Gotenberg не сжигает все попытки.
- **Следствия:**
  - закрыт пункт D-09 о справке в окне между `paid` и ответом Inventory;
  - переходы статуса справки — условный UPDATE (сквозное правило);
  - после 3 неудач — `failed` окончательно, пользователь видит «обратитесь в поддержку»;
  - `sequence-certificate` обновить: создание по завершению саги, `pending`, `attempts`, `next_attempt_at`.

## D-07 — чистые доменные правила

- **Решение:** бизнес-правила — функции без БД и сети; покрываются табличными unit-тестами; вызываются из репозитория внутри транзакции (D-03). Стартовый перечень (дополняется при разработке):
  - **Orders:** перевод этапа в «выдан» (только при `paid` и успешно завершённой саге, иначе 409 — D-09); допустимость отмены (`requested`/`active`); допустимость начала оплаты; расчёт суммы (товары + услуги, `decimal`); шаг саги «состояние + ответ → завершить / откатить / проигнорировать»; справка — нужна ли попытка и когда следующая;
  - **Inventory:** «состояние попытки + команда → действие» (вся идемпотентность D-02);
  - **Vehicle:** нормализация госномера (регистр, пробелы, латиница/кириллица) перед проверкой уникальности.
- **Следствия:** функция Inventory тестируется полной таблицей «состояние × команда»; новые правила, найденные при разработке, добавляются сюда.

## D-08 — soft delete

- **Решение:**
  - soft delete у пользователей, машин, товаров, услуг; заказы не удаляются (статус «отменён»);
  - колонка `deleted_at timestamptz` в самой таблице сущности (рядом с `created_at`, `updated_at`); `NULL` — запись жива;
  - уникальные индексы — частичные, только среди живых (`… WHERE deleted_at IS NULL`): госномер, email;
  - фильтр `deleted_at IS NULL` пишется в каждом SQL-запросе sqlc; соблюдение проверяет CI (см. «Проверки в CI»); запросы, которым нужны удалённые записи, помечаются комментарием `-- include-deleted`.
- **Причина:** на записи ссылаются старые заказы; views отвергнуты (антипаттерн по мнению разработчика); склеивание запросов в Go ломает sqlc (P-04).
- **Следствия:**
  - проверка текстовая, а не разбор SQL — нестандартный запрос может её обойти;
  - при удалении в outbox может уходить событие «удалено» (только id), если другим сервисам это нужно;
  - отвергнуто: архивная таблица (`*_deleted`) — история требовала бы чтения из двух таблиц.

## D-09 — расхождения в документах

| Расхождение | Решение |
| --- | --- |
| Списание при `quantity > 0` уводит остаток в минус при N > 1 | `UPDATE … WHERE quantity >= N` + `CHECK (quantity >= 0)` в схеме; если хоть одна позиция не прошла — откат всего списания по попытке, ответ «не хватает» (`rejected`, D-02) |
| Между `paid` и ответом Inventory доступны справка и этап «выдан» | Справка — создаётся по завершению саги (D-06). «Выдан» — доменная функция проверяет `paid` **и** успешно завершённую сагу (D-07) |
| В `order_items`/`order_services` нет цены — смена прайса меняет старые суммы | Цена копируется в позиции заказа при его создании; Orders запрашивает цены у Inventory и Services по HTTP до открытия транзакции (D-03). Сумма заказа считается по сохранённым ценам |
| ADR-003/009 приводят сагу «создание заказа» | Исправить текст: единственная сага — оплата |
| План CI (ADR-014) на три сервиса | Исправить на шесть (см. «Проверки в CI») |

Следствие: создание заказа зависит от доступности Inventory и Services (как и прежде расчёт суммы); при их недоступности — ошибка в формате долга №9.

## D-10 — поиск в списке заказов директора (30.10.2026)

- **Проблема:** таблица директора ищет по клиенту и госномеру, а в Orders только id.
- **Решение:** API composition в Gateway — строка поиска сначала превращается в id через
  Users и Vehicle, затем Orders фильтрует по `client_id = ANY / vehicle_id = ANY` и
  пагинирует; имена для страницы — пакетными запросами по id. Gateway остаётся
  оркестратором без бизнес-правил. → ADR-039.
- **Отвергнуто:** снапшот имени/номера в заказе; реплика через события; поиск только по
  номеру заказа.
- **Позиции в оплаченном заказе:** принятый риск — в UI завершённого заказа нет кнопок
  добавления.
