# Решения по стеку v1 (блоки S и P)

Дата: 28.10.2026

## Как пользоваться

Сводка решений, принятых 27–28.10.2026 при проходе блоков S и P карты знаний `go-v1-knowledge-map.md`. Каждое решение блока P — заготовка отдельного ADR (раздел 10 карты): решение, причина, следствия.

Идентификаторы (S-xx, P-xx, D-xx, L-xx, ADR-0xx) совпадают с картой знаний и архивом `final_export_v1_v2.zip`. Отложенные вопросы собраны в последнем разделе.

## Блок S — стандартная библиотека

S-01…S-10 и S-13…S-16 известны и разбора не требуют. Отдельно разобраны S-11, S-12 и шаблонизатор.

| Пункт | Решение | Следствия |
| --- | --- | --- |
| S-11 загрузка файлов | `http.MaxBytesReader` обязателен; для фото — `ParseMultipartForm` с небольшим `maxMemory` (файл реализует `io.Seeker`) | 413 через `errors.As(*http.MaxBytesError)`; первый рубеж — `client_max_body_size` в nginx; имя файла — свой UUID, не клиентский `filename` |
| Хранение файлов | Том Docker, монтируется только в сервис; отдача через сам сервис (`http.ServeFile`), путь до клиента nginx → Gateway → сервис | В БД только ключ/url; порядок записи «файл → строка → при ошибке удалить файл»; права проверяет общий middleware; бэкап тома отдельно от `pg_dump` |
| S-12 изображения | Сервер: белый список JPEG/PNG (blank import), `DecodeConfig` с лимитом размеров до `Decode` | Защита от «пиксельной бомбы»; HEIC сервер не принимает (решается на клиенте, см. P-14) |
| Шаблонизатор | `html/template`, парсинг один раз при старте через `go:embed` | Используется для шаблона справки (P-11) |

## P-01–P-05: роутер, JWT, пароли, БД, миграции

### P-01 — HTTP-роутер
- **Решение:** stdlib `net/http` + `ServeMux` (Go 1.22+) во всех шести сервисах.
- **Причина:** модель `http.Handler` нужна для `ReverseProxy` и middleware; ноль зависимостей.
- **Следствия:** группы маршрутов и роли пишутся вручную по принципу deny-by-default: один middleware над mux Gateway, таблица «префикс → роли», неизвестный путь → 403, публичные `/login`, `/register` помечены явно.

### P-02 — JWT
- **Решение:** `golang-jwt/jwt/v5`, HS256, один долгоживущий токен на 7 дней без refresh.
- **Причина:** простота; при perimeter trust (ADR-010) Gateway и так точка доверия, асимметричная подпись почти ничего не даёт.
- **Следствия:**
  - секрет — 32+ случайных байт в `.env` у Users и Gateway;
  - при разборе `WithValidMethods` (только HS256) и обязательный `exp`;
  - `sub` = user_id, роль — свой claim;
  - срок жизни вынесен в env Users;
  - смена роли и удаление пользователя действуют только после перелогина или истечения токена (до 7 дней);
  - logout только клиентский, токен на сервере остаётся валидным до `exp`;
  - на RN токен хранится в защищённом хранилище (Keychain/Keystore), не в `AsyncStorage`.

### P-03 — хеш пароля
- **Решение:** bcrypt (`golang.org/x/crypto/bcrypt`), cost 12.
- **Причина:** готовое API без самописной криптографии; знаком разработчику.
- **Следствия:** проверка длины пароля ≤ 72 байт при регистрации; при отсутствии пользователя — сравнение с фиктивным хешем (одинаковое время ответа, защита от перебора логинов).

### P-04 — слой доступа к БД
- **Решение:** sqlc (генерация под `pgx/v5`) + `pgxpool`.
- **Причина:** SQL — первоисточник, без ORM/DSL/LINQ; ошибки в запросах ловятся до запуска.
- **Следствия:**
  - схема читается из миграций goose;
  - интерфейс `DBTX` + `WithTx` — outbox в одной транзакции с данными (D-01);
  - overrides типов в `sqlc.yaml` (uuid → `google/uuid`, numeric → `decimal.Decimal`);
  - динамические фильтры через `sqlc.narg` или отдельные запросы;
  - сгенерированные модели остаются внутри репозитория и маппятся в доменные типы;
  - сгенерированный код коммитится, CI проверяет отсутствие диффа после `sqlc generate`.

### P-05 — миграции
- **Решение:** goose, миграции встроены через `go:embed` и применяются при старте сервиса; только forward (down-миграции не пишутся).
- **Причина:** транзакция на каждую миграцию (нет состояния dirty); один экземпляр сервиса (ADR-006).
- **Следствия:** ошибка схемы исправляется новой up-миграцией; упавшая миграция откатывается транзакцией goose; настоящий откат — из бэкапа (`pg_dump` перед применением миграций).

## P-06: RabbitMQ (`amqp091-go`)

Клиент официальный, выбор шёл по механике. Часть 5 (идемпотентность Inventory) отложена — см. последний раздел.

| Часть | Решение | Следствия |
| --- | --- | --- |
| Соединения и каналы | Отдельные соединения для публикации и потребления; канал на роль/горутину | Канал не потокобезопасен для публикации; ошибка протокола (406) закрывает канал, а не соединение |
| Топология | Direct exchange для команд и ответов саги (`saga_commands`, `orders.saga_replies`); quorum-очереди | Вся топология (exchange, очереди, binding, лимит доставок) описана в definitions-файле RabbitMQ (`load_definitions`), смонтированном в compose. Сервисы делают только пассивную проверку своих очередей и падают при их отсутствии |
| Публикация | Publisher confirms; outbox помечает `published = true` только по ack | At-least-once: дубли возможны, получатели обязаны их переживать. Проверить, создаётся ли `RABBITMQ_DEFAULT_USER` при загрузке definitions (иначе пароль попадёт в файл — конфликт с ADR-011) |
| Потребление | Ручной ack строго после коммита транзакции; prefetch 1 для обоих консьюмеров | Сохраняется порядок шагов саги; повторная доставка после падения — норма |
| Ошибки обработки | Временная ошибка: nack с requeue после паузы 0,2 с. После 5 доставок сервис логирует сообщение и делает ack (выбрасывает) | Счётчик — заголовок `x-delivery-count` quorum-очереди; на брокере страховочный `x-delivery-limit` выше (например, 10). 5 × 0,2 с ≈ 1 с — выброшенный ответ Inventory оставит сагу в `verifying_stock` (решается долгом из последнего раздела) |
| Реконнект | Цикл-супервизор в `chassis`: подключение → канал → Qos → Consume → обработка до обрыва → пауза с нарастанием (0,5 с … 30 с) → заново; выход по `ctx.Done()` | `NotifyClose` с буферизованным каналом; ack старых доставок через новый канал невозможен; у публикатора outbox сам переотправит неподтверждённое |

## P-07–P-12: UUID, деньги, тесты, линтеры, PDF, конфиг

### P-07 — UUID
- **Решение:** `google/uuid`, v4, генерация в Go; `DEFAULT gen_random_uuid()` в схеме как страховка.
- **Причина:** id нужен до записи (имя файла фото, payload outbox).
- **Следствия:** override `uuid` → `uuid.UUID` в `sqlc.yaml`; переход на v7 — замена одного вызова, схема не меняется.

### P-08 — деньги
- **Решение:** `shopspring/decimal`; Postgres `numeric(12,2)`; в JSON строкой.
- **Причина:** совпадает с UML (`decimal`), читаемо в БД.
- **Следствия:**
  - адаптер `pgx-shopspring-decimal` регистрируется на каждом соединении пула (`AfterConnect`);
  - overrides в sqlc для `numeric` и nullable-`numeric` (`decimal.NullDecimal`);
  - сравнение только через `Equal`/`Cmp`, не `==`;
  - значения неизменяемы (`a.Add(b)` возвращает новое значение);
  - контракт «деньги строкой» (`"1500.50"`) обязателен для всех трёх клиентов.

### P-09 — тестирование
- **Решение:** `testify` (`assert`/`require`); моки ручные — fake-структуры с полями-функциями в `*_test.go`.
- **Причина:** поведение задаётся в каждом тесте своё; проверка компилятором; тесты безопасно параллелятся.
- **Следствия:** не используются `testify/mock` и генераторы моков — уточнение к ADR-013; интерфейсы держать маленькими (L-05).

### P-10 — линтер
- **Решение:** `golangci-lint` v2.x (минорная версия зафиксирована), `golangci-lint-action@v9`, `version: "2"` в `.golangci.yml`. Линтеры: standard (`errcheck`, `govet`, `ineffassign`, `staticcheck`, `unused`) + `errorlint`, `bodyclose`, `noctx`, `exhaustive`, `nilerr`.
- **Причина:** дополнительные линтеры закрывают конкретные места проекта: ошибки (L-06), HTTP-клиенты (Gotenberg, дашборд), `switch` по статусам и шагам саги.
- **Следствия:**
  - ADR-014 исправить: `golangci-lint-action@v6` не поддерживает golangci-lint v2;
  - `gosec` не включён (много шума);
  - `rowserrcheck`/`sqlclosecheck` не нужны — работу с `rows` пишет sqlc;
  - сгенерированный код (sqlc, oapi-codegen) исключается автоматически по заголовку `Code generated … DO NOT EDIT`.

### P-11 — PDF справки
- **Решение:** Gotenberg (HTML → PDF через headless Chromium) отдельным контейнером; `chassis/certificate` — HTTP-адаптер к нему; шаблон на `html/template`.
- **Причина:** в Go нет PDF-зависимостей; вёрстка на HTML/CSS.
- **Следствия:**
  - контейнер во внутренней сети без публикации порта (ADR-010), тег мажорной версии, healthcheck по `/health`;
  - `http.Client` с таймаутом;
  - свой TTF с кириллицей передаётся в multipart и подключается через `@font-face`;
  - сбой Gotenberg → справка `failed` → retry-воркер (D-06);
  - в тестах Orders мокается интерфейс генератора, шаблон проверяется отдельно (рендер HTML).

### P-12 — конфигурация
- **Решение:** `os.LookupEnv` + своя структура конфига, без библиотек.
- **Причина:** нет смысла тянуть библиотеку ради env.
- **Следствия:** все обязательные переменные проверяются при старте, ошибки собираются через `errors.Join`; типы разбираются в одном месте (`time.ParseDuration`, `strconv`); конфиг передаётся явно; секреты не логируются.

## P-13–P-16: валидация, фото, CORS, OpenAPI

### P-13 — валидация входа
- **Решение:** ручная: метод `Validate()` у входных DTO; общие хелперы проверок и тип ошибки валидации («поле → причина») в `chassis`.
- **Причина:** проверка компилятором, условная логика без тегов, ноль зависимостей.
- **Следствия:** все сервисы отдают ошибки валидации в одном формате (часть открытого решения №9); доменные правила (D-07) живут отдельно; поля идентичности (`owner_id`, `client_id`, роль) не принимаются из тела; `DisallowUnknownFields`.

### P-14 — обработка фото
- **Решение:** подготовка на клиенте (уменьшение, применение EXIF-поворота к пикселям, JPEG). Сервер проверяет (`MaxBytesReader`, `DetectContentType`, `DecodeConfig`) и перекодирует в JPEG без ресайза.
- **Причина:** меньше трафика и работы на сервере; разбор этого на RN.
- **Следствия:** перекодирование стирает метаданные, включая GPS; на RN проверить, что пикер применяет поворот к пикселям; в веб-клиенте то же через canvas.

### P-15 — CORS
- **Решение:** CORS не нужен: nginx отдаёт с одного origin статику (`/`) и API (`/api/` → Gateway); в разработке dev-сервер проксирует `/api`.
- **Причина:** нет разных origin — нет CORS.
- **Следствия:** ноль кода и конфигурации CORS.

### P-16 — контракт API
- **Решение:** spec-first OpenAPI 3.0.x + `oapi-codegen` v2 (`std-http-server`, strict-режим).
- **Причина:** контракт проверяется компилятором, а не дисциплиной.
- **Следствия:**
  - одна публичная спецификация; сервисы генерируют серверы из своей части (по тегам), Gateway — только для собственных эндпоинтов (дашборд);
  - префиксы путей согласуются с переписыванием в Gateway;
  - `x-go-type` для денег, `format: uuid` → `google/uuid`;
  - три слоя типов (OpenAPI DTO, sqlc, домен) с маппингом между ними;
  - рантайм-зависимость `oapi-codegen/runtime`;
  - сгенерированный код коммитится, CI проверяет дифф;
  - TS-типы для React/RN генерируются из той же спецификации;
  - валидация проксируемых запросов по спецификации в Gateway — возможное расширение.

## Фронтенд v1

- **Решение** — одно приложение React на Next.js с App Router для клиента и директора в `frontend/web/`. Приложение инженера на React Native размещается в `frontend/mobile/` в том же репозитории.
- **Причина** — файловая маршрутизация App Router и layout’ы дают привычный способ организовать два кабинета, а TypeScript позволяет явно описывать данные экранов.
- **Следствия** — в вебе `app/` содержит маршруты, страницы и layout’ы, `features/` содержит сценарии и их запросы к Gateway, `lib/api/` содержит типизированный клиент Gateway. Типы OpenAPI общие для веба и React Native и лежат в `frontend/common/api/schema.d.ts`. Оба приложения работают через Gateway. Проверка прав, бизнес-правила и хранение данных остаются в Go-бэкенде. Режим сборки и развёртывания веба определяется отдельно с учётом ADR-038.

| Задача | Решение для веба |
| --- | --- |
| Типы и интеграция | TypeScript и типизированный клиент Gateway. Типы запросов и ответов генерируются из `api/openapi.yaml`. |
| Стили и UI | Tailwind CSS и shadcn/ui. Компоненты адаптируются к макетам STO. |
| Данные Gateway | TanStack Query для загрузки, кэша, обновления после изменений и периодического чтения статуса оплаты. |
| Состояние интерфейса | `useState` для локальных значений, URL для фильтров и страницы, Zustand для общего изменяемого UI-состояния при первом подходящем сценарии. В App Router стор создаётся в клиентском провайдере нужного кабинета, отдельно для каждого экземпляра провайдера. |
| Поиск | Существующий `GET /director/orders`. Поиск по имени, телефону и госномеру, фильтрация и пагинация выполняются на Go-бэкенде с PostgreSQL. |
| Отрисовка | React-компоненты для карточек и списков, таблица shadcn/ui для строк текущей страницы. TanStack Table можно добавить при появлении сложных операций с таблицей. |

### Правила кода фронтенда

#### Имена файлов в `features/`

Название сценария задаёт папка. Внутри неё используем следующие имена:

| Файл | Ответственность |
| --- | --- |
| `view.tsx` | UI сценария, локальное состояние интерфейса и навигация. Вызывает операции из `controller` и передаёт описание формы общему рендереру, если у экрана есть форма. |
| `form.ts` или `form.tsx` | Описание полей, их порядок, группировка по строкам и валидация. `.tsx` используем, если описание содержит функции рендера с JSX. |
| `controller.ts` | Операции сценария, связанные с бэкендом. Здесь находятся вызовы Gateway, настройки TanStack Query и обновление кэша после изменений. |

Для экрана без формы достаточно `view.tsx` и `controller.ts`. Например,
после создания заявки контроллер обновляет кэш истории, а `view` открывает
карточку заказа по полученному ID.

Поиск оформляем как подпапку модуля, например
`features/director/orders/search/`. В ней используем те же имена.
`view.tsx` отображает поиск, `form.ts` или `form.tsx` описывает фильтры,
их начальные значения и преобразование в параметры запроса, а
`controller.ts` выполняет поиск через Gateway с фильтрами и пагинацией.
Для подсказок внутри обычной формы достаточно `search/controller.ts`:
он загружает варианты или фильтрует их на клиенте, а поля описывает основная форма.

Соседние модули не импортируют код друг друга. Сценарий собирает свои
подмодули, а переиспользуемый код поднимаем в `shared/` их ближайшего
общего родителя. Логику, общую для нескольких фич приложения, размещаем
в `frontend/web/common/`. Например, история заказов клиента лежит в
`customer/shared/orders/`, а провайдер сессии и `useSession` — в
`common/session/`.

При работе с несколькими сервисами разделяем контроллеры по сервисам.
Сценарий хранит собственные операции у себя, а общий запрос лежит в
подпапке сервиса внутри `shared/`. Имена вспомогательных файлов описывают
назначение модуля, например `routes.ts` для маршрутов и `form-data.ts`
для чтения данных формы.

#### Переиспользование и реализация

- Как и в Go, при добавлении похожего сценария сначала ищем существующий
  компонент, хук или функцию и по возможности переиспользуем их. Если поведение
  совпадает, а различаются данные, подписи или правила валидации, выносим общую
  часть и передаём различия через параметры. Например, поля марки и желаемой
  услуги используют одно меню подсказок, а правила заполнения задаёт каждая форма.
  Отдельную реализацию оставляем, когда обобщение заметно усложняет код.
- Утилиты, которые уже используют разные фичи, размещаем в
  `frontend/web/common/utils/` в файлах по назначению, например
  `form-data.ts`. Общие утилиты не импортируют код фич.
- Общие операции поиска и преобразования изображений принимают настройки
  от фичи. Режим поиска, ограничения файла и параметры JPEG задаёт сценарий.
- Утилиты, общие для Next.js и React Native, храним в `frontend/common/`
  по назначению. Веб импортирует их через `@shared/`. В этой папке лежат
  нормализация телефона, строковый поиск, формат рублей и подписи заказов.
- Сценарии веба получают текущую сессию и авторизованный клиент Gateway
  через `useSession`. Разбор сессии и маршруты кабинетов храним в `session.ts`.
- В `.tsx` размещаем разметку и привязку обработчиков. Модули без JSX
  пишем в `.ts`. Асинхронные
  обработчики подключаем через Promise. Импорты, состояние, обработчики и
  разметку разделяем пустыми строками.
- Декомпозицию больших функций и комментарии в сложных сценариях проверяем
  по [общим критериям ревью](../../AGENTS.md#читаемость-кода-на-ревью).
- Прямой доступ к `window` и `document` оставляем для браузерных API, например
  событий жизненного цикла вкладки. Рядом указываем, для чего он нужен.
  Внешний вид и анимации задаём через Tailwind и CSS.
- В веб-формах используем `IMaskInput` из `react-imask`. Переиспользуемые
  маски и нормализацию храним в `frontend/web/lib/forms/masks.ts`.
  Телефон в Gateway отправляется как `+7` и десять цифр. Ошибки локальной
  валидации и ошибки Gateway отображаем рядом с полем.
