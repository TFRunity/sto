# План фронтенда СТО v1

Один веб-клиент для клиента СТО и директора. Отдельное приложение React
Native для инженера. Рабочий маршрут v1 проходит от регистрации и записи до
выдачи машины, скачивания справки и поиска заказа. Для каждого экрана ниже
указан исходный макет или новая форма и отмечено, что позволяет текущий API.

[Веб клиента](web-general/web-screens.html) · [Веб директора](web-director/director-web-screens.html) · [React Native](react-native/react-native-screens.html) · [Дополнительные формы](frontend-forms.html) · [OpenAPI](../../api/openapi.yaml)

## Структура приложений

- `frontend/web/` — одно приложение Next.js с App Router. В `app/` живут маршруты, страницы и layout’ы клиента и директора. Например, `app/director/orders/[id]/page.tsx` открывает карточку заказа директора.
- Внутри `frontend/web/features/` лежат компоненты и маппинг данных для экранов по фичам. В `frontend/web/lib/api/` лежит типизированный клиент к Gateway.
- Общие типы запросов и ответов веба и React Native генерируются из `api/openapi.yaml` в `frontend/common/api/schema.d.ts`. Команда из корня проекта — `make generate-frontend-api`.
- Production-сборка веба из корня проекта — `make build-web`.
- Файлы сценариев в `features/` называем по [соглашению об именах файлов](../decisions/stack-decisions-v1.md#имена-файлов-в-features).
- `frontend/mobile/` — отдельное приложение React Native для инженера, использующее тот же контракт Gateway.

Next.js отвечает за маршрутизацию и композицию страниц. Go-бэкенд отвечает за проверку прав, бизнес-правила и хранение данных. Режим сборки и развёртывания веба выбирается отдельно с учётом ADR-038. [Решение по стеку](../decisions/stack-decisions-v1.md#фронтенд-v1).

## Порядок реализации

Подробные задачи и проверки вынесены в [вечера 1–7](../tasks/frontend/README.md).

| Шаг | Что делаем | Как принимаем |
| --- | --- | --- |
| 1. Общий вход | Веб-вход и регистрация клиента, вход инженера в RN, переход по роли, выход, обработка истёкшей сессии и ошибок API. | Клиент создаёт аккаунт, директор и инженер входят со своими учётными данными. После 401 пользователь возвращается ко входу. |
| 2. Запись и приём | Клиент добавляет ТС и записывается на сервис. Инженер видит заявку в пуле и берёт её в работу. | ID ТС и заказа совпадают у клиента и инженера. Заявка исчезает из пула после взятия, клиент видит её в истории. |
| 3. Работа и каталоги | Инженер открывает карточку, добавляет товары, услуги и фото, меняет этап. Директор управляет каталогами. | Позиции и сумма видны в заказе. Изменение цены в каталоге сохраняет цены уже добавленных позиций. Фото видно с обеих сторон. |
| 4. Оплата и выдача | Клиент запускает оплату и скачивает готовый PDF. Инженер выдаёт заказ и может отменить открытый заказ. | Показаны ожидание и откат оплаты. Выдача доступна после подтверждения. Отмена видна в истории. |
| 5. Директор и приёмка | Дашборд, поиск, фильтрация, страницы и навигация. Проверить ошибки и адаптивность. | Директор находит тот же заказ по имени, телефону и номеру ТС. Проходим полный цикл через nginx. |

Перед шагами 2–4 решаем только пробелы API, которые мешают выбранному сценарию.
Чат и отчёты относятся к v2. Восстановление пароля, настройки уведомлений и
push требуют отдельного API. Их макеты можно оставить как идеи для следующих
итераций.

## Общие экраны и состояния

| Экран или форма | Поля и действия | Связь с API |
| --- | --- | --- |
| [Вход веба](frontend-forms.html#login) и [вход RN](react-native/react-native-screens.html#render-1) | Телефон, пароль, показать пароль, войти. В вебе ссылка на регистрацию. | `POST /login`. Веб открывает область клиента или директора, RN принимает роль инженера. Ошибка входа рядом с формой. |
| [Регистрация клиента](web-general/web-screens.html#render-1) | Имя, телефон, пароль, создать аккаунт. Состояния отправки и [занятого телефона](web-general/web-screens.html#render-1b). | `POST /register`. Роль задаёт сервер. Максимум пароля — 72 байта UTF-8. |
| [Общие состояния](frontend-forms.html#states) | Загрузка, пустой результат, повтор загрузки, недоступный или удалённый объект, истёкшая сессия, отказ в доступе. | `error.fields` под полями, текст интерфейса по `error.code`. На 502/504 и ошибку сети дать повтор чтения. Отправку формы блокировать на время запроса. |

## Веб клиента

| Экран или форма | Что отрисовать |
| --- | --- |
| [Мои заказы](web-general/web-screens.html#render-3) | История от новых к старым, отдельно статус заказа и этап работ. История доступна через `GET /orders?client_id=me`. Сетка «Мои ТС» и выбор при записи загружаются через `GET /vehicles`, включая машины без заказов. |
| [Добавление ТС](frontend-forms.html#vehicle-create) | Маска российского госномера и VIN. Марка выбирается из `GET /vehicles/makes`, поиск по началу названия или синонима. Успех открывает карточку ТС. Для `plate_taken` подсказка под номером. `POST /vehicles`. |
| [Запись на сервис](frontend-forms.html#booking) | ТС, название желаемой услуги, желаемая дата и необязательный комментарий. При отсутствии выбранного ТС — переход к добавлению. Название из заявки хранится текстом и не становится оплачиваемой позицией. `POST /orders`. |
| [Карточка ТС](web-general/web-screens.html#render-4) | Марка, номер, VIN, текущая обложка, [замена обложки](frontend-forms.html#cover), галерея и просмотр снимка, история по ТС. Историю запрашиваем отдельно через `client_id=me&vehicle_id=…`. Загрузка обложки отправляет multipart с полем `photo`. |
| [Детали заказа](frontend-forms.html#customer-order) и [состояния оплаты](web-general/web-screens.html#render-3b) | Позиции, количества, цены, сумма, этап, статус. Кнопка оплаты у активного заказа. После `202` показать ожидание и перечитывать карточку. Успех — `paid` и `payment_confirmed`. Возврат в `active` возвращает кнопку. `GET /orders/{id}`, `POST /orders/{id}/pay`. |
| [Справки](web-general/web-screens.html#render-5) | Показывать действия по заказам с подтверждённой оплатой. PDF приходит из `GET /orders/{id}/certificate`. При 404 текст «Справка пока недоступна» и ручная повторная проверка. Отдельные бейджи «формируется» и «ошибка» требуют статуса справки в API. |

## React Native инженера

| Экран или форма | Что отрисовать |
| --- | --- |
| [Пул заявок](frontend-forms.html#pool) | Желаемая услуга, дата, комментарий, время заявки, карточка ТС и действие «Взять в работу». После успеха открыть заказ. `GET /orders?status=requested`, `PATCH /orders/{id}/claim`. |
| [Мои заказы](react-native/react-native-screens.html#render-2) | Активные и [завершённые](react-native/react-native-screens.html#render-2b) из `GET /engineer/orders`. Сразу после claim или создания открываются детали. При возврате список перечитывается. |
| [Прямое создание заказа](frontend-forms.html#engineer-order) | Подбор зарегистрированного клиента через `GET /engineer/clients`. Поиск по госномеру и создание ТС через `/engineer/vehicles`. Создание заказа через `POST /orders` с `vehicle_id` и `client_id`. |
| [Детали заказа](react-native/react-native-screens.html#render-3) | ТС, позиции, сумма, ответственный по `engineer_id`, статус и этап. С отдельным [ожиданием оплаты](react-native/react-native-screens.html#render-3c). Просмотр по `GET /orders/{id}`. |
| [Добавление позиции](frontend-forms.html#order-line) | Подбор товара или услуги, выбор строки из каталога, количество, подтверждение. Показать остаток товара. Цена в запрос не входит. `GET /inventory` или `GET /services`, затем `POST /orders/{id}/items` или `POST /orders/{id}/services`. |
| [Смена этапа и отмена](frontend-forms.html#order-actions) | Этапы «Принят», «В работе», «Готов», «Выдан». «Выдан» доступен при подтверждённой оплате. Отмена из `requested` или `active` с подтверждением. При конфликте перечитать заказ. |
| [Карточка ТС](react-native/react-native-screens.html#render-4) и [камера](react-native/react-native-screens.html#render-5) | Просмотр данных и галереи, разрешение на камеру, превью, переснять, отправить, ошибка и повтор. Передавать `photo` и, если снимок открыт из заказа, `order_id`. `POST /vehicles/{id}/photos`. |
| [Сессия инженера](frontend-forms.html#session) | Роль и выход. Подробный [профиль](react-native/react-native-screens.html#render-7) отрисовывать после появления источника персональных данных. |

Для просмотра защищённых фото и PDF клиент выполняет запрос с авторизацией
и показывает или скачивает полученные байты. Для загрузок сохраняем JPEG/PNG,
целимся в файл до 3 МБ и учитываем серверный предел 3,5 МиБ на весь multipart.

## Расхождения макетов и API

| Что есть в макетах | Решение для первого прохода |
| --- | --- |
| Активные и завершённые заказы инженера, история работ ТС для инженера | В v3 списки выдаются по ответственному. История ТС открывается из текущего заказа до выдачи. Оплаченный заказ до выдачи остаётся в активных. |
| Подбор клиента и ТС для прямого заказа инженера | В v3 клиент регистрируется сам. Инженер ищет клиента по имени или телефону и вводит госномер вручную. |
| Полные детали и PDF для директора, справки для инженера | В первом проходе директору доступна сводка из списка. Детали заказа разрешены клиенту и инженеру, скачивание PDF — клиенту. Дополнительный доступ требует согласования ролей. |
| Список справок и точные состояния `pending` / `failed` | Использовать оплаченные заказы и результат загрузки PDF. Отдельная выдача статусов нужна, чтобы различать ещё не готовую и окончательно не сформированную справку. |
| Имя и данные профиля после входа, все исполнители в деталях заказа | Карточка инженера получает `engineers`, ответственного отмечает по `engineer_id`. Для профиля требуется отдельное чтение. |
| Фото в карточке клиента и RN при нехватке прав или удалении | Показать заглушку изображения, сохранить переход назад и повтор чтения. |

Готовность макета проверяем для каждой формы по четырём состояниям:
начальное, заполненное, отправка, ошибка. Для списков добавляем пустой
результат. Для успешных действий фиксируем экран назначения и что
обновится после возврата на предыдущий экран.
