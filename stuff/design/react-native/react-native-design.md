# react-native-design

> Обновлено 30.10.2026 под ADR-021, 029, 030, 031, 032, 035: этап «выдан»
> после подтверждения оплаты, состояние «оплата подтверждается», справка
> автоматически (без кнопки), отмена только `requested`/`active`, ошибки
> по `code`, подготовка фото на устройстве.

Наметки экранов React Native приложения (инженеры/мастера СТО).
Это структурный каркас — иерархия блоков, состояния, размеры для
доступности — не финальный визуальный дизайн. Финальный дизайн
делается отдельно, эти наметки служат ему опорой.

## Область применения

Приложение — **только для инженеров/мастеров**. Директор и клиенты
работают через веб-сайт (отдельная разработка, не описана здесь).

## Типографика и accessibility

- Базовый размер текста интерфейса (тело, кнопки, поля ввода) — **16px**,
  соответствует стандарту доступности для мобильных приложений.
- Вспомогательный текст (метки блоков, даты, подписи) — 13-14px.
- Заголовки экранов — 17-18px.
- Решение осознанно упрощено: рассматривалось настраиваемое
  масштабирование текста/кнопок (по аналогии с индустриальными
  приложениями вроде Warehouse Management), но отклонено — проект
  сфокусирован на функционале, не на дизайне.

### Тач-таргеты
Инженеры часто работают в перчатках — основные интерактивные элементы
увеличены сверх стандартных 44px:
- Основные действия (Оплатить, Отправить, Войти) — **52px** высотой
- Второстепенные действия (Добавить товар/услугу, Переснять) — **48px**
- Мелкие элементы (стрелка назад, шеврон) — без изменений, не требуют
  точного тапа в той же степени

### Цветовая палитра
Нейтральная (нейтральные токены design system), без дополнительного
брендового акцента — осознанный выбор: инженеры часто работают в
условиях сложного освещения (мастерская, улица при осмотре ТС), где
высокий контраст важнее декоративного цвета. Цвет используется только
семантически — для статусов (success/warning/danger), не для брендинга.

## Экраны

### 1. Вход
Сервис: Users.
Телефон + пароль, кнопка "Войти" (52px), ссылка "Забыли пароль?".

### 2. Список заказов
Сервис: Orders (список + этап работ), Vehicle (данные ТС в карточке).
Табы "Активные" / "Завершённые".
- Активные: карточка — ТС, номер заказа, дата, бейдж этапа работ
  (принят / в работе / готов). Заказ `active` на этапе "готов"
  дополнительно помечается "ожидает оплаты клиентом".
- Завершённые (`paid` / `cancelled`): то же + блок справки внизу
  карточки, этап "выдан". Состояния справки (ADR-035): `completed` —
  ссылка "Справка #…"; `pending` — "Справка формируется…"; `failed`
  после 3 попыток — "Справка не сформирована — обратитесь в поддержку".

### 3. Детали заказа
Сервис: Orders + Vehicle + Inventory + Services (агрегация).
- Шапка: номер заказа, статус + переключатель этапа работ (принят /
  в работе / готов / выдан). "Выдан" недоступен, пока заказ не `paid` **и**
  склад не подтвердил оплату (сага завершена, ADR-021); при попытке —
  сервер отвечает 409, UI показывает "Выдача возможна только после
  подтверждения оплаты" (`sequence-change-work-stage`).
- Блок ТС + клиент (переход на карточку ТС).
- Блок "Товары" (из Inventory) с кнопкой добавления.
- Блок "Услуги" (из Services) с кнопкой добавления.
- Блок "Инженеры" (`order_engineers` — все исполнители; ответственный,
  `orders.engineer_id`, отмечен).
- Итоговая сумма.
- Вместо кнопки оплаты — индикатор "Ожидает оплаты клиентом": оплата
  только клиентом в вебе (решение 08.10.2026; оплата на месте вернётся
  вместе с модулем коммерческих операций, TODO §4).
- Кнопки "Сформировать справку" нет: справка создаётся автоматически при
  подтверждении оплаты (ADR-035). Внизу — подсказка "Справка сформируется
  автоматически после оплаты".
- Кнопка "Отменить заказ" — только для `requested` / `active` (сервер
  отвечает 409 на остальные, ADR-031).

**Оплата подтверждается** (заказ `paid`, сага ещё идёт, до ~10 с): вместо
индикатора "Ожидает оплаты клиентом" — "Оплата подтверждается…"; кнопок
"Добавить" и "Отменить" нет, "выдан" недоступен с подсказкой. Признак
подтверждения оплаты Orders отдаёт в карточке заказа (поле — в OpenAPI).

Для завершённого заказа (переход из истории работ ТС) — тот же формат
без индикатора оплаты и кнопок "Добавить", вместо них одна кнопка
"Открыть справку".

### 4. Карточка ТС (Vehicle)
Сервис: Vehicle.
- Данные ТС: марка, номер, VIN, владелец. Статуса у ТС нет.
- Блок **"Фотофиксация"** (не "Фото повреждений" — фото делаются не
  только при повреждениях, а как визуальная фиксация состояния ДО и
  во время работы). Сетка 3 колонки, последняя ячейка — кнопка
  добавления (пунктirная рамка).
- Блок "История работ" — кликабельные строки, ведут на экран деталей
  завершённого заказа (см. пункт 3).

### 5. Экран камеры
Сервис: Vehicle (загрузка).
Тёмный фон, верхняя панель (закрыть/вспышка, привязка к ТС в шапке),
нижний блок — превью снимка, кнопки "Переснять" / "Отправить" (48px).
Загрузка — обычный синхронный HTTP-запрос клиент → Gateway → Vehicle
(не через RabbitMQ — тот используется только между Go-сервисами).
Перед отправкой фото готовится на устройстве (ADR-029): уменьшение,
применение EXIF-поворота к пикселям, JPEG **≤ 3 МБ**. Сервер отклоняет
больше ~3,5 МБ (413) и не-JPEG/PNG — UI показывает "Не удалось загрузить
фото, попробуйте снова".

### Ошибки API (сквозное)
Сервер отдаёт ошибки конвертом `{"error": {"code", "message", "fields"}}`
(ADR-032). Тексты для инженера UI формирует сам по `code`
(`order_not_paid`, `payment_not_confirmed`, `order_not_cancellable`, …);
`message` не показывается. Ошибки полей (`fields`) — под полями формы.
Сетевые / 502 / 504 — общее "Нет связи с сервером, попробуйте ещё раз".

### 8. Профиль
Сервис: Users.
- Аватар-инициалы, имя, роль, дата начала работы.
- Переключатель push-уведомлений.
- Телефон (только отображение).
- Пункт "Поддержка" (актуален для сценария certificate: 3 неудачные
  попытки формирования справки — паузы 10 с и 1 мин — → "обратитесь в
  поддержку").
  В v1 — статический экран с контактами директора (чата поддержки нет,
  он в v2).
- Кнопка "Выйти" (`text-danger`, деструктивное действие).

**Геолокация исключена из профиля** — рассматривалась изначально,
отклонена как не нужная для сценариев приложения.

### Push-уведомления (сквозной поток, не отдельный экран)
Источник в v1: Orders ("Новый заказ #… ожидает мастера" — не "назначен
вам", так как заказы берут сами мастера, не получают по назначению).
Chat (новое сообщение) — v2.
Тап по уведомлению → диплинк на экран заказа (диалог — v2).
