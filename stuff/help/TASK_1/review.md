# Саморевью изменений вечера 3

Исходный код в коммите `2d8d35b`. Правки ниже лежат в рабочей папке. Объём работы — создать заказ, добавить товар, прочитать заказ. Для каждого замечания ниже указано, как был устроен код и что изменилось.

## 1. Gateway

Файл [gateway/internal/routes.go](../../gateway/internal/routes.go).

Раньше `handleRequest` сам искал маршрут, проверял JWT и роль, собирал контекст, обрабатывал отсутствие upstream и отправлял запрос. `decideRequest` возвращал исходный маршрут и значение перечисления, из которого использовалось только разрешение. Публичными типами `Route` и `Decision` пользовался только этот файл.

Теперь после поиска маршрута поток читается сверху вниз.

```go
request, err := authorizeRequest(r, route, secret)
if err != nil {
    httpx.WriteError(w, logger, err)
    return
}
forwardRequest(w, request, proxies[route.upstream], logger)
```

- `authorizeRequest` пропускает публичный маршрут, а для закрытого вызывает `Authenticate`, проверяет роль и добавляет идентичность в контекст.
- `decideRequest` остаётся обычной функцией. Она возвращает ошибку доступа, которую вызывающий код сразу передаёт в `WriteError`.
- `forwardRequest` отвечает за выбор между вызовом прокси и ответом `502`. Он также обрабатывает отсутствующий обработчик в таблице прокси.
- Тип `route` и его поля приватные. Для `/orders` рядом с правилом доступа указано, почему в текущем сценарии его видит инженер.

Имена внутренних заголовков лежат в [chassis/httpx/identity.go](../../chassis/httpx/identity.go). [Gateway](../../gateway/internal/proxy.go) выставляет их, а Orders читает ID по той же константе. Извлечение UUID относится к созданию заказа и остаётся в его HTTP-адаптере.

## 2. Orders HTTP и Inventory

Файлы [handler.go](../../orders/internal/order/handler.go), [response.go](../../orders/internal/order/response.go), [inventory.go](../../orders/internal/order/inventory.go).

| Было | Стало |
|---|---|
| `NewHTTPHandler` загружал спецификацию, собирал зависимости и настраивал strict-сервер. | Конструктор загружает спецификацию и связывает `newHandler`, `strictHTTPHandler` и существующий валидатор. |
| `AddOrderItem` одновременно запрашивал цену, переводил ошибки Inventory в HTTP-ответы и сохранял позицию. | `itemPrice` отвечает за получение цены и перевод ошибки. Хендлер после этого сохраняет позицию и возвращает ответ. |
| `GetOrder` строил JSON среди веток обработки ошибок. Вложенный `api.Order` содержал одноимённые поля `items` и `total`, которые перекрывались полями внешней структуры. | `orderResponse` собирает явный HTTP-ответ. По структуре сразу видны имена полей и строковый формат денег. Пустой список создаётся как `[]`. Цена этой ясности — при изменении OpenAPI придётся сверить и локальную структуру. |
| Методы ответа Orders и Inventory повторяли выставление HTTP-заголовка и JSON-кодирование. Ошибка записи могла вернуться в strict-сервер уже после отправки статуса. | Оба сервиса используют существующий `httpx.WriteJSON`. |
| Файл `service.go` содержал HTTP-клиент. Одна функция выполняла запрос и разбирала JSON. | Клиент лежит в `inventory.go`. `price` выполняет HTTP-запрос и проверяет статус, `decodeInventoryPrice` разбирает тело. |

**Исправленный баг.** Раньше цена `"1.239"` проходила проверку знака и могла сохраниться в PostgreSQL как `1.24`. Ответ при этом строился из значения до записи. Значение за пределами вместимости столбца приводило к ошибке БД. Теперь Orders принимает цену в формате из двух дробных цифр и до десяти целых, который помещается в `numeric(12,2)`. Нарушение контракта от Inventory обрабатывается как `502 upstream_error` до попытки вставки.

```go
if !inventoryPricePattern.MatchString(item.Price) {
    return decimal.Zero, errors.New("inventory price must fit numeric(12,2)")
}
return decimal.NewFromString(item.Price)
```

## 3. Репозиторий и итоговая сумма

Файлы [repository.go](../../orders/internal/order/repository.go), [order.go](../../orders/internal/order/order.go).

- При создании `create` ведёт транзакцию. `insertOrderWithEngineer` выполняет обе связанные вставки на переданном наборе запросов транзакции. Комментарий объясняет требование атомарности.
- При чтении `get` управляет последовательностью запросов, а `mapOrderItems` переводит строки БД в позиции. У `RepeatableRead` есть комментарий про единый снимок заказа, оплаты и позиций.
- При добавлении позиции один `INSERT` остаётся атомарной операцией. Обработка отсутствующего заказа привязана к конкретному внешнему ключу. Это сохраняет корректность между проверкой и вставкой без второго запроса.
- В расчёте `total` выделено промежуточное значение суммы строки. Само умножение и сложение достаточно короткие для одной функции.

## 4. Запуск сервисов и общий код

Файлы [chassis/postgres/postgres.go](../../chassis/postgres/postgres.go), [Orders main](../../orders/cmd/orders/main.go), [Inventory main](../../inventory/cmd/inventory/main.go).

Оба сервиса повторяли один блок: открыть пул, применить миграции и записать их число в журнал. Сейчас это один вызов `postgres.ConnectAndMigrate`. Общая функция закрывает пул при ошибке миграции и передаёт владение готовым пулом вызывающему коду при успехе. В `main` остаются конфигурация, подключение зависимостей и запуск HTTP.

Конфиги зависимостей и `go.sum` сверены в составе сборки контейнеров. Файл `orders/migrations/embed.go` уже состоял из объявления встроенных миграций и поясняющего комментария.
