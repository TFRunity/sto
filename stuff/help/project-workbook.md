# Практикум по бэкенду СТО

Напарник, берём один маршрут и идём по нему до базы. Потом сами прикинем,
как добавить новый. Если застрял, открывай указанные файлы по порядку.
Ответ под каждой задачей можно оставить закрытым до первой попытки.

## Как подготовить новый маршрут к генерации

Возьмём готовый пример. Инженер вызывает `PATCH /orders/{id}/claim` и
берёт заявку в работу. Вот что я готовлю перед тем, как ты сядешь за Go.

1. **Записываю поведение.** Какая роль вызывает маршрут? Что меняется в базе?
   Что получит клиент при ошибке? Для claim нужны статус заказа, ответственный
   и список исполнителей. Они уже есть. Если для другой задачи понадобится
   колонка, добавлю новую миграцию и учту старые строки.
   [Миграция Orders](../orders/migrations/00001_orders.sql)
2. **Описываю маршрут в OpenAPI.** У claim есть метод `PATCH`, ID в пути,
   возможные ответы, тег `orders` и `operationId: claimOrder`. По тегу
   генератор выбирает сервис, а по `operationId` называет Go-метод.
   Смотрю в Gateway, проходит ли запрос с нужной ролью. Здесь правило для
   инженера уже есть.
   [OpenAPI](../api/openapi.yaml) · [Настройки генератора](../orders/oapi-codegen.yaml) · [Gateway](../gateway/internal/routes.go)
3. **Готовлю SQL.** Один запрос назначает ответственного, второй добавляет
   его в список исполнителей. У первого стоит `:execrows`, чтобы Go узнал,
   сколько строк изменилось. Ноль строк — повод выяснить, существует ли
   заказ и можно ли его взять. Оба запроса записи выполняются в одной
   транзакции.
   [SQL Orders](../orders/queries/orders.sql)
4. **Выбираю команду из корня.** Для этого примера подходит
   `make generate MODULE=orders`. Make запускает sqlc, затем oapi-codegen.
   sqlc читает миграции и запросы, обновляет `orders/internal/db/`.
   oapi-codegen читает OpenAPI, обновляет `orders/internal/api/api.gen.go`.
   Генерация пишет Go-файлы. База и Docker для неё не нужны. Как агент я
   запускаю команду после твоего разрешения.
   [Makefile](../Makefile)
5. **Смотрю, что получилось.** В HTTP-адаптере ищу сигнатуру хендлера
   `ClaimOrder`, в SQL-адаптере — запрос `ClaimOrder` с результатом
   `(int64, error)`. Если тип удивил, возвращаюсь к YAML или SQL и правлю
   источник. Тебе передаю сигнатуру хендлера, запросы и ожидаемые ответы.
   Дальше ты связываешь их Go-кодом.
   [HTTP-адаптер](../orders/internal/api/api.gen.go) · [SQL-адаптер](../orders/internal/db/orders.sql.go)

**Твоя очередь.** На бумаге подготовь `GET /vehicles` со списком машин
текущего клиента. Запиши имя операции, имя SQL-запроса, фильтр и команду
генерации. Реши, где разрешить маршрут клиенту.

<details>
<summary>Сверить ответ</summary>

Добавь `get` под `/vehicles`, тег `vehicle`, имя `listVehicles` и ответ
200 с массивом. Запрос можно назвать `ListVehiclesByOwner :many`.
Он принимает ID клиента, выбирает его машины с `deleted_at IS NULL`
и задаёт порядок строк. Колонки уже есть. Доступ клиента добавляется в
`vehicleRoles`. Команда — `make generate MODULE=vehicle`. После неё
в Go появятся метод хендлера `ListVehicles` и SQL-метод, который возвращает
срез и ошибку. Для клиента пустой список должен выглядеть как `[]`.
[Таблица ТС](../vehicle/migrations/00001_vehicles.sql) · [SQL Vehicle](../vehicle/queries/vehicles.sql)

</details>

## 1. Проведи запрос до базы

Возьми `POST /api/vehicles`. Найди, откуда берётся ID владельца и что
происходит с номером перед вставкой в базу. Затем реши, какой ответ будет,
если последовательно отправить `a123bc77` и `А123ВС77` для двух новых машин.

Где копать. Начни с `CreateVehicle` и перейди в `prepareVehicleDetails`.
[Хендлер](../vehicle/internal/handler.go) · [Нормализация](../vehicle/internal/vehicle.go) · [Миграция](../vehicle/migrations/00001_vehicles.sql)

<details>
<summary>Сверить ответ</summary>

ID владельца приходит из идентичности в контексте запроса. Оба номера
превращаются в одну строку. При свободном номере первый запрос получает
201. Второй упирается в уникальный индекс и получает 409 `plate_taken`.

</details>

## 2. Поймай момент, когда один сервис зовёт другой

Клиент создаёт заявку через `POST /api/orders`. Найди место, где Orders
проверяет машину в Vehicle. Запиши, будет ли вставка заявки в каждом из
трёх случаев: машина своя, машина чужая, Vehicle недоступен.

Где копать. Открой `createServiceBooking`, затем `requireVehicleOwner`.
[Хендлер заявки](../orders/internal/order/booking.go) · [Вызов Vehicle](../orders/internal/order/vehicle.go)

<details>
<summary>Сверить ответ</summary>

Orders берёт ID клиента из контекста, ID машины из тела запроса и передаёт
оба в Vehicle. Своя машина — заявка записывается. Чужая — 404
`vehicle_not_found`. Vehicle недоступен — 502 `upstream_error`.
В двух последних случаях до вставки дело не доходит.

</details>

## 3. Проследи, кто отвечает за заказ

Инженер А берёт заявку через `PATCH /api/orders/{id}/claim`. Потом повторяет
запрос. Затем эту же заявку берёт Б. После каждого шага запиши статус,
ответственного и список исполнителей. Что будет, если обновление заказа
прошло, а добавление исполнителя вернуло ошибку?

Где копать. Найди `claim` в репозитории, потом два запроса из этого метода.
[Репозиторий](../orders/internal/order/repository.go) · [SQL](../orders/queries/orders.sql)

<details>
<summary>Сверить ответ</summary>

После первого запроса статус `active`, ответственный А, в списке А.
Повтор сохраняет те же значения. После запроса Б статус остаётся `active`,
ответственный Б, в списке А и Б. Если вставка исполнителя падает, транзакция
откатывает и обновление заказа.

</details>

## 4. Разложи оплату по шагам

Нарисуй три колонки: Orders, RabbitMQ, Inventory. Проведи оплату заказа
с одной позицией от HTTP 202 до подтверждения. Потом поменяй одно условие:
Inventory списал товар, но успех пришёл после дедлайна. Кто возвращает заказ
в работу и кто возвращает товар?

Где копать. Проследи `StartPayment`, отправку из outbox и `RunDeadlines`.
[Старт](../orders/internal/saga/handler.go) · [Отправка](../chassis/outbox/outbox.go) · [Дедлайн](../orders/internal/saga/deadline.go) · [Списание и возврат](../inventory/internal/stock/repository.go)

<details>
<summary>Сверить ответ</summary>

К моменту принятия оплаты заказ становится `paid`, попытка ждёт списания,
а команда записана в outbox, таблицу исходящих сообщений. Воркер отправляет
её через RabbitMQ. Inventory списывает товар и отвечает. Когда Orders
применяет успех, попытка становится `completed` и оплата считается
подтверждённой.

После дедлайна Orders пропускает поздний успех, возвращает заказ в `active`
и отправляет команду отмены. Inventory по ID попытки находит своё списание
и возвращает товар. Если команда списания приходит повторно после успешного
списания, Inventory повторяет ответ и сохраняет остаток.

</details>

## 5. Напиши один тест на Go

Вот и код, напарник. Сделай `TestReplyStep` в пакете `saga`. Возьми форму
таблицы из теста Vehicle. Для начала хватит трёх случаев: успех во время
ожидания, отказ во время ожидания и повторный успех после завершения.

Где копать. У каждой строки таблицы укажи текущий шаг, событие и ожидаемый
результат. Для проверки подходит `make test MODULE=orders`.
[Функция оплаты](../orders/internal/saga/saga.go) · [Тест Vehicle](../vehicle/internal/vehicle_test.go)

<details>
<summary>Сверить ответ</summary>

Успех из `verifying_stock` даёт `completed`, отказ — `failed`, повторный
успех из `completed` даёт пустую строку. Функции хватает двух входных строк.
Дедлайн проверяется при записи перехода в PostgreSQL.
[SQL переходов](../orders/queries/saga.sql)

</details>
