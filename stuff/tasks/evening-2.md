## [x] 2. Проверка JWT

Нужно написать в `gateway/internal/auth.go` функцию, которая разбирает токен из заголовка
`Authorization: Bearer …` и возвращает id пользователя и роль, чтобы дальше Gateway знал,
кто пришёл.
Используя `golang-jwt/jwt/v5` (подключим перед задачей): `jwt.Parse` с
`WithValidMethods([]string{"HS256"})` и `WithExpirationRequired()` (ADR-023).

Токен выпускает Users (вечер 1, задача 7): `sub` — id, `role` — роль, `exp` — срок.
Нет заголовка, битый токен, чужая подпись, истёк, нет `exp` → одна ошибка
`401 unauthorized` в конверте (ADR-032). Что именно не так — только в лог (debug).

**Проверка:** `curl` в задаче 5 — с токеном из `/login` проходит; без токена, с мусором,
с токеном, подписанным другим секретом → 401. Тестов нет: проверку делает библиотека,
наша часть — вызов с опциями.

**Подумай:** зачем `WithValidMethods`, если секрет и так знаем только мы, — что будет
с токеном, у которого в заголовке `"alg": "none"`?

## [x] 3. Таблица маршрутов и роли

Нужно написать в `gateway/internal/routes.go` таблицу «префикс пути → сервис + допустимые
роли» и функцию решения «пускать или нет», чтобы правила доступа жили в одном месте и по
принципу deny-by-default: маршрута нет в таблице — отказ (ADR-019, ADR-022).
Используя только stdlib.

Таблица недели 1:

| Префикс | Сервис | Кто |
|---|---|---|
| `/register`, `/login` | users | все, без токена (публичные) |
| `/orders` | orders | `engineer`, `client` (точнее — в вечере 3, когда появятся пути Orders) |

Решение — чистая функция: (путь, есть ли токен, роль) → пустить / 401 / 403. Неизвестный
путь → `403 forbidden` (ADR-022), роль не подходит → `403`, токена нет на закрытом → `401`.

**Автоматические тесты Gateway для вечера 2 отменены по решению разработчика.**

**Подумай:** префикс `/orders` — пропустит ли наивное `strings.HasPrefix` путь
`/orders-admin`? Как сравнивать по границе сегмента.

## [x] 4. Прокси

Нужно написать в `gateway/internal/proxy.go` прокси в сервис, который собирает исходящий
запрос заново, чтобы до сервиса доходили только разрешённые заголовки и идентичность,
выставленная самим Gateway (ADR-037).
Используя `net/http/httputil.ReverseProxy` с полем `Rewrite` (не `Director`).

Исходящий запрос:
- из входящих заголовков — только `Content-Type`, `Accept`, `Accept-Language`;
- `X-User-Id`, `X-User-Role` — из токена (задача 2); на публичном маршруте — не ставятся;
- `X-Request-Id` — новый UUID; присланный клиентом игнорируется;
- `Authorization` вниз не уходит.

Ошибки: ответы сервиса (в том числе 4xx/5xx) — как есть; сервис недоступен → `502`,
не ответил вовремя → `504` — конвертом, через `ErrorHandler` прокси (ADR-032).

**Проверка:** вместо Orders агент поднимает echo-сервер, который возвращает полученные
заголовки (запуск — с «можно»). `curl` с токеном инженера и подложенными
`X-User-Role: director`, `X-Request-Id: 1`, `Cookie: a=b` → echo видит роль `engineer`,
свой UUID, нет `Cookie` и `Authorization`. Echo остановлен → `502`. Тестов нет: обвязка.

**Подумай:** чем `Rewrite` безопаснее `Director` — что `ReverseProxy` делает с
заголовками до вызова `Rewrite` и чего не может гарантировать с `Director`.

## [x] 5. Сборка Gateway и проверка через nginx

Задача закрыта по сообщению разработчика. Код Gateway местами отличается от плана ниже.

Нужно собрать в `main.go` цепочку «проверка токена и роли → прокси нужного сервиса»,
чтобы весь путь клиент → nginx → Gateway → Users работал в Docker Compose.
Используя задачи 1–4 и `make up` (ADR-038).

**Проверка (итог вечера):** `make up SVC="gateway users"` (с «можно»), затем через
`http://sto.localhost/api`:
- `POST /register` → 201 с токеном; `POST /login` инженером из seed → 200;
- `GET /orders` без токена → 401; с токеном клиента и чужой ролью в заголовке → роль
  берётся из токена;
- неизвестный путь → 403;
- Users не отвечает (`make stop SVC=users`) → 502 в конверте.

**Подумай:** где в цепочке ставить проверку токена — над всем mux или внутри каждого
маршрута — чтобы новый маршрут нельзя было случайно оставить открытым.
