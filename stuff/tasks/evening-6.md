# Вечер 6 — задачи

**Итог вечера:** `scripts/e2e.sh` проходит оба пути: успешная оплата заканчивается
скачиванием PDF-справки; при остановленном Inventory через ~10 с сага `failed`, заказ снова
`active`, а поднятый Inventory получает `CancelStock` и ничего лишнего не списывает.

Задачи идут по порядку — каждая опирается на предыдущие. После каждой — ревью.
Отмечай сделанное: `[ ]` → `[x]`.

Схемы: `sequence-pay-order` (шаги 19–23), `sequence-certificate`,
`sequence-download-certificate`; ADR-030, ADR-035, ADR-027.

**Перед вечером — агент:** `GET /orders/{id}/certificate` (`200 application/pdf`, 404) в
`api/openapi.yaml`; запросы sqlc для дедлайнов и справок; HTML-шаблон справки и TTF с
кириллицей (этап 0, п. 8); `scripts/e2e.sh` (п. 9).

Вечер плотный. Если не успеваешь — **линия отреза 2** (`PLAN.md`): задачи 4–7 (справка)
переезжают на неделю 2, цель недели сужается до саги.

## [x] 1. Inventory: `CancelStock`

Нужно добавить в обработку команд Inventory ветку `CancelStock`, чтобы отмена саги
возвращала списанное и не зависела от порядка доставки (ADR-030, шаги 22–23).
Используя `decide` из вечера 5 (таблица уже покрывает `CancelStock`), условные `UPDATE`.

Одна транзакция:
- `deducted` → по `stock_attempt_items` вернуть остатки (`quantity = quantity + N`),
  попытка → `cancelled` (условно: `WHERE state = 'deducted'`);
- попытки нет → `INSERT stock_attempts (state = 'cancelled')` — tombstone;
- `rejected` / `cancelled` → ничего.

Ответа на отмену нет — outbox не пишется.

**Проверка:** в задаче 7. Тестов нет: решения уже в `decide`.

**Подумай:** в `stock_attempts` колонка `order_id NOT NULL`, хотя ключ — `saga_id`. Откуда
взять `order_id` для tombstone и зачем он там вообще?

## [x] 2. Orders: воркер дедлайнов

Нужно написать в `orders/internal/saga/deadline.go` воркер, который раз в ~1 с находит
просроченные саги и откатывает их, чтобы сага никогда не висела дольше 10 с + тик (ADR-030,
шаги 19–21).
Используя `time.NewTicker`, `select` по `ctx.Done()`, `:execrows`, `chassis/outbox`.

- `SELECT saga_id, order_id FROM saga_state WHERE current_step = 'verifying_stock' AND
  deadline < now()` — индекс `idx_saga_state_deadline` уже есть;
- на каждую сагу — **своя** транзакция: условный переход в `failed` → 1 строка →
  `UPDATE orders SET status = 'active' WHERE id = $1 AND status = 'paid'` + outbox
  `CancelStock {saga_id, order_id}`; 0 строк → консьюмер успел раньше, пропустить;
- ошибка одной саги — лог и дальше, воркер не падает.

**Проверка:** в задаче 7. Тестов нет: SQL-оркестрация; переходы саги — под тестом вечера 5.

**Подумай:** почему транзакция на каждую сагу, а не одна на всю пачку?

## [x] 3. Orders: правило повтора справки

Нужно написать в `orders/internal/certificate/certificate.go` чистую функцию «сколько
попыток сделано + результат + сейчас → новый статус, `attempts` и `next_attempt_at`», чтобы
вся политика повторов была закрыта тестом (ADR-035, D-06, D-07).
Используя `time.Time`, `time.Duration`.

- всего **3** попытки, включая первую;
- успех → `completed`, `next_attempt_at = NULL`;
- неудача: после 1-й → `failed`, пауза 10 с; после 2-й → `failed`, пауза 1 мин; после 3-й
  → `failed` окончательно, `next_attempt_at = NULL`.

**Проверка:** табличный тест `certificate_test.go`: успех на 1/2/3-й попытке, неудача на
1/2/3-й; время — параметр функции, не `time.Now()` внутри.

**Подумай:** почему `now` передаётся параметром — что иначе пришлось бы делать в тесте?

## [x] 4. `chassis/certificate`: адаптер Gotenberg

Нужно написать в `chassis/certificate` функцию «файлы (index.html + шрифт) → PDF», чтобы
Orders получал PDF одним вызовом и ничего не знал о multipart (ADR-027).
Используя `mime/multipart` (`multipart.NewWriter`, `Writer.CreateFormFile("files", имя)`,
`Writer.FormDataContentType`), `bytes.Buffer`, `http.NewRequestWithContext`,
`http.Client{Timeout: …}`, `io.ReadAll`.

`POST {GOTENBERG_URL}/forms/chromium/convert/html`, поле `files`, главный файл **обязательно**
`index.html`; шрифт — в том же запросе, в `@font-face` — по имени файла, без каталогов
(Gotenberg кладёт файлы плоско). Не `200` или таймаут → ошибка (попытка неудачна).

Сигнатура интерфейса генератора не решена (`TODO.md` §5) — она за тобой.

**Проверка:** в задаче 7. Тестов нет: HTTP-обвязка; в тестах Orders генератор мокается
(ADR-027).

**Подумай:** где лежат шаблон и шрифт — в `chassis` или в Orders? `chassis` должен знать
«шаблон + данные → PDF», но не маппинг справки (ADR-027).

## [x] 7. Скачивание справки и `e2e.sh`

Нужно написать хендлер `GET /orders/{id}/certificate` и подключить воркеры в `main.go`
Orders, чтобы агентский `e2e.sh` прошёл оба сценария (`sequence-download-certificate`,
`PLAN.md` — критерий готовности недели).
Используя strict-ответ `application/pdf` из `orders/internal/api`, воркеры задач 2 и 6.

Отдаётся только `completed` — PDF из базы, не пересобирается. Нет справки или не
`completed` → 404 в конверте (код согласуй с агентом в OpenAPI, ADR-032).

**Проверка (итог вечера):** `scripts/e2e.sh` (с «можно»):
- **успех:** регистрация → заказ → товары → оплата → `completed` → справка `completed` →
  `GET /orders/{id}/certificate` отдаёт PDF, кириллица читается;
- **дедлайн:** `make stop SVC=inventory` → оплата → через ~11 с заказ `active`, сага
  `failed`; `make up SVC=inventory` → `CancelStock` доставлен, в `stock_attempts` —
  tombstone `cancelled`, остаток не изменился.

**Подумай:** во втором сценарии сначала придёт `DeductStock`, потом `CancelStock` — или
наоборот? Почему результат одинаковый (ADR-030, «не зависит от порядка доставки»).
