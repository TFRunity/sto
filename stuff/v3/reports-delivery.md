# Обмен данными Reports

## Сообщения

Reports создаёт запрос со статусом `pending` и команды для нужных источников
в одной транзакции. AMQP `MessageId` равен ID записи outbox, `Type` задаёт вид
сообщения, тело передаётся в JSON. Топология объявлена в Compose.

| AMQP `Type` | Exchange | Ключ маршрутизации и очередь |
| --- | --- | --- |
| `ReportDataRequested` для Orders | `reports_commands` | `orders.reports_commands` |
| `ReportDataRequested` для Users | `reports_commands` | `users.reports_commands` |
| `ReportDataProvided` | `reports_replies` | `reports.data` |

В команде обязательны `request_id` (UUID), `attempt` (целое от 1 до 3),
`report_type` (`revenue`, `engineers`, `certificates_orders`),
`period_from`, `period_to` и `expires_at` (RFC 3339).
Границы периода: начало включено, конец исключён. Reports переводит
пользовательские даты в эти границы в согласованном часовом поясе.

В ответе обязательны `request_id`, `attempt`, `source` (`orders` или `users`),
`report_type` и `rows`. Один ответ содержит весь набор строк источника,
включая пустой список. ID в строках передаются как UUID, даты и отметки времени —
в ISO 8601, деньги — десятичными строками. Версия набора полей совпадает с
описанным ниже `report_type`.

## Данные по типам

| Тип | Orders | Users |
| --- | --- | --- |
| `revenue` | `order_id`, `paid_at`, `total_amount` для оплаченных заказов с `paid_at` в периоде | — |
| `engineers` | `order_id`, `engineer_ids` из `order_engineers`, `created_at`, `paid_at`, `status`, `total_amount`. Кандидаты имеют создание или подтверждение оплаты в периоде | `engineer_id`, `role`, `work_started_at` для текущих инженеров и исторических записей с пересечением периода работы. Границу для удалённых даёт `deleted_at` |
| `certificates_orders` | `order_id`, `created_at`, `status`, `stage`, `certificate_id`, `certificate_status`, `certificate_created_at`. Кандидаты имеют создание заказа или справки в периоде. Без справки её поля равны `null` | — |

Orders вычисляет `total_amount` из количеств и сохранённых цен товаров и
услуг заказа. Поля `paid_at` и `work_started_at` допускают `null`.
При необходимости Reports дополняет строки сотрудников именами через
внутреннее чтение Users по ID, затем сохраняет их в снапшоте. Сообщения outbox
содержат только идентификаторы и данные для вычислений.
Правила разбивки по дням, учёта старых заказов и распределения выручки между
исполнителями остаются в [вечере 6](../tasks/v3/evening-6.md).

## Дедлайн и повтор

Предложенные значения для первого запуска — 30 секунд от коммита каждой
попытки, максимум три попытки, включая первую. Параметры фиксируются для
запроса при создании. Дедлайн включает ожидание публикации при недоступном
брокере. Источник пропускает просроченную команду и подтверждает доставку.

Ключ обработки команды у источника — `(request_id, attempt)`. Источник
сохраняет факт обработки и ставит ответ в outbox одной транзакцией.
Повтор той же команды не создаёт второй ответ. Ack отправляется после коммита.

Reports принимает ответ только для ожидаемого источника, типа и текущей
попытки источника, пока запрос в `pending` и дедлайн не истёк.
Для сохранённых ответов уникален ключ `(request_id, source)`. По таймауту
Reports сохраняет уже принятые ответы и ставит команды только для недостающих
источников с новым `attempt`. Когда пришли все ответы, Reports атомарно
сохраняет итоговый снапшот и переводит запрос в `received`. Если истекла
третья попытка, условный переход переводит запрос в `failed`.
Повторы и опоздавшие ответы подтверждаются без записи.
