# Обмен данными Reports

## Сообщения

Reports создаёт запрос со статусом `pending` и команды для нужных источников
в одной транзакции. AMQP `MessageId` равен ID записи outbox, `Type` задаёт вид
сообщения. JSON-тело описано [схемой](reports-messages.schema.json).
Топология объявлена в Compose.

| AMQP `Type` | Exchange | Ключ маршрутизации и очередь |
| --- | --- | --- |
| `ReportDataRequested` для Orders | `reports_commands` | `orders.reports_commands` |
| `ReportDataRequested` для Users | `reports_commands` | `users.reports_commands` |
| `ReportDataProvided` | `reports_replies` | `reports.data` |

При подключении обработчиков маршрут должен определяться для каждой записи
outbox. У двух команд `ReportDataRequested` одинаковый `Type`, поэтому
назначение Orders или Users сохраняется вместе с записью outbox. Orders
публикует ответы Reports и команды саги в разные маршруты. Текущая обвязка
`chassis/outbox` использует один маршрут на воркер и читает все записи
из outbox сервиса. Подключение требует явной маршрутизации сообщений.

В команде обязательны `request_id` (UUID), `attempt` (целое от 1 до 3),
`report_type` (`revenue`, `engineers`, `certificates_orders`),
`period_from`, `period_to` и `expires_at` (RFC 3339).
Границы периода включают начало и исключают конец. Reports переводит
пользовательские даты в полночь соответствующего дня с локальным смещением
в обеих границах. `period_from < period_to` проверяется по времени.
Users берёт `period_end_date` из календарной даты `period_to` с исходным
смещением до перевода времени в UTC. Команды Users допустимы для `engineers`.

В ответе обязательны `request_id`, `attempt`, `source` (`orders` или `users`),
`report_type` и `rows`. Один ответ содержит весь набор строк источника,
включая пустой массив. ID в строках передаются как UUID, даты и отметки времени —
в ISO 8601, деньги — десятичными строками с двумя знаками после точки.
При сборке ответа пустой результат sqlc преобразуется в `rows: []`.

## Данные по типам

| Тип | Orders | Users |
| --- | --- | --- |
| `revenue` | `order_id`, `paid_at`, `total_amount` для оплаченных заказов с `paid_at` в периоде | — |
| `engineers` | `order_id`, `engineer_ids` из `order_engineers`, `created_at`, `paid_at`, `status`, `total_amount`. Кандидаты имеют создание или подтверждение оплаты в периоде | `engineer_id`, `role`, `work_started_at` для инженеров, которые начали работу до конца периода либо у которых дата начала неизвестна. Удалённый инженер входит в выборку, если удаление произошло после начала периода |
| `certificates_orders` | `order_id`, `created_at`, `status`, `stage`, `certificate_id`, `certificate_status`, `certificate_created_at`. Кандидаты имеют создание заказа или справки в периоде. Без справки её поля равны `null` | — |

Orders вычисляет `total_amount` из количеств и сохранённых цен товаров и
услуг заказа. Поля `paid_at` и `work_started_at` допускают `null`.
[Запросы Orders](../../orders/queries/reports.sql) ·
[Запросы Users](../../users/queries/reports.sql)

При необходимости Reports дополняет строки сотрудников именами через
внутреннее чтение Users по ID, затем сохраняет их в снапшоте. Сообщения outbox
содержат только идентификаторы и данные для вычислений.
Правила разбивки по дням, учёта старых заказов и распределения выручки между
исполнителями остаются в [вечере 6](../tasks/v3/evening-6.md).

## Дедлайн и повтор

Значения по умолчанию для первого запуска — 30 секунд на попытку и максимум
три попытки, включая первую. Параметры фиксируются для запроса при создании.
`expires_at` выставляется от времени записи команд в транзакции.
Дедлайн включает ожидание публикации при недоступном
брокере. Источник пропускает просроченную команду и подтверждает доставку.

Ключ обработки команды у источника — `(request_id, attempt)`. Источник
сохраняет факт обработки и ставит ответ в outbox одной транзакцией.
Повтор той же команды не создаёт второй ответ. Ack отправляется после коммита.

Reports принимает ответ только для ожидаемого источника, типа и текущей
попытки источника, пока запрос в `pending` и дедлайн не истёк.
Для сохранённых ответов уникален ключ `(request_id, source)`. По таймауту
Reports сохраняет уже принятые ответы и ставит команды только для недостающих
источников с новым `attempt`. Когда пришли все ответы, Reports атомарно
сохраняет итоговый снапшот и переводит запрос в `received`. Если истекла
последняя попытка, условный переход переводит запрос в `failed`.
Обработчик ответа и воркер таймаута конкурируют за одну строку запроса.
Метод репозитория начинает транзакцию и использует условный `UPDATE` по
статусу `pending`, ожидаемой попытке и её дедлайну, согласно
[ADR-031](../adr/architecture/ADR-031-transactions-and-domain-rules.md).
При нуле обновлённых строк метод завершает обработку без побочных записей.
Сохранение ответа, постановка команды на повтор или запись снапшота идут
в той же транзакции. Дедлайн сравнивается с текущим временем БД
(`clock_timestamp()`). Ровно в `expires_at` попытка уже истекла.
Повторы и опоздавшие ответы подтверждаются без записи.

## Пример повтора по одному источнику

Для отчёта `engineers` Reports отправляет команды с `attempt: 1` в Orders и
Users. Если Orders ответил вовремя, а Users пропустил дедлайн, Reports
сохраняет ответ Orders и отправляет команду с `attempt: 2` только в Users.
Запоздавший ответ Users с `attempt: 1` подтверждается без записи.
Ответ Users с `attempt: 2` завершает запрос, даже если его `rows` пуст.
