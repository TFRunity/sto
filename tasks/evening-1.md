# Вечер 1 — задачи

**Итог вечера:** Users запускается (`make infra`, потом `make run SVC=users`), и через
`curl` на `http://127.0.0.1:8081` работают регистрация и вход.

Задачи идут по порядку — каждая опирается на предыдущие. После каждой — ревью.
Отмечай сделанное: `[ ]` → `[x]`.

---

## [x] 1. Конфигурация

Нужно написать в `chassis/config` общую функцию загрузки конфига и описать структуру
конфига Users, чтобы сервис при старте сразу видел **все** недостающие переменные одним
сообщением и дальше работал с готовыми типами, а не с `os.Getenv` по коду.
Используя `caarlos0/env/v11` (уже подключена) и теги `env:"…"` / `envDefault:"…"`.

У Users пять переменных: `HTTP_ADDR`, `DATABASE_URL`, `JWT_SECRET`, `JWT_TTL`
(по умолчанию `168h`) и `LOG_LEVEL` (по умолчанию `info`).
`JWT_SECRET` и `DATABASE_URL` — `notEmpty`, а не `required`: `required` пропустит пустое
значение. Оба — секреты, в лог они попасть не должны.

**Проверка:** `make run SVC=users` с `.env`, где закомментирован `JWT_SECRET`, печатает
недостающую переменную (`HTTP_ADDR` и `DATABASE_URL` подставляет сам Makefile, а без
`.env` упадёт шелл, до Go не дойдёт). Тестов нет: конфиг — не бизнес-логика (ADR-013),
проверяется запуском.

**Подумай:** каким типом сделать `JWT_SECRET`, чтобы его нельзя было случайно
напечатать (`slog.LogValuer`).

## [x] 2. Логгер

**Проверка:** при `make run` видна JSON-строка старта с `service=users` и без секретов;

**Подумай:** логгер передавать явно в конструкторы или сделать глобальным
(`slog.SetDefault`) — и как тогда подменять его в тестах.

## [ ] 3. Конверт ошибок

Нужно написать в `chassis/httpx` тип ошибки API и функцию записи JSON-ответа, чтобы
любой сервис отвечал ошибкой в одном формате `{"error": {"code", "message", "fields"}}`,
а внутренние детали (цепочка `%w`, текст Postgres) уходили только в лог.
Используя `errors.As`, `encoding/json`, `net/http` (ADR-032).

Наш тип ошибки → его статус и `code`; любая чужая ошибка → `500 internal_error` без её
текста в ответе.

**Проверка:** запуском в задаче 8 — `409 phone_taken` приходит в конверте; при
остановленной `users-db` регистрация отвечает `500 internal_error` без текста Postgres,
а сам текст виден в логе. Тестов нет: обвязка, не бизнес-логика (ADR-013).

**Подумай:** домен Users должен знать HTTP-статусы или возвращать свою ошибку
(`ErrPhoneTaken`), которую в статус превращает хендлер?

## [x] 4. HTTP-сервер и остановка

Нужно написать в `chassis/httpx` запуск HTTP-сервера с `/healthz` и корректной
остановкой, чтобы по `Ctrl+C` / `docker compose stop` сервис дожидался текущих запросов
и выходил, а остальной код (позже — воркеры) узнавал об остановке через контекст.
Используя `net/http` (`Server`, `Shutdown`) и `os/signal` (`NotifyContext`).

`/healthz` всегда отвечает `200` — только «процесс жив» (ADR-038).
Задай таймауты сервера, хотя бы `ReadHeaderTimeout`.

**Проверка:** `curl 127.0.0.1:8081/healthz` → 200; `Ctrl+C` — сервис выходит с кодом 0;
порт занят — понятная ошибка.

**Подумай:** `http.ErrServerClosed` — это ошибка или нормальный исход?

## [ ] 5. Валидатор запросов

Нужно написать в `chassis/httpx` middleware, проверяющий запрос по `api/openapi.yaml`, и
обработчик ошибок strict-сервера, чтобы лишние поля, пропущенные обязательные и битый
JSON отклонялись ответом `400 validation_failed` в нашем конверте ещё до хендлера.
Используя `oapi-codegen/nethttp-middleware` (подключена) и встроенную
спецификацию `api.GetSwagger()` (ADR-041).

Два нюанса: `DoNotValidateServers: true` (обнуляет `Servers` — сервис видит путь без
`/api`); аутентификацию в валидаторе выключить (`NoopAuthenticationFunc`: JWT проверил
Gateway). Текст ошибки kin-openapi клиенту не отдавать — в нём может быть значение поля
(пароль).

Минимум (правило «сначала работает, потом лучше»): `fields` пока не заполняем — ответ
`400 validation_failed` без указания поля. Улучшение на потом: первая (или все, `MultiError`)
ошибка схемы → `fields` «поле → причина».

**Проверка:** `curl` в задаче 8 — лишнее поле → 400 `validation_failed`, нет обязательного
→ 400, корректный запрос доходит до хендлера, `/healthz` по-прежнему 200. Тестов нет:
обвязка, не бизнес-логика (ADR-013).

**Подумай:** как не дать валидатору отклонить `/healthz`, которого нет в спецификации.

## [ ] 6. Users: база и миграции

Нужно подключить Users к Postgres и применять миграции при старте, написать репозиторий
поверх сгенерированного sqlc-кода, чтобы при запуске появлялись таблица и сотрудники из
seed, а наружу из репозитория выходили доменный пользователь и доменные ошибки.
Используя `pgxpool`, `pressly/goose/v3` (подключим перед задачей), `go:embed`,
`users/internal/db`.

Занятый телефон (Postgres `unique_violation` по `uq_users_phone`) → `ErrPhoneTaken`;
«не найден» → своя ошибка вместо `pgx.ErrNoRows`. Роль из строки → доменный тип.

Подключение и миграции — в `chassis/postgres` (`Connect` с таймаутом `Ping`, `Migrate`):
базы есть у трёх сервисов. `DBTX` / `WithTx` из ADR-024 пока не нужны — у Users нет
транзакций и outbox.

**Проверка:** `make run` применяет миграции, повторный запуск — «нет новых»; в БД есть
инженер и директор с непустым хешем; при остановленной `users-db` — ошибка за 5 секунд,
а не зависание. Тестов нет: маппинг ошибок — обвязка репозитория (ADR-013),
`409 phone_taken` проверяется `curl` в задаче 8.

**Подумай:** `go:embed` видит только свой каталог и ниже — где должен лежать файл с
директивой для `users/migrations`?

## [ ] 7. Users: регистрация и вход

Нужно написать сервис Users — регистрацию клиента и вход с выдачей JWT, чтобы
HTTP-слою оставалось только вызвать его и превратить результат в ответ.
Используя `golang.org/x/crypto/bcrypt` (cost 12) и `golang-jwt/jwt/v5` (HS256) —
подключим перед задачей (ADR-023).

Пароль не длиннее 72 **байт**. Токен: `sub` = id, отдельный claim роли, `exp` = сейчас +
`JWT_TTL`. Неизвестный телефон и неверный пароль — одна ошибка и одинаковое время ответа
(сравнение с фиктивным хешем).

**Проверка:** табличные тесты на fake-репозитории — успех, занятый телефон, пароль
73 байта кириллицей, неверный пароль, неизвестный телефон, содержимое токена.

**Подумай:** фиктивный хеш — считать один раз при старте или при каждом запросе?

## [ ] 8. Users: хендлеры и запуск

Нужно реализовать сгенерированный `StrictServerInterface` и собрать `main.go`, чтобы
Users запускался целиком и отвечал на `/register` и `/login` по контракту.
Используя всё из задач 1–7 и `users/internal/api` (`NewStrictHandlerWithOptions`).

Доменные ошибки → ответы контракта: `phone_taken` → 409, неверный вход → 401
`invalid_credentials`, пароль длиннее 72 байт → 400 с `fields.password`.

**Проверка (итог вечера):**
- регистрация → 201 с токеном; повтор с тем же телефоном → 409 `phone_taken`;
- лишнее поле → 400 `validation_failed`;
- вход клиентом → 200; неверный пароль → 401;
- вход инженером из seed (`+70000000001`, пароль `engineer-example` — в комментарии
  миграции `users/migrations/00002_seed_staff.sql`) →
  200 — это проверка всей цепочки seed.

**Подумай:** валидатор оборачивает strict-хендлер снаружи или изнутри — что увидит
клиент, если перепутать?

## [ ] 9. Middleware идентичности — можно перенести

Нужно написать в `chassis/httpx` middleware, который кладёт `X-User-Id` и `X-User-Role`
в контекст запроса, чтобы сервисы за Gateway знали, кто пришёл, не проверяя токен сами.
Для регистрации и входа не нужен — понадобится Orders (вечер 3).
Используя `context`, `uuid`, конверт из задачи 3 (ADR-037).

Нет заголовков на закрытом маршруте → 401 и **warn**-лог: запрос пришёл мимо Gateway,
это ошибка конфигурации.

**Проверка:** `curl` на первый закрытый маршрут Orders (вечер 3) — заголовки есть → проходит,
нет → 401 и warn в логе, битый UUID → 401. Тестов нет: обвязка, не бизнес-логика (ADR-013).

**Подумай:** почему ключ контекста — свой тип, а не `string`.
