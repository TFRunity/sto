# Вечер 10 — Orders: запись на сервис и взятие в работу

**Итог вечера:** клиент отправляет заявку с реальным ТС, инженер видит её
в общем пуле и становится ответственным.

Схемы: `sequence-book-service`, `sequence-requests-list`, `sequence-claim-order`,
`sequence-create-order`. ADR-017, 019, 020, 021, 028, 031, 037.

**Перед вечером — агент:** согласовать в OpenAPI два варианта `POST /orders`,
описать список заявок и claim, подготовить новые миграции при необходимости и SQL.
Данные записи из ТЗ — ТС, выбранная услуга, дата, комментарий. Формат выбранной
услуги сверить с каталогом вечера 12 до утверждения контракта.

## [x] 1. Развести два сценария создания заказа

Gateway допускает клиента и инженера на `POST /orders` и передаёт их роль.
Хендлер Orders выбирает сценарий по доверенной идентичности. В клиентской
ветке возьми `client_id` из запроса Gateway, проверь доступ к выбранному ТС
через Vehicle до записи и создай `requested` с пустым `engineer_id`.
В инженерной ветке сохрани прямое создание `active` и запись в
`order_engineers` в одной транзакции. Данные записи клиента и оплачиваемая
позиция заказа имеют разные назначения. Позиции с ценой добавляются отдельно.

**Проверка:** клиентская заявка появляется в `requested` без ответственного,
инженерный сценарий из первого этапа продолжает работать.

Оба сценария создания проверены через nginx. Результаты в
[Task_06](../help/Task_06/README.md#подготовка-вечера-10).

## [x] 2. Показать инженеру общий пул

`GET /orders?status=requested` для инженера вызывает запрос списка заявок
с сортировкой по времени создания. В запрос списка передавай только фильтры,
разрешённые этому сценарию. Список показывает заявки всех клиентов,
пока они находятся в `requested`.

**Проверка:** заявки двух клиентов видны инженеру, активный заказ в список не попадает.

Проверено через nginx, включая порядок выдачи, проверку роли и фильтр.
Результаты в [Task_06](../help/Task_06/README.md#общий-пул-заявок).

## [ ] 3. Взять заявку в работу

`PATCH /orders/{id}/claim` получает ID инженера из доверенной идентичности.
Репозиторий в одной транзакции назначает ответственного, переводит заказ в
`active` и добавляет инженера в `order_engineers` через `ON CONFLICT DO NOTHING`.
Поведение при гонке согласуй с ADR-017 и ADR-020: последний инженер становится
ответственным, оба остаются исполнителями. При подготовке SQL отдельно проверь,
что claim не возвращает оплаченный или отменённый заказ в `active`.

**Проверка:** заявка исчезает из пула, в заказе заполнен ответственный, в
`order_engineers` есть связанная строка. Повтор вставки не создаёт дубль.
