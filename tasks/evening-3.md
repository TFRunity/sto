# Вечер 3 — задачи

**Итог вечера:** через `http://sto.localhost/api` инженер создаёт заказ, добавляет в него
товары (цена берётся из Inventory и фиксируется в позиции), читает заказ — сумма верна.

Задачи идут по порядку — каждая опирается на предыдущие. После каждой — ревью.
Отмечай сделанное: `[ ]` → `[x]`.

**Перед вечером — агент (этап 0, `PLAN.md`):**
- `api/openapi.yaml`: `POST /orders`, `GET /orders/{id}`, `POST /orders/{id}/items`,
  `GET /inventory/{id}`; деньги — `type: string` + `x-go-type` decimal (ADR-026, ADR-028);
  в заказе — признак «оплата подтверждена» (`TODO.md` §7); `oapi-codegen.yaml` для Orders
  и Inventory;
- `sqlc.yaml` (overrides `uuid` и `numeric` → decimal) + `queries/*.sql` для Orders и
  Inventory. Условные переходы с `:execrows` понадобятся на вечере 5;
- seed-миграция Inventory: 3–5 товаров с остатком; фиксированный `vehicle_id` и id клиента
  для проверки (у `vehicle_id` нет FK — подойдёт любой uuid, ADR-007).

**ID для проверки:**
- `client_id`: `20000000-0000-4000-8000-000000000001`;
- `vehicle_id`: `20000000-0000-4000-8000-000000000002`;
- первый товар: `10000000-0000-4000-8000-000000000001` (`1500.50`);
- второй товар: `10000000-0000-4000-8000-000000000002` (`350.25`).

Фиксированные `client_id` и `vehicle_id` используются как ссылки в Orders. Для сценария
с оплатой подставь id клиента, возвращённый при регистрации, чтобы он мог войти и оплатить заказ.

## [x] 1. Идентичность запроса — при подключении хендлера Orders

В Gateway оставить `decideRequest` обычной функцией. Проверка JWT и роли остаётся
в `authenticateRequest`, прокси выставляет заголовки идентичности (ADR-037).

Когда появится хендлер создания заказа (задача 7), прочитать и провалидировать
`X-User-Id` прямо в хендлере или простой функцией рядом. При отсутствующем или
некорректном UUID вернуть `401` в конверте ошибок и записать warn в лог. Отдельный
middleware в `chassis` вернётся на обсуждение, когда разбор понадобится нескольким
хендлерам.

## [x] 2. Деньги в пуле Postgres

Нужно научить `chassis/postgres.Connect` регистрировать тип `decimal` на каждом соединении
пула, чтобы `numeric(12,2)` из базы читался в `decimal.Decimal`, а не в строку или
`pgtype.Numeric` (ADR-026).
Используя `pgxpool.ParseConfig`, поле `Config.AfterConnect`, `pgxpool.NewWithConfig` и
`pgxdecimal.Register(conn.TypeMap())` из `github.com/jackc/pgx-shopspring-decimal`.

**Проверка:** в задаче 3 — `GET /inventory/{id}` отдаёт цену `"1500.50"` строкой, без
`1500.5` и без экспоненты. Users продолжает стартовать как раньше. Тестов нет: обвязка.

**Подумай:** у Users денег нет — регистрировать адаптер всем сервисам или передавать
`AfterConnect` параметром? Что проще и что ничего не ломает.

## [x] 3. Inventory: запуск и цена товара

`inventory/internal/item` чтение товара по id, чтобы Orders мог узнать цену и имя товара.
Используя `chassis/config`, `chassis/postgres` (`Connect`, `Migrate`), `chassis/httpx`,
сгенерированные `inventory/internal/db` (sqlc) и strict-сервер из `inventory/internal/api`.

Пока только HTTP: `RABBITMQ_URL` в конфиге уже описан, но консьюмер и outbox — вечер 4.
Товар ищется с `deleted_at IS NULL` (ADR-033); нет товара → `404 item_not_found` (ADR-032).

**Проверка:** `make run SVC=inventory` → миграции и seed применились;
`curl 127.0.0.1:8083/inventory/<id из seed>` → 200 с ценой строкой; несуществующий id →
404 в конверте. Тестов нет: чтение без правил (ADR-013).

**Подумай:** `pgx.ErrNoRows` — где превращать в доменное «не найдено»: в репозитории или в
хендлере? (Ответ уже есть в Users, вечер 1, задача 6.)

## [x] 5. Orders: репозиторий заказов

Нужно написать в `orders/internal/order/repository.go` методы «создать заказ»,
«добавить позицию» и «прочитать заказ», чтобы каждый сценарий был одним методом со своей
транзакцией внутри (ADR-031, D-03).
Используя `pool.Begin`, `defer tx.Rollback(ctx)`, `tx.Commit`, `db.New(pool).WithTx(tx)`
(sqlc), `orders/internal/db`.

- **Создать:** `INSERT orders` сразу `status = 'active'`, `engineer_id` = кто создал +
  `INSERT order_engineers` (ответственный) — **одна** транзакция (`sequence-create-order`,
  ADR-020). `client_id` — как прислали, без проверки в Users (ADR-015).
- **Добавить позицию:** `INSERT order_items` с уже известной ценой; сама цена приходит
  параметром — репозиторий в сеть не ходит.
- **Прочитать:** заказ + позиции + признак «оплата подтверждена»
  (`EXISTS saga_state WHERE current_step = 'completed'`, ADR-030); нет заказа →
  доменное «не найдено».

**Проверка:** в задаче 7, запуском. Тестов нет: SQL-оркестрация (ADR-031, ADR-013).

**Подумай:** позицию в `paid` или `cancelled` заказ добавить можно? Где это проверить —
см. `TODO.md` §7, «принятый риск».

## [x] 6. Orders: клиент Inventory

Нужно написать в Orders HTTP-клиент «товар по id → цена и имя», чтобы сервис добавления
позиции получал цену из Inventory **до** открытия транзакции (ADR-034, ADR-031).
Используя `http.Client{Timeout: …}`, `http.NewRequestWithContext`, `encoding/json`; адрес —
`INVENTORY_URL` из конфига.

Ответы Inventory → доменные ошибки: `404` → «товара нет» (клиенту `404 item_not_found`);
сеть, таймаут, `5xx` → «Inventory недоступен» (клиенту `502 upstream_error`, ADR-032).
Текст чужой ошибки — только в лог.

**Проверка:** в задаче 7 — с остановленным Inventory добавление позиции → 502 в конверте,
позиция не появилась. Тестов нет: обвязка.

**Подумай:** где объявить интерфейс этого клиента — рядом с реализацией или в пакете
`order`, который его использует? Как это поможет подменить его fake-структурой в тесте
сервиса (ADR-013).

## [x] 7. Orders: сервис, хендлеры и запуск

Нужно написать сервис и хендлеры Orders и собрать `orders/cmd/orders/main.go`, чтобы
создание заказа, добавление позиции и чтение работали через nginx → Gateway → Orders.
Используя задачи 1–6, `orders/internal/api` (`NewStrictHandlerWithOptions`), валидатор
из вечера 1.

`engineer_id` — из проверенного `X-User-Id` (задача 1) (ADR-028, ADR-037). Порядок добавления
позиции: цена из Inventory → метод репозитория (`sequence-add-items`). Остаток здесь **не**
списывается — только при оплате (вечер 5). RabbitMQ, воркеры, Gotenberg — позже: в конфиге
переменные уже есть, но `main.go` их пока не запускает.

**Проверка (итог вечера):** `make up SVC="gateway users orders inventory"` (с «можно»),
затем через `http://sto.localhost/api` с токеном инженера из seed:
- `POST /orders` → 201 с id; заказ `active`, в `order_engineers` — инженер;
- `POST /orders/{id}/items` двумя товарами → 201; `GET /orders/{id}` — позиции с ценами,
  сумма совпадает с ручным расчётом, «оплата подтверждена» = `false`;
- несуществующий товар → 404 `item_not_found`; `make stop SVC=inventory` → 502;
- без токена → 401 (Gateway).

**Подумай:** создавать заказ должен только инженер, а оплачивать (вечер 5) — только клиент.
Таблица Gateway различает роли по префиксу, не по методу. Хватит ли этого сейчас — или
проверить роль в хендлере Orders (ADR-019 говорит «роль — в Gateway»)?
