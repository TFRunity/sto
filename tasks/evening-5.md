# Вечер 5 — задачи

**Итог вечера:** клиент оплачивает заказ → `202` → через 1–2 с сага `completed`, у товаров
в Inventory уменьшился остаток, в Orders появилась справка `pending`. Повторная доставка той
же команды остаток второй раз **не** списывает. Не хватило товара → сага `failed`, заказ
снова `active`.

Задачи идут по порядку — каждая опирается на предыдущие. После каждой — ревью.
Отмечай сделанное: `[ ]` → `[x]`.

Главная схема вечера — `uml/sequence/sequence-pay-order.drawio` (шаги 1–18) и ADR-030.
Шаги 19–23 (дедлайн и `CancelStock`) — вечер 6.

**Перед вечером — агент:** `POST /orders/{id}/pay` (202, 409 `order_not_active`) в
`api/openapi.yaml`; запросы sqlc для `saga_state`, `stock_attempts`, `stock_attempt_items`,
условного списания и условных переходов (`:execrows`).

## [x] 1. Inventory: `decide` — чистая таблица решений

Код готов. Табличные тесты остаются открытыми в [TODO.md §9](../TODO.md#9-отложенный-рефактор-сначала-работает-потом-лучше).

Нужно написать в `inventory/internal/stock/decide.go` функцию «состояние попытки + команда →
действие», чтобы вся идемпотентность Inventory жила в одном месте без БД и была закрыта
тестом целиком (ADR-030, D-02, D-07).
Используя только Go: свои типы-перечисления (`const` + `iota` или строки).

| Состояние \ Команда | `DeductStock` | `CancelStock` |
|---|---|---|
| нет попытки | списать (итог — `deducted` или `rejected`) | записать tombstone `cancelled` |
| `deducted` | повторить ответ `StockDeducted` | вернуть остатки → `cancelled` |
| `rejected` | повторить ответ `StockRejected` | ничего |
| `cancelled` | ответить `StockRejected`, не списывать | ничего |

Повтор — это **тот же ответ ещё раз**, не молчаливый ack: первый ответ мог потеряться
(ADR-030).

**Проверка:** табличный тест `decide_test.go` на **все 8** клеток «состояние × команда»
(ADR-013, D-07).

**Подумай:** почему по `cancelled` + `DeductStock` нельзя просто списать — какой порядок
доставки сообщений к этому приводит?

## [x] 3. Orders: старт оплаты

Нужно написать метод репозитория саги «начать оплату» и HTTP-хендлер `POST
/orders/{id}/pay`, чтобы оплата атомарно переводила заказ в `paid`, создавала сагу и
команду `DeductStock` (ADR-030, `sequence-pay-order` шаги 1–6).
Используя `orders/internal/db` (`:execrows`), `chassis/outbox` (вставка в tx, вечер 4),
`CanStartPayment` (вечер 3, задача 4).

Одна транзакция:
1. `UPDATE orders SET status = 'paid' WHERE id = $1 AND status = 'active'` — 0 строк →
   `409 order_not_active`;
2. `INSERT saga_state` (`saga_id = uuid.New()`, `verifying_stock`, `deadline = now() +
   interval '10 seconds'`);
3. позиции заказа → outbox `DeductStock {saga_id, order_id, items[{item_id, qty}]}`.

Ответ — `202 Accepted` без ожидания саги; клиент перечитывает заказ (А-06). Повтора нет
(ADR-016).

**Проверка:** в задаче 6. Тестов нет: SQL-оркестрация (ADR-031); правило «только active» уже
под тестом.

**Подумай:** `CanStartPayment` проверяет статус, но условный `UPDATE` тоже. Зачем тогда чистая
функция, если база всё равно решает? (Подсказка: пустой заказ из вечера 3.)

## [x] 4. Inventory: обработка `DeductStock`

Нужно написать метод репозитория «обработать DeductStock» и подключить его к консьюмеру
`inventory.saga_commands`, чтобы списание, запись попытки и ответ шли одной транзакцией
(ADR-030, ADR-005, `sequence-pay-order` шаги 8–13).
Используя `decide` (задача 1), `chassis/outbox`, `json.Unmarshal` по `Delivery.Type`.

Одна транзакция:
- прочитать попытку по `saga_id` (нет → «нет попытки») → `decide`;
- «списать»: по каждой позиции `UPDATE inventory SET quantity = quantity - $2 WHERE id = $1
  AND quantity >= $2 AND deleted_at IS NULL`; хоть одна дала 0 строк → откатить **все**
  списания этой команды и записать `rejected` (ADR-030);
- `INSERT stock_attempts` (+ `stock_attempt_items` при `deducted`);
- ответ `StockDeducted` / `StockRejected {saga_id, order_id}` → outbox Inventory.

Ack — только после `Commit` (ADR-025): обработчик возвращает `nil` после коммита.

**Проверка:** в задаче 6. Тестов нет: SQL-оркестрация; решения — в `decide`.

**Подумай:** «откатить все списания команды, но записать `rejected`» — это внутри одной
транзакции. Как: `SAVEPOINT` (`tx.Begin` во вложенной `pgx.Tx`) или сначала проверить
остатки, потом списывать? Чем плохо второе (ADR-031, условный UPDATE)?

## [x] 5. Orders: консьюмер ответов

Нужно написать метод репозитория «применить ответ» и подключить его к консьюмеру
`orders.saga_replies`, чтобы сага завершалась или откатывалась, а при успехе рождалась
справка (ADR-030, ADR-035, шаги 15–18).
Используя функцию шага (задача 2), условные `UPDATE` с `:execrows`.

- `StockDeducted`: `UPDATE saga_state SET current_step = 'completed' WHERE saga_id = $1 AND
  current_step = 'verifying_stock'` → 1 строка → `INSERT certificates (status='pending',
  next_attempt_at = now())` в **той же** транзакции;
- `StockRejected`: сага → `failed` (условно) + `UPDATE orders SET status = 'active' WHERE id
  = $1 AND status = 'paid'`;
- 0 строк или неизвестная сага → warn-лог, `nil` (ack): другой участник успел раньше
  (D-02).

**Проверка:** в задаче 6.

**Подумай:** консьюмер ответов и воркер дедлайнов (вечер 6) будут менять одну и ту же сагу
одновременно, в одном процессе. Почему mutex в Go здесь хуже условного `UPDATE` (ADR-030,
«Альтернативы»)?

## [x] 6. Сквозная проверка саги

Успешная оплата и повтор доставки подтверждены [предыдущим прогоном](../help/TASK_2/review.md).
Два дополнительных сценария прошли на локальном Compose через nginx:

- Повторная оплата уже оплаченного заказа вернула `409 order_not_active`. В БД осталась
  одна сага для этого заказа.
- Заказ `40415c49-2940-40c6-b6a8-f15e6a992750` запросил 1 единицу первого товара при
  остатке 18 и 41 единицу второго при остатке 40. Старт вернул `202`, затем Inventory
  отправил `StockRejected`, сага перешла в `failed`, заказ вернулся в `active`. Остатки
  сохранились на 18 и 40 единицах. Записей о списании и справки нет. `CancelStock` в
  outbox отсутствует, поэтому отказ подтверждён отдельно от сценария дедлайна.

Успех, отказ и дубль проверены через nginx.
Используя всё из вечеров 3–5.

**Проверка (итог вечера):** `make up` (с «можно»), через `http://sto.localhost/api`:
- инженер создаёт заказ и добавляет товар; клиент `POST /orders/{id}/pay` → 202;
- через 1–2 с `GET /orders/{id}` → `paid`, «оплата подтверждена» = `true`; в `saga_state` —
  `completed`; в `certificates` — `pending`; остаток в Inventory уменьшился;
- повторная оплата → 409 `order_not_active`;
- **дубль:** в `orders-db` у строки outbox `DeductStock` поставить `published = false` → она
  уйдёт снова → остаток **не** изменился, в outbox Inventory — второй такой же
  `StockDeducted`, в логе Orders — warn «сага уже завершена»;
- **отказ:** заказ с количеством больше остатка → оплата → сага `failed`, заказ снова
  `active`, остаток не изменился.

**Подумай:** где в логах видно, что второй `StockDeducted` пришёл именно на дубль, а не на
новую оплату? Хватит ли `saga_id` в каждой строке лога.
