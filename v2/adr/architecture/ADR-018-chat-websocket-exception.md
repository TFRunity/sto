# ADR-018: WebSocket для доставки сообщений чата — исключение из правила "RabbitMQ только между сервисами"

> **v2.** Решение относится к модулю Chat, который вынесен из v1 (19.10.2026). В v1 не реализуется; сохраняется как принятое проектное решение для v2.

## Статус
Принято

## Контекст
Общий паттерн проекта (см. `sequence-photofix.drawio`, а также perimeter
trust, ADR-010): взаимодействие клиент/инженер ↔ сервис идёт через
синхронный HTTP-запрос к Gateway, RabbitMQ используется исключительно
для обмена между Go-сервисами. Для отправки сообщения в чат этот
паттерн подходит без изменений — "написать в чат" остаётся обычным
`POST` через Gateway в Chat.

Получение новых сообщений в реальном времени, однако, не решается
синхронным HTTP по своей природе: клиенту нужно узнавать о новом
сообщении от собеседника без действия с его стороны, инициирующего
запрос.

## Решение
Для доставки входящих сообщений в реальном времени используется
WebSocket-соединение клиент ↔ Chat service (через Gateway). Это
осознанное исключение из общего паттерна "клиент общается с сервисами
только через синхронный HTTP" — специфика чата (push от сервера, а не
запрос от клиента) требует другого транспорта.

RabbitMQ в этой схеме не участвует ни в каком виде: соединение остаётся
в рамках perimeter trust (ADR-010), просто по протоколу WS, а не HTTP.
Отправка сообщения (клиент → сервер) остаётся обычным HTTP `POST`, как
и везде — WebSocket используется только для доставки от сервера к
клиенту.

## Альтернативы, которые рассматривались
- **Long-polling / обычный polling** — отклонено: для чата ощутимая
  задержка обновления хуже, чем стоимость поддержки WS-соединения. В
  отличие от оплаты/отчётов (где проект последовательно выбирает
  простоту, см. ADR-016, ADR-017), здесь дополнительная сложность ради
  реального времени осознанно оправдана — это ядро функциональности
  чата, а не побочная гарантия.
- **Доставка через RabbitMQ до клиента** — отклонено: RabbitMQ в
  проекте зарезервирован для меж-сервисного (Go↔Go) обмена (см.
  `sequence-photofix.drawio`, где клиент-сервисное взаимодействие явно
  разведено с брокером); клиент не является участником брокера ни в
  каком другом сценарии проекта — вводить исключение именно здесь
  означало бы ничем не обоснованную связанность клиента с
  инфраструктурой брокера.

## Последствия
**Плюсы:** мгновенная доставка сообщений без задержки поллинга;
отправка сообщений остаётся простым HTTP, консистентным с остальным
API.

**Минусы:** Chat service становится единственным сервисом в проекте,
поддерживающим долгоживущие стейтфул-соединения — отдельно потребуется
продумать переподключение при обрыве связи и, при будущем
горизонтальном масштабировании Chat на несколько инстансов,
маршрутизацию сообщений к тому инстансу, где держится соединение
конкретного пользователя. Пока Chat не масштабируется горизонтально,
это не блокер.
